## Introduction

Brief context (1–3 paragraphs) describing the engineering surface in
play, the contract that is being violated, and the population that
suffers from the breakage. The fix-spec's reader is a Tech Spec author
or an implementation agent — sometimes a junior developer. Hold to:

- **Explicit and unambiguous.** No prose that requires guessing at intent.
- **Define jargon on first use** or avoid it.
- **Numbered FR-N IDs are load-bearing.** Every functional requirement
  (`FR-1`, `FR-2`, …) gets a stable ID so the Tech Spec and the
  Acceptance Criteria document (Phase 3) can cite it.
- **Concrete examples** where they shorten understanding.

## What Broke

Name the contract that is being violated and how the violation
manifests. Concrete: which file / module / command / endpoint / cron
job. The fix-spec's posture is **diagnose-first**, not design-first;
the answer to "what broke" is the load-bearing input.

- <one or more bullets describing the broken contract>

## Reproduction / Trigger

The exact path that surfaces the breakage. A reproduction is the
preferred shape (a sequence of commands or events that the reader can
replay); an event-driven trigger (cron tick, deploy step, request
shape) is the fallback. Vague descriptions ("sometimes the API fails
under load") mean the trigger is not yet shaped — the dialogue should
have asked for more.

- <reproduction step 1>
- <reproduction step 2>

## Expected Behavior

The contract the system is supposed to honor. Anchor to a concrete
source: a documented behavior, a runtime invariant, a specification
section, a prior commit's intent. "Should support X" without an
existing contract anchor signals design-rethink and trips the
narrowness gate's contract-shape proxy.

- <expected behavior, with anchor>

## Observed Behavior

What actually happens when the trigger fires. Concrete: a stack trace,
a wrong return value, a missing side-effect, a degraded latency
measurement. Not "users complain" — "users complain about <observable
symptom>".

- <observed behavior>

## Blast Radius

Who and what is affected by the breakage. Replaces the PRD's "Audience"
+ "Success Metrics" framing — for a fix, the population is whoever
depends on the violated contract and the success metric is binary
("the bug stops reproducing"). Surface the radius in concrete bands:

- **Single function / file** — one call site or one helper.
- **One module** — multiple call sites within a single logical
  surface (e.g. one auth flow, one CLI command, one cron job).
- **Cross-module** — surfaces span multiple modules but stay within
  one service.
- **Cross-service** — multiple services, multiple deploys, or
  multiple owners affected.

Pick the narrowest band that still describes the truth. The narrowness
gate's surface-containment proxy fails when the radius reaches
cross-module / cross-service without a contract anchor pinning the
boundary.

- <blast radius statement>

## Functional Requirements

satisfy. Same shape as the PRD's FR-N: each must be specific enough
that a sensor can decide pass/fail. The Acceptance Criteria document
(Phase 3) decomposes these into per-User-Story DoD and AC entries via
the Senior-QA grill.

- **FR-1:** The fix must <restore-the-contract specifically>.
- **FR-2:** When <trigger fires>, the system must <observable correct response>.
- **FR-3:** <requirement>
