# Pattern: Acceptance Contract — Binding Pre-Runtime Artifact

<!-- vibeflow:auto:start -->
## What
The Acceptance Contract is a binding artifact produced by the Validator in
Phase 3 from the approved PRD and Tech Spec. After human ratification
(Trigger 3), it is the **operational definition of "done"** for the task.
Any change during Phase 4 requires a fresh ratification round — sprint
contracts cannot override it.

## Where
Lives as `acceptance-contract.md` in working memory of the task. Consumed by
the Validation Agent during Phase 4 and by the Orchestrator when judging
loop stop conditions.

## The Pattern

### Required content
- **Use cases → BDD scenarios** (Given / When / Then), one per use case from the Tech Spec.
- **Validation fixtures** for each scenario.
- **Measurable functional requirements** mapped to scenarios or sensors.
- **Applicable policies** (PCI-DSS, LGPD, internal MUST policies, etc.).
- **Computational sensors** that will run during the loop (linters, type checks, structural tests, unit tests).
- **Inferential sensors** calibrated for this scope (semantic judge prompts, rubrics).

### Generation contract
The Validator generates this artifact by:
1. Reading PRD + Tech Spec from working memory.
2. Querying canonical memory through the Orchestrator for applicable regulatory policies, approved fixtures and known sensors.
3. Drafting the Contract.
4. Pausing for Trigger 3 ratification.

### Binding semantics
"Done" = every criterion in the Contract passes. There is no other definition.
- The user can reject during Trigger 3 or send the artifact back for revision.
- Once ratified, only a fresh Trigger 3 can change it.
- Inside Phase 4, sprint contracts negotiate sub-interpretations **inside** the Contract envelope. They cannot relax it.

## Rules
- The Contract is generated by the Validator, not the Generator. The role separation is the point.
- Every BDD scenario must have at least one fixture or sensor that can decide pass/fail.
- Inferential sensors must be calibrated against the specific scope of this Contract — not generic prompts.
- Regulatory policies are non-negotiable. They cannot be overridden by sprint contracts or by user edits at Trigger 3 unless Compliance ratifies.
- A Contract without measurable criteria is rejected. "Looks good" is not a criterion.

## Anti-patterns
- BDD scenarios without fixtures or sensors — the Contract becomes unenforceable.
- Generic semantic judges reused across unrelated scopes — calibration drift, false negatives.
- Allowing the loop to "interpret" the Contract liberally — sprint contracts must cite the Acceptance Contract clause they refine, not paraphrase it.
- The Generator producing the Contract — collapses Generator/Validator separation and reintroduces self-evaluation bias.
- Modifying the Contract after Trigger 3 without a fresh ratification — destroys binding semantics; future tasks lose trust in the gate.

## Implementation Mapping

From `yoke-implementation-plan.md` (2026-04-24) — concrete artifacts:

- **Producer skill** — `/yoke:acceptance-contract` (`skills/acceptance-contract/SKILL.md`).
- **Producer subagent** — `agents/validator.md` (separate from `agents/generator.md` so role separation is structural, not a mode flag).
- **Template** — `templates/acceptance-contract.md` with sections for BDD scenarios, fixtures, FRs, policies, computational sensors, inferential sensors, and an explicit binding statement.
- **Sensor discovery** — `lib/sensors/discover-from-claude-md.sh` parses the host project's `CLAUDE.md` for `## Testing`, `## Linting`, `## Build` sections to populate the sensor list. Fallback: Validator asks the user.
- **Verification hook** — `hooks/verify-acceptance.sh` consumes the Contract and runs each declared sensor; status is `pass` / `fail` / `skip` per criterion.
- **Pre-conditions** — skill aborts if `.yoke/prd.md` or `.yoke/tech-spec.md` are missing or unapproved.

Sprint-3 ships only "shell command" sensor support (e.g. `npm test`, `pytest`).
Richer sensor types (structural fixtures, inferential semantic judges with
rubrics) ship in later sprints.
