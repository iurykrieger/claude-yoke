> **Definition of Done vs Acceptance Criteria — distinct, layered.**
> **DoD** is a single binary checklist per User Story that defines when
> the implementation is *finished*. **Acceptance Criteria** are
> multiple observable QA conditions per User Story that, given the
> implementation is done, define when the work is *acceptable* in
> quality terms. The runtime council enforces ordering: DoD checks
> must pass before any AC is evaluated for that story.

> collapse a runtime-policy decision into an authoring-time decision.

## User Stories

### US-001 — Author a fix-spec via the new Phase-1 entrypoint

As a Yoke user with a bug or narrow engineering task, I want to invoke
`/yoke:fix` with a problem statement and have the skill grill me on
diagnose-first questions (what broke / repro / expected / blast
radius) instead of product-shaped questions, so that I can document
the fix in engineering shape and chain into the existing
tech-spec → acceptance-criteria → implement cycle without ceremony
tax.

#### Definition of Done

- [ ] `skills/fix/SKILL.md` exists and is registered in
      `.claude-plugin/plugin.json` as `/yoke:fix`.
- [ ] The skill body opens its persona block with the line
      `**Mode:** diagnose-first` on the first line under "Your role".
- [ ] On a happy-path invocation with a 4/4-readiness input, the skill
      writes `.yoke/fixes/<slug>.md` and chains into `/yoke:tech-spec`
      via the `Skill` tool from the approval menu's option 1.
- [ ] `templates/fix.md` exists and carries every section listed in
      PRD FR-7 in the documented order.
- [ ] Smoke test at `tests/smoke/fix-skill-happy-path.test.sh` covers
      the full PRD-backed and fix-backed flow end-to-end.

#### Acceptance Criteria

- **AC-001-1:** Running `/yoke:fix "axios CVE bump to 1.6.0"` on a
  clean `.yoke/runtime/` produces `.yoke/fixes/<YYYY-MM-DD>-axios-cve-bump.md`
  (or a semantically equivalent slug) carrying `Status: approved`,
  `scope_caution:` (empty when 4/4 narrowness proxies pass), and the
  PRD FR-7 section ordering, with `wm_active_slug` returning the
  same slug.
- **AC-001-2:** The persona body's first line under "Your role"
  matches the regex `^\*\*Mode:\*\*\s+diagnose-first\s*$` exactly,
  enforced by a `tests/sensors/persona-mode-tag.test.sh` sensor that
  scans both `skills/fix/SKILL.md` and `skills/tech-spec/SKILL.md`.
- **AC-001-3:** Approval-menu option 1 (`approve_and_continue`) on a
  happy-path fix-spec invokes `/yoke:tech-spec` via the `Skill` tool
  in the same turn (no manual paste from the user); the fallback
  branch fires only when the `Skill` tool is unavailable.
- **AC-001-4:** Re-running `/yoke:fix` on a slug already owned by
  `/yoke:discover` (a `.yoke/prds/<slug>.md` exists) hits FR-4's
  collision check during slug proposal, regenerates a *semantically
  distinct* slug, and writes the fix-spec under the new slug — never
  silently overwrites the PRD or appends a numeric suffix.

### US-002 — Block feature smuggling via narrowness gate

As a Yoke maintainer, I want `/yoke:fix` to refuse inputs that
describe new desired behavior rather than broken existing behavior,
so that the Phase-1 product framing protection is preserved on the
new path and `/yoke:fix` does not become a universal Phase-1
backdoor.

#### Definition of Done

- [ ] The skill's persona body declares the four narrowness proxies
      verbatim (component breadth / contract shape / trigger
      specificity / surface containment), anchored to host-project
      structure read at skill startup.
- [ ] `templates/fix.md`'s frontmatter carries the mandatory
      `scope_caution:` field with the documented value space (empty
      | `component-breadth` | `contract-shape` | `trigger-specificity`
      | `surface-containment`).
- [ ] The skill writes `scope_caution: <proxy-id>` into the fix-spec
      frontmatter when 3/4 proxies pass and aborts with a re-route
      prompt to `/yoke:discover` when ≤ 2/4 pass.

#### Acceptance Criteria

- **AC-002-1:** Running `/yoke:fix "add OAuth2 support to the auth
  middleware"` (feature-add language, no contract reference) trips
  the narrowness gate's contract-shape proxy and produces a re-route
  prompt offering `/yoke:discover`; the skill exits non-zero
  without writing any file under `.yoke/fixes/`.
- **AC-002-2:** Running `/yoke:fix "extract notification logic from
  the user service into a separate module"` (3/4 narrowness — passes
  contract / trigger / surface but soft-fails component-breadth)
  produces a fix-spec carrying `scope_caution: component-breadth` in
  its frontmatter, exit-code 0, and the standard Trigger 1 surface.
- **AC-002-3:** A fix-spec written by the skill always carries the
  `scope_caution:` key in its frontmatter (even when empty); a
  fix-spec missing the key is rejected by a
  `tests/sensors/fix-spec-frontmatter-shape.test.sh` sensor that
  walks `.yoke/fixes/` and asserts the schema.
- **AC-002-4:** Mid-dialogue scope inflation re-evaluates the four
  proxies on the cumulative dialogue answers; if a previously-narrow
  input becomes ≤ 2/4 after the user answers, the skill aborts with
  the same re-route prompt instead of completing the draft.

### US-003 — Path-agnostic Phase-1 input across downstream skills

As a Yoke maintainer, I want every downstream skill to read the
Phase-1 input via `wm_phase1_artifact_path`, so that the fix-spec
and PRD are interchangeable from Phase 2 onwards without any skill
branching its core logic on which artifact backed the slug.

#### Definition of Done

- [ ] `wm_fix_path` and `wm_phase1_artifact_path` exported from
      `lib/working-memory/paths.sh`; the latter's docstring states
      that the existence-aware contract does not propagate to future
      helpers.
- [ ] `/yoke:tech-spec`, `/yoke:acceptance-criteria`,
      `/yoke:implement`, `/yoke:canonize`, and `/yoke:status` all
      consume `wm_phase1_artifact_path` instead of `wm_prd_path` for
      Phase-1-artifact reads; pre-flight error messages updated to
      "Run `/yoke:discover` or `/yoke:fix` first."
- [ ] New sensor at `tests/sensors/no-direct-prd-path.test.sh`
      grep-audits `skills/` and fails on any `wm_prd_path` read
      outside `skills/discover/SKILL.md` and `skills/fix/SKILL.md`.

#### Acceptance Criteria

- **AC-003-1:** `grep -rE "wm_prd_path" skills/ | grep -v -E
  "skills/(discover|fix)/SKILL\.md"` returns zero matches; the
  no-direct-prd-path sensor exits 0 in CI on every PR.
- **AC-003-2:** Every existing PRD-backed task in the project's
  test corpus completes the full PRD → tech-spec → AC → implement
  → canonize chain end-to-end with no path-resolution errors —
  measured against a regression suite of ≥ 5 representative
  PRD-backed scenarios under `tests/regression/phase1-backward-compat/`.
- **AC-003-3:** A fix-spec-backed task (a slug with only
  `.yoke/fixes/<slug>.md` and no PRD) flows through the same
  downstream chain end-to-end with no path-resolution errors,
  proving the resolver's symmetry — measured against a smoke
  test at `tests/smoke/fix-spec-end-to-end.test.sh`.
- **AC-003-4:** The plugin manifest at
  `.claude-plugin/plugin.json` declares the new skill and its
  version is bumped per Yoke's "each sprint produces an
  installable plugin version" decision; the manifest passes
  schema validation in CI.

### US-004 — Fail loudly on Phase-1 archive corruption

As a Yoke user, I want `wm_phase1_artifact_path` to hard-abort
with a structured recovery diagnostic when both `.yoke/prds/<slug>.md`
and `.yoke/fixes/<slug>.md` exist for the same slug, so that
archive corruption never silently propagates into Phase 2 driving
a tech-spec from the wrong artifact.

#### Definition of Done

- [ ] `wm_phase1_artifact_path` aborts non-zero on the "both exist"
      and "neither exists" cases with the verbatim PRD-FR-9
      diagnostic shape (paths + first-100-bytes excerpts +
      last-commit shas + remediation recipe).
- [ ] `wm_set_active` enforces the same invariant on write —
      refuses to record a slug whose archives carry both files,
      printing the FR-9 diagnostic verbatim.
- [ ] The diagnostic message is ratified verbatim in this AC
      document (see AC-004-1) so the sensor scanning stderr has a
      stable substring target.

#### Acceptance Criteria

- **AC-004-1:** When both `.yoke/prds/<slug>.md` and
  `.yoke/fixes/<slug>.md` exist on disk for slug `<slug>`,
  invoking any caller of `wm_phase1_artifact_path` (read or
  write path) emits to stderr a message starting exactly with
  `wm: ambiguous Phase-1 state for slug '<slug>'` and exits
  non-zero. The full diagnostic includes both paths, first-100
  bytes of each file body, last commit sha + author + ISO-8601
  timestamp for each file, and a `git rm` example recipe.
- **AC-004-2:** When neither `.yoke/prds/<slug>.md` nor
  `.yoke/fixes/<slug>.md` exists, the resolver emits a `wm:`-prefixed
  diagnostic ending with the literal remediation hint
  `Run /yoke:discover or /yoke:fix first.` and exits non-zero.
- **AC-004-3:** `wm_set_active` invoked with a slug whose archives
  contain both files refuses to record `.yoke/runtime/.current` and
  prints the same diagnostic; the file at `.yoke/runtime/.current`
  is not modified.
- **AC-004-4:** A new CI gate at
  `tests/sensors/no-ambiguous-phase1.test.sh` greps every test
  output stream for the substring `wm: ambiguous Phase-1 state` and
  fails the build if found in main-branch CI runs.

### US-005 — Backfill Mode tag into /yoke:tech-spec for OQ-2 resolution

As a Yoke maintainer, I want `/yoke:tech-spec`'s persona body to
declare `**Mode:** design-first`, so that the two-tier (literal name
+ Mode tag) convention from PRD OQ-2 is consistent across both
engineering Phase-skills and future engineering-flavored skills
inherit a clean precedent.

#### Definition of Done

- [ ] `skills/tech-spec/SKILL.md` opens its persona block with the
      line `**Mode:** design-first` on the first line under "Your
      role".
- [ ] `concepts/yoke-conventions` (canonical-memory entity) carries
      a new section ratifying the Mode-tag convention: open
      vocabulary, initial values `diagnose-first` and `design-first`.
- [ ] The Phase-5 canonize handoff for this task includes the
      Mode-tag amendment as a Model C write proposal classified at
      least as **medium impact** (notify-and-apply).

#### Acceptance Criteria

- **AC-005-1:** `head -50 skills/tech-spec/SKILL.md | grep -E
  "^\*\*Mode:\*\*\s+design-first\s*$"` returns exactly one match.
- **AC-005-2:** The persona-mode-tag sensor (per AC-001-2) walks
  every engineering-flavored skill body and asserts each declares a
  well-formed Mode tag; the sensor's catalog at
  `tests/sensors/persona-mode-tag.test.sh` lists `skills/fix/SKILL.md`
  and `skills/tech-spec/SKILL.md` as in-scope and exits 0 in CI.
- **AC-005-3:** The canonize-handoff package produced at Phase 5
  termination contains a proposed amendment to
  `concepts/yoke-conventions` introducing the Mode-tag convention,
  classified as `model_c_impact: medium` in the proposal frontmatter
  and pointing at PRD OQ-2 / Spec Alt(b) for traceability.
