## Introduction

`agents/orchestrator.md` is the persona prompt loaded by `/yoke:implement`
when it spawns the Orchestrator subagent at full-run termination. The
prompt's job is to teach the persona how to hand off to `/yoke:canonize`
(the v2.0.0 facade verb that dispatches to the active canonical-memory
provider and is the sole surface through which Model C writes happen).

In the v2.0.0 cutover (Part 4 of the bedrock canonical-memory port), the
helper script `lib/canonical-memory/canonization-criteria.sh` was retired:
the five-criterion cascade and the impact-classification keyword
heuristics were moved inside `/yoke:canonize`'s Phase 3, where they
became implementation detail of the facade rather than a tool the
Orchestrator persona invokes. The orchestrator prompt was updated in
three sites to acknowledge the retirement (the v3.0 cutover note at
lines 31–54 and the prose at lines 81–82, 97–98, 192–193 all say "Part 4
of the bedrock canonical-memory port retired that primitive").

The same prompt nonetheless continues to cite the retired script as if
it were a live invocation surface in four other sites — lines 78, 100,
142, and 190. The document is internally contradictory: it tells the
persona "this script is retired" and "invoke this script" in the same
breath. This fix-spec captures the violated contract and the FR set
that closes it.

## What Broke

`agents/orchestrator.md` cites `lib/canonical-memory/canonization-criteria.sh`
in four sites that frame the script as a current invocation surface,
while three other sites in the same file declare the script retired in
v2.0.0. The script does not exist on disk
(`lib/canonical-memory/canonization-criteria.sh` returns "MISSING").

The four offending sites:

- **Line 78** — Canonize-mode prose: "`/yoke:canonize` performs the work
  that v1.1 split across this agent: it invokes
  `lib/canonical-memory/canonization-criteria.sh` to apply the
  five-criterion cascade …". Frames the retired script as the
  dispatch target.
- **Line 100** — Impact-classification-rules section: "`/yoke:canonize`
  invokes `lib/canonical-memory/canonization-criteria.sh --classify-impact`
  with the same keyword heuristics …". Names a `--classify-impact` flag
  on the retired script.
- **Line 142** — `### Never` clause: "`/yoke:canonize` invokes
  `lib/canonical-memory/canonization-criteria.sh` in Phase 3 to apply
  it [the five-criterion filter]". Reasserts the retired script as the
  filter implementation.
- **Line 190** — Allowed-tools `Bash` clause: "`Bash` — reserved for
  canonize-time deterministic helpers invoked from inside `/yoke:canonize`
  (e.g. `lib/canonical-memory/canonization-criteria.sh`)". Lists the
  retired script as the canonical example of a Bash-callable helper.

## Reproduction / Trigger

Any reader (human or agent) following the orchestrator prompt's
documented flow hits the contradiction. Concrete reproduction:

1. From the repo root, run `grep -n "canonization-criteria"
   agents/orchestrator.md` — observe four hits at lines 78, 100, 142, 190.
2. Run `test -f lib/canonical-memory/canonization-criteria.sh` — observe
   that the file does not exist (the v2.0.0 retirement removed it).
3. Compare with the v3.0 cutover note (lines 31–54) and the retirement
   sentences at lines 81–82, 97–98, 192–193, all of which state the
   script is retired and the responsibility now lives inside `/yoke:canonize`.

A Claude Code session that loads `agents/orchestrator.md` as a persona
prompt will receive contradictory instructions: the cutover note tells
it to invoke `/yoke:canonize` opaquely; the offending sites tell it the
facade is implemented as a shell-out to a script that cannot be located.

## Expected Behavior

The orchestrator prompt MUST treat `/yoke:canonize` as an opaque
dispatch surface and MUST NOT name internal helpers of the canonize
skill in any site that frames them as live invocation targets.

Contract anchors:

- **Self-anchor inside the same file.** Lines 31–54 (v3.0 cutover note)
  and lines 81–82, 97–98, 192–193 explicitly declare
  `canonization-criteria.sh` retired and route all responsibility
  through `/yoke:canonize`. The four offending sites contradict that
  declaration.
- **v2.0.0 architecture anchor.** `CLAUDE.md`'s "Migration history"
  entry for 2026-04-30 (v2.0.0) states the canonical-memory implementation
  was extracted to a peer plugin and replaced by two facade verbs
  (`/yoke:search-canonical-memory` and `/yoke:canonize`). Naming
  internal helpers of the facade leaks the retired single-vendor
  implementation back into a persona prompt.
- **Pattern anchor.** `concepts/yoke-pattern-roles` defines the
  Orchestrator's surface as canonize-only and isolates it from
  provider-specific helpers. The four offending sites violate that
  isolation by surfacing a provider-internal script name in the
  persona prompt.

## Observed Behavior

- `grep -n "canonization-criteria" agents/orchestrator.md` returns
  exactly four matches:
  - line 78 (Canonize-mode prose)
  - line 100 (Impact-classification-rules section)
  - line 142 (`### Never` clause about the five-criterion filter)
  - line 190 (Allowed-tools `Bash` clause)
- `test -f lib/canonical-memory/canonization-criteria.sh` returns false.
- The combined effect: a persona instructed to invoke a tool that does
  not exist. Any literal-minded follow-through silently fails or aborts
  the canonize step.

## Blast Radius

**Single file.** The breakage is confined to `agents/orchestrator.md`.
No other repository file currently cites
`lib/canonical-memory/canonization-criteria.sh` as a live invocation
target (the only other occurrences are in archived fix-specs and
audit reports describing the v2.0.0 retirement itself).

The downstream radius — sessions that load the orchestrator prompt
during `/yoke:implement` runs — is large in principle, but the fix's
edit surface is one file and one paragraph per offending site.

## Root-Cause Hypothesis (optional)

The v2.0.0 cutover (Part 4 of the bedrock canonical-memory port)
edited the prompt by **adding** retirement notes alongside the existing
prose rather than rewriting the affected paragraphs. The contradictory
sites at lines 78, 100, 142, 190 are leftovers of that additive edit.

## Functional Requirements

- **FR-1:** The string `lib/canonical-memory/canonization-criteria.sh`
  MUST NOT appear anywhere in `agents/orchestrator.md` after the fix.
  A `grep -n "canonization-criteria" agents/orchestrator.md` MUST
  return zero matches.
- **FR-2:** The Canonize-mode prose at line 78 MUST be rewritten so
  `/yoke:canonize` is described as the opaque dispatch surface that
  applies the five-criterion cascade and classifies Model C impact,
  without naming any internal helper of the canonize skill.
- **FR-3:** The Impact-classification-rules section starting at
  line ~95 MUST be reshaped so that the Orchestrator persona is told
  impact classification "happens inside `/yoke:canonize` Phase 3" and
  that the keyword-heuristics table documents what `/yoke:canonize`
  applies on the persona's behalf — without naming
  `canonization-criteria.sh` or any `--classify-impact` flag.
- **FR-4:** The `### Never` clause at line ~140 MUST be rewritten so
  the five-criterion-filter prohibition reads: "Never bypass the
  five-criterion filter — `/yoke:canonize` applies it in Phase 3; do
  not propose canonization candidates that have not been filtered" —
  without naming the retired script.
- **FR-5:** The Allowed-tools `Bash` clause at line ~188 MUST be
  rewritten so the persona's `Bash` allowance is justified by the
  canonize skill's internal use of deterministic helpers, without
  naming `canonization-criteria.sh` or any other retired primitive.
  Pure removal (deleting the example) is acceptable; substituting a
  current example is acceptable; reframing the Bash allowance around
  the active facade verb is acceptable.
- **FR-6:** The fix MUST NOT introduce or rename any file under
  `lib/canonical-memory/`, MUST NOT touch any other persona prompt
  (`agents/sr-eng.md`, `agents/sr-qa.md`, `agents/sr-staff.md`,
  `agents/council-arbiter.md`), and MUST NOT change `skills/canonize/`
  or `skills/implement/` content. The fix is doc-shaped.
- **FR-7:** The retirement statements already present at lines 31–54
  (v3.0 cutover note), 81–82, 97–98, and 192–193 MUST remain intact
  in spirit (they may be reorganized for prose flow, but the
  declarative content "Part 4 of the bedrock canonical-memory port
  retired that primitive" or its semantic equivalent MUST survive at
  least once in the file).
- **FR-8:** After the fix lands, the file's "v3.0 cutover note" block
  (lines 31–54) and any retirement assertion still present MUST NOT
  contradict any remaining prose elsewhere in the file. Internal
  consistency is a binary check: either every site agrees the script
  is retired and `/yoke:canonize` is the dispatch surface, or the
  fix has not landed.

## Non-Goals (Out of Scope)

- **Rewriting `/yoke:canonize` itself.** The skill's internal
  implementation (Phase 3, the five-criterion cascade, impact
  classification) is unaffected and unchanged by this fix.
- **Re-introducing or renaming `canonization-criteria.sh`.** The
  v2.0.0 retirement is doctrine; this fix accepts it and updates the
  doc to match.
- **Touching other persona prompts.** Sr Eng / Sr QA / Sr Staff /
  Council Arbiter prompts are out of scope. Only
  `agents/orchestrator.md` is edited.
- **Editing the canonize skill body** (`skills/canonize/SKILL.md` or
  any sub-skill / template under `skills/canonize/`).
- **Auditing or migrating other doc-doctrine drift.** This fix is a
  surgical doc edit; broader v2.0.0 doctrine-sync passes belong to a
  separate `/yoke:fix` invocation or to `/yoke:drift-sense --target
  codebase` follow-ups.
- **Authoring User Stories.** Phase 3 (`/yoke:acceptance-criteria`)
  owns US authoring; this fix-spec emits FR-N only.

## Risks

- **Risk: prose drift introduces a fresh contradiction.** Rewriting
  four paragraphs in close proximity risks producing a new internal
  contradiction (e.g. one site saying "Phase 3 of `/yoke:canonize`"
  and another saying "Phase 4"). Signal: any post-fix
  `grep -n "Phase [0-9]" agents/orchestrator.md` output where the
  same dispatch step is named with two different phase numbers.
  Mitigation: cross-check phase references after the edit lands.
- **Risk: Bash-tool allowance loses justification.** If FR-5 is
  satisfied by pure removal of the example, the
  Allowed-tools `Bash` clause may end up under-justified ("`Bash` —
  reserved for canonize-time deterministic helpers invoked from
  inside `/yoke:canonize`" with no example). Signal: Sr Staff review
  flagging the clause as load-bearing-but-content-free. Mitigation:
  reframe the allowance around the canonize facade and its
  deterministic phase steps without naming any retired primitive.
- **Risk: silent contradiction with `skills/canonize/` body.** If the
  rewritten prose names a phase number or an artifact path that does
  not match `skills/canonize/SKILL.md`, the Orchestrator persona
  receives instructions that diverge from the actual skill. Signal:
  any phase-number or artifact-path string in the rewritten paragraphs
  that does not appear verbatim in `skills/canonize/SKILL.md`.
  Mitigation: cross-reference `skills/canonize/SKILL.md` while
  drafting the rewritten paragraphs.
