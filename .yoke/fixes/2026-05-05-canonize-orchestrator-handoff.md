# Fix-spec: Orchestrator → /yoke:canonize handoff is incoherent at v2.0.0

> Generated by `/yoke:fix` on 2026-05-05.
> Status: approved
> Approved by: iury.krieger@stone.com.br
> Approved at: 2026-05-05T19:01:06Z
> scope_caution:

## Introduction

At v2.0.0 the canonical-memory write path was reshaped into a
provider-agnostic facade: `/yoke:canonize` now resolves the active
provider from `.yoke/config.yaml` and dispatches to the provider's
pinned canonize verb. Per that reshape, `skills/canonize/SKILL.md:76`
hard-rejects any positional argument and aborts with
`wm: /yoke:canonize takes no arguments at v2.0.0`.

The Orchestrator's full-run termination handoff was not migrated in
the same change. `agents/orchestrator.md:74` and
`skills/implement/SKILL.md:488` both instruct the canonize-only
Orchestrator to invoke `/yoke:canonize` via the Skill tool **passing
the active task's `.yoke/<task-slug>/` directory path along with
`--from-orchestrator`**. Those two contracts are mutually exclusive:
the Orchestrator passes arguments that the canonize skill is
documented to reject.

Concrete consequence: every Phase 4 termination handoff that runs the
documented Orchestrator path aborts on entry to `/yoke:canonize` with
the v2.0.0 hard-rejection message, before the five-criterion cascade
or any provider dispatch can run. The automated canonize handoff is
unreachable until the contract is made coherent on both sides.

## What Broke

The canonize-invocation contract is defined inconsistently across
three repository surfaces:

- `agents/orchestrator.md:74` — instructs the canonize-only
  Orchestrator to "invoke `/yoke:canonize` via the Skill tool, passing
  the active task's `.yoke/<task-slug>/` directory path along with
  `--from-orchestrator`."
- `skills/implement/SKILL.md:488` — restates the same contract:
  "Orchestrator (in canonize mode) invokes `/yoke:canonize` via the
  Skill tool, passing the active task's `.yoke/<task-slug>/` path and
  `--from-orchestrator`."
- `skills/canonize/SKILL.md:76` — defines the v2.0.0 facade contract:
  "No arguments are accepted at v2.0.0. If `$ARGUMENTS` is non-empty,
  abort with: `wm: /yoke:canonize takes no arguments at v2.0.0`."

The first two surfaces describe one shape (positional path argument +
`--from-orchestrator` flag); the third surface describes the inverse
shape (zero arguments, hard-reject otherwise). There is no shared
authority for the canonize-invocation contract — each surface is
internally consistent but the union is incoherent.

## Reproduction / Trigger

Trigger: full-run termination handoff inside `/yoke:implement`. The
exact path:

1. Run `/yoke:implement` against any approved Acceptance Criteria
   document until every sprint converges (coordinator exit reason
   `merge-ready`).
2. The coordinator issues a single foreground Task call to
   `agents/orchestrator.md` with `mode=canonize`, per
   `skills/implement/SKILL.md:484-494` and `agents/orchestrator.md:64-78`.
3. The Orchestrator subagent follows its documented instructions and
   invokes `/yoke:canonize` via the Skill tool, passing the active
   task's `.yoke/<task-slug>/` path together with the
   `--from-orchestrator` flag.
4. `skills/canonize/SKILL.md:77-82` reads `$ARGUMENTS`, observes a
   non-empty value, and aborts with
   `wm: /yoke:canonize takes no arguments at v2.0.0`.
5. The Orchestrator subagent inherits the non-zero exit; the
   automated canonize handoff cannot proceed.

The trigger is event-driven (the `merge-ready` termination event) and
deterministic — any full-run that reaches Phase 4 termination via the
documented Orchestrator path reproduces the abort.

## Expected Behavior

The canonize-invocation contract is single-authored and consistent
across `skills/canonize/SKILL.md`, `agents/orchestrator.md`, and
`skills/implement/SKILL.md`. The Orchestrator's documented full-run
termination handoff completes against `/yoke:canonize` without
hitting the v2.0.0 hard-rejection guard, and the canonize skill
proceeds into Phase 1 (stage the active task's diff) under both the
documented Orchestrator path and a manual user invocation.

Anchors for the expected contract:

- `skills/canonize/SKILL.md:71-82` — the v2.0.0 facade-shape decision,
  ratified at v2.0.0 cutover (see canonical-memory entry
  `concepts/provider-agnostic-verbs-yokesearch-canonical-memory-yokecanonize`).
- `agents/orchestrator.md:60-78` — the canonize-only Orchestrator
  contract: the subagent must reach the canonize verb and dispatch the
  five-criterion cascade.
- `skills/implement/SKILL.md:480-500` — the coordinator's full-run
  termination handoff must succeed end-to-end on `merge-ready`.

The fix is to make the three surfaces describe the same contract;
which of the three options listed in the issue body is selected is a
Tech Spec decision (see Open Questions FR-anchor below).

## Observed Behavior

Following the documented Orchestrator path produces, deterministically,
the v2.0.0 hard-rejection diagnostic from `skills/canonize/SKILL.md`:

```text
wm: /yoke:canonize takes no arguments at v2.0.0
```

The canonize skill exits non-zero before sourcing
`lib/canonical-memory/resolve-provider.sh`, before staging the active
task's diff (Phase 1), and before any provider dispatch.
Consequently:

- No Phase 1 staging step (`git stash` of the active slug's archive
  files plus `runtime/`) executes.
- No five-criterion cascade runs against the staged diff.
- No Model C impact classification or PR-opening step is reached.
- The Orchestrator subagent returns the propagated non-zero exit to
  `/yoke:implement`, leaving the loop in a state where it has reached
  `merge-ready` but cannot complete the canonical-memory write
  handoff.

## Blast Radius

**One module — the canonize-invocation contract.** Three repository
surfaces describe one logical contract (the shape of a `/yoke:canonize`
invocation); the breakage is confined to that surface even though the
fix touches three files. No cross-service or cross-deploy effect.

The population affected is everyone running `/yoke:implement` through
to full-run termination — every successful sprint walk that reaches
`merge-ready` currently cannot complete the automated canonize step.
Manual `/yoke:canonize` invocations from a developer terminal are
unaffected (they already pass zero arguments and are honored by the
v2.0.0 hard-rejection guard's intended path).

## Root-Cause Hypothesis (optional)

The v2.0.0 facade extraction (`2026-04-30-pluggable-canonical-memory`)
reshaped `/yoke:canonize` to a zero-argument verb that resolves
context exclusively from the host project's working memory
(`.yoke/runtime/.current` for the active slug; `.yoke/config.yaml`
for the active provider). The migration of the v3.0.0 council cutover
(`2026-05-01-agent-council`) reshaped the Orchestrator into
canonize-only mode but inherited the v1.x handoff prose, which still
referenced the retired `--from-orchestrator` flag and the
directory-path argument. The two migrations did not converge on the
canonize-invocation contract, leaving the orchestrator and implement
prose stale relative to the v2.0.0 canonize-skill contract.

The smallest-scope alignment is **prose-only on the two stale
surfaces**: drop the directory-path argument and the retired flag
from `agents/orchestrator.md` and `skills/implement/SKILL.md`,
leaving the v2.0.0 zero-argument facade contract intact. The
canonize skill is the v2.0.0 contract authority; the two prose
surfaces converge to it.

## Functional Requirements

- **FR-1:** `agents/orchestrator.md` and `skills/implement/SKILL.md`
  document the **same** invocation shape for `/yoke:canonize` that
  `skills/canonize/SKILL.md` enforces at runtime. After the fix, the
  three surfaces agree byte-for-byte on whether `/yoke:canonize`
  accepts arguments, which arguments (if any), and how the
  Orchestrator passes context.

- **FR-2:** When the canonize-only Orchestrator (`agents/orchestrator.md`,
  `mode=canonize`) is spawned by `/yoke:implement` at full-run
  termination (coordinator exit reason `merge-ready`), invoking
  `/yoke:canonize` via the Skill tool per the **documented**
  contract MUST NOT trip the
  `wm: /yoke:canonize takes no arguments at v2.0.0` hard-rejection
  guard. The Orchestrator-driven canonize handoff completes the
  five-criterion cascade and reaches the active provider's pinned
  canonize verb without aborting on argument-shape grounds.

- **FR-3:** Manual `/yoke:canonize` invocations (a developer typing
  `/yoke:canonize` at the terminal with no arguments) continue to
  work end-to-end as documented at `skills/canonize/SKILL.md:71-82`.
  The fix does not regress the zero-argument manual path.

- **FR-4:** The active slug consumed by `/yoke:canonize` is read from
  `.yoke/runtime/.current` (the existing working-memory contract for
  the active task), regardless of whether the invocation comes from
  the Orchestrator or from a manual user. No alternate slug-resolution
  path is introduced.

- **FR-5:** The fix introduces **no** caller-identity discriminator.
  `/yoke:canonize` continues to honor its v2.0.0 zero-argument
  contract verbatim and remains caller-agnostic — the Orchestrator
  and a manual user invoke the verb identically (no positional
  argument, no opt-in flag, no environment variable). Any Model C
  routing decision the canonize skill makes (auto-apply lane for
  `low` impact vs notify-and-apply with veto window vs synchronous
  human ratification) is derived from the staged diff via the
  five-criterion cascade documented at
  `lib/canonical-memory/canonization-criteria.sh`, not from caller
  identity. As a corollary, **`skills/canonize/SKILL.md` is not
  modified by this fix** — the alignment is prose-only on the
  Orchestrator and implement surfaces.

- **FR-6:** Canonical memory carries one decision entry that records
  the chosen contract shape (which of the three options listed in
  the issue is selected, plus the rationale). The entry supersedes
  any earlier doctrine that referenced the retired
  `--from-orchestrator` flag (e.g. `concepts/yoke-pattern-model-c-governance`
  body sections that still cite the v1.x `/yoke:preserve --from-orchestrator`
  shape). Supersession is bidirectional.

- **FR-7:** A regression sensor exercises the end-to-end Orchestrator
  → `/yoke:canonize` path against a representative `merge-ready`
  fixture and asserts that the canonize skill does not abort with the
  v2.0.0 hard-rejection diagnostic
  (`wm: /yoke:canonize takes no arguments at v2.0.0`). The sensor MUST
  satisfy the per-sensor working-memory contract documented in
  `.yoke/sensors/` and enforced by `lib/sensors/ack-sensors.sh`:

    - **Location.** `.yoke/sensors/<sensor-id>.md`. The sensor file is
      project-level and durable, not a per-task artifact.
    - **Type.** `type: computational`. The regression check is a
      deterministic shell-based pass/fail, not an LLM judgment.
    - **Command field.** `command:` is required (mutually exclusive
      with `agent:`) and MUST hold a literal shell command that maps
      to a **valid** project entry point. "Valid" means: the command
      runs from the repository root with no manual setup beyond the
      conditions ack-sensors readiness checks already enforce, exits
      0 on the documented passing path, and exits non-zero on the
      regression path the issue describes (Orchestrator-driven
      `/yoke:canonize` invocation tripping the v2.0.0 hard-rejection
      guard).
    - **Body sections.** `## How to run`, `## Known issues`, and
      `## Frequent errors` are mandatory and non-empty per the
      template's lint-enforced schema; `## Calibration` is absent
      (computational sensors do not carry a calibration block).
    - **Cost channels.** `token_cost: 0` (computational baseline)
      and `time_cost: <seconds>` populated from observed runtime.

  Naming and exact `command:` payload are Tech Spec decisions; the
  binding constraint is the location + type + command-validity
  contract above.

## Non-Goals (Out of Scope)

- Reshaping the v2.0.0 facade contract beyond what FR-1 through FR-7
  require. Adding new positional arguments to `/yoke:canonize` for
  use cases other than the Orchestrator handoff is out of scope.
- Changing the Orchestrator's authority class (still canonize-only;
  still spawned exactly once per `/yoke:implement` run at termination).
- Changing the Model C governance contract (auto-apply / notify-and-apply
  / synchronous classification thresholds remain unchanged).
- Migrating manual `/yoke:preserve --from-orchestrator` call sites in
  pre-v2.0.0 documentation. The legacy `/yoke:preserve` skill is
  retired; references in canonical-memory entities older than v2.0.0
  are historical and out of scope here.
- Adding new provider-side dispatch arguments. Whatever the v2.0.0
  facade resolves to (e.g. `/bedrock:teach` for the bedrock provider)
  continues to receive whatever it receives today; this fix-spec
  does not change the provider-side contract.
- Changing the slug-resolution path. Active slug continues to be read
  from `.yoke/runtime/.current` per FR-4.

## Risks

- **Loss of caller-aware Model C routing** — Removing the
  `--from-orchestrator` discriminator means `/yoke:canonize` can no
  longer use caller identity to short-circuit a Model C lane (e.g.
  auto-apply for `low` impact). The five-criterion cascade in
  `lib/canonical-memory/canonization-criteria.sh` must remain the
  sole source of impact classification, and any historical doctrine
  that **routed** writes by caller (vs **classified** writes by
  diff content) must be either inert or migrated. Signal: a Phase 4
  termination handoff that previously took the auto-apply lane via
  caller-identity now requires a notify-and-apply window (or vice
  versa). Mitigation: the FR-6 doctrine entry MUST audit the existing
  Model C governance pattern entry in canonical memory and confirm
  that no behavioral path depended on the retired flag.

- **Contract drift recurrence** — A fix that updates the two prose
  surfaces (`agents/orchestrator.md`, `skills/implement/SKILL.md`)
  without anchoring the contract in canonical memory can drift again
  on the next migration. Signal: a future PR re-introduces a
  `--from-orchestrator` reference in either surface. Mitigation:
  FR-6's superseding doctrine entry plus FR-7's regression sensor.

- **Sensor-coverage false positive** — FR-7's regression sensor must
  exercise the actual canonize-invocation path the Orchestrator
  takes, not a mock that calls `/yoke:canonize` directly with an
  inert wrapper. Signal: the sensor passes locally but production
  `/yoke:implement` runs still abort. Mitigation: anchor the
  sensor's `command:` to a script that reproduces the documented
  Orchestrator handoff (or its closest deterministic shell
  equivalent), and verify the script reproduces the v2.0.0 abort
  diagnostic on the **un**fixed code before claiming the sensor is
  load-bearing — Tech Spec decision.

## Regression Surface (optional)

- `.yoke/sensors/` — currently lists ten sensors
  (`tests-smoke`, `tests-sensors`, `tests-canonical-memory`, `lint`,
  `run-project`, `tests-runtime`, `build`, `code-review`,
  `fetch-logs`, `llm-as-judge`); none of them targets the
  Orchestrator → `/yoke:canonize` handoff. FR-7 backfills this gap
  with a new `type: computational` sensor whose `command:` field
  resolves to a valid project entry point.
- `tests/smoke/` — the project's smoke-test surface is a likely
  home for the underlying script that the new sensor's `command:`
  invokes (e.g. `bash tests/smoke/<name>.test.sh`); the binding
  contract is FR-7's location + type + command-validity rules, not
  a specific subdirectory. Tech Spec selects the script's exact
  path.
- `lib/sensors/ack-sensors.sh` — the readiness mode that gates
  every invocation of `/yoke:implement`; the new sensor file MUST
  pass `ack-sensors --mode readiness` before Phase 4 can spawn the
  Orchestrator subagent.
- `agents/orchestrator.md` and `skills/implement/SKILL.md` are the
  prose surfaces that any future migration must keep in sync; the
  fix should leave them anchored to the same authoritative source
  as `skills/canonize/SKILL.md`.
- `concepts/yoke-pattern-model-c-governance` (canonical memory) —
  the legacy `/yoke:preserve --from-orchestrator` references in this
  entry should be superseded by the new doctrine entry per FR-6.
- `docs/migration-v1-to-v2.md` — the v2.0.0 migration runbook should
  call out the canonize-invocation contract change so future readers
  understand the shape evolution.
