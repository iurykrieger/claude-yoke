# Fix-spec: Reset `.cycle-counter` on sprint advance

> Generated by `/yoke:fix` on 2026-05-05.
> Status: approved
> Approved by: iurykrieger
> Approved at: 2026-05-05T18:35:51Z
> scope_caution:

## Introduction

The Phase-4 ralph-loop coordinator is documented to enforce a hard
upper bound of **≤ 8 cycles per sprint**. The bound is checked at
runtime by `hooks/check-hard-bounds.sh`, which reads the per-task
counter file at `wm_cycle_counter_path()` (i.e.
`.yoke/runtime/.cycle-counter`). The same hook is the only entry
point to Trigger 4 escalation (`lib/ralph-loop/escalate.sh --reason
hard-bound`); a stale counter therefore directly maps to a wrong
arbitration decision (premature pause or silent bypass).

`skills/implement/SKILL.md` documents three times — at lines 74, 193
and 425–428 — that on per-sprint convergence the coordinator advances
`current_sprint:` and **resets** `cycle_count:` to `0`. The same
contract is canonized in `concepts/yoke-pattern-sprint-runtime-bundle`
(per the `/yoke:search-canonical-memory` round): "Hard-bound
exhaustion fires Trigger 4 keyed on the active sprint." The reset
intent is therefore doctrine-level, not just SKILL.md prose.

There is no script that resets the actual `.yoke/runtime/.cycle-counter`
file when sprint advance happens. Only the frontmatter's
`cycle_count:` is touched by the (still implicit) sprint-advance
prose, while the file the hard-bound hook reads is incremented by
`hooks/post-iteration.sh` and never zeroed. Issue #14 captures the
related "dual source of truth" between `progress.md :: cycle_count`
and `.cycle-counter`; **this fix-spec is narrower** — it only
restores the sprint-advance reset on the file that the hard-bound
check actually consumes, leaving the dual-source consolidation to
issue #14.

## What Broke

- `hooks/check-hard-bounds.sh:93` reads
  `counter_file="$(wm_cycle_counter_path)"` (i.e.
  `.yoke/runtime/.cycle-counter`) and compares its integer contents
  against `cycles_max` from `.yoke/config.yaml` to decide Trigger 4.
- `hooks/post-iteration.sh` increments that same file every cycle.
- No code path ever writes `0` to `.cycle-counter` on sprint advance.
  `lib/ralph-loop/orchestrate.sh` exposes only an `active-sprint`
  reader; `lib/working-memory/scaffold-sprints.sh` initialises the
  per-task sprint files without touching the counter; `skills/implement/SKILL.md`'s
  step 9 sprint-advance bullets list the reset in prose without
  pointing at any helper.
- The contract being violated is documented twice and canonized once:
  - `skills/implement/SKILL.md:74` — "advances `current_sprint:` and
    resets `cycle_count:` to 0".
  - `skills/implement/SKILL.md:425–428` — "increment `current_sprint:`
    to the next zero-padded sprint id (with bounds), reset
    `cycle_count:` to 0".
  - `concepts/yoke-pattern-sprint-runtime-bundle` — sprint-advance
    resets `cycle_count:` to 0; hard-bound exhaustion fires Trigger 4
    keyed on the active sprint.

## Reproduction / Trigger

The breakage is event-driven; it surfaces deterministically at the
start of every sprint after the first.

1. Run `/yoke:implement` against any task whose
   `.yoke/sprints/` directory contains at least two sprint files
   (i.e. the chosen slug has `*-s01.md`, `*-s02.md`, …).
2. Let the council coordinator drive sprint 1 to convergence —
   `hooks/post-iteration.sh` will have incremented
   `.yoke/runtime/.cycle-counter` once per cycle, ending at any value
   in `[1, 8]`.
3. The coordinator's step-9 stop-check appends to
   `completed_sprints:`, advances `current_sprint:`, and (per prose)
   resets `cycle_count:` in `progress.md`.
4. The next iteration enters sprint 2 with `.cycle-counter` still at
   the value sprint 1 left behind.
5. `hooks/check-hard-bounds.sh` then reads that stale value as if it
   belonged to sprint 2.

The trigger is a single named event flow — sprint-advance — on a
single counter surface; no concurrency, load, or rare data shape is
required.

## Expected Behavior

When sprint advance happens, `.yoke/runtime/.cycle-counter` MUST
contain `0` before the first cycle of the new sprint runs, so that
`hooks/check-hard-bounds.sh` measures cycles **of the active
sprint**, not the cumulative count across sprints. The contract is
anchored to:

- `skills/implement/SKILL.md:74` and `:425–428` — the prose definition
  of sprint advance includes the reset.
- `hooks/check-hard-bounds.sh:93` — the only consumer reads
  `wm_cycle_counter_path()`; the documented bound therefore has to
  be enforced on that file.
- `concepts/yoke-pattern-sprint-runtime-bundle` (canonical memory) —
  doctrine pins the per-sprint bound semantics to a counter that
  resets at sprint boundaries.

## Observed Behavior

- After sprint 1 converges with N cycles consumed
  (`.cycle-counter` == `N`), sprint 2 starts with `.cycle-counter`
  still at `N`.
- For sprints whose first cycle would otherwise pass the hard-bound
  hook (i.e. `N < cycles_max`), `check-hard-bounds.sh` either:
  - Fires Trigger 4 prematurely once the cumulative
    cross-sprint count crosses `cycles_max` (false-positive
    arbitration pause), or
  - Silently lets the sprint run beyond its documented per-sprint
    bound when the sprint-2 reset semantic is assumed in
    `progress.md` frontmatter (false-negative — the user never sees
    the ≤ 8-cycles-per-sprint guarantee that doctrine and SKILL.md
    promised).
- Both branches violate the same contract; which one fires depends
  on sprint-1 cycle count.

## Blast Radius

**Cross-module within one service.** The breakage is contained
inside the Yoke plugin (a single deploy unit). The surfaces involved:

- `lib/working-memory/paths.sh` (path helper, the only sanctioned
  writer of working-memory files).
- The sprint-advance call site (today implicit in
  `skills/implement/SKILL.md` step 9; whichever helper materializes
  it must take ownership of the reset).
- `hooks/check-hard-bounds.sh` (consumer of the counter; behavior
  changes by virtue of getting correct input — no code change
  required).
- `lib/ralph-loop/status-snapshot.sh` (secondary reader of
  `.cycle-counter`; sees the same input as the hook).

The population affected is whoever runs `/yoke:implement` against a
task with more than one sprint — i.e. the canonical multi-sprint
case.

## Root-Cause Hypothesis (optional)

`hooks/post-iteration.sh` was added as the per-cycle counter
incrementor when `wm_cycle_counter_path()` was introduced; the
matching reset on the sprint-advance code path was never wired,
likely because step 9 of `skills/implement/SKILL.md` describes the
reset as a frontmatter operation (`cycle_count: 0` in
`progress.md`) without distinguishing the persisted counter file
from the frontmatter scalar. The two surfaces drifted because the
prose elided the file reset.

## Functional Requirements

- **FR-1:** A new working-memory helper, `wm_reset_cycle_counter`,
  MUST be added to `lib/working-memory/paths.sh`. Calling it MUST
  write the literal string `0` (no trailing newline policy beyond
  what existing helpers like `wm_set_active` follow) to
  `wm_cycle_counter_path()`. The helper MUST be idempotent: calling
  it when the file is absent creates it; calling it when the file
  already contains `0` leaves it at `0`.
- **FR-2:** The sprint-advance code path MUST invoke
  `wm_reset_cycle_counter` immediately after appending the just-
  converged sprint to `completed_sprints:` and before the next
  cycle of the outer walk starts. The exact call site is a
  Tech-Spec decision — candidates named in
  `skills/implement/SKILL.md:425–428` are
  `lib/ralph-loop/orchestrate.sh` and (less likely)
  `lib/working-memory/scaffold-sprints.sh`. The Tech Spec MUST
  pick exactly one and document why.
- **FR-3:** When `hooks/check-hard-bounds.sh` runs the first cycle
  of any sprint after the first, it MUST observe
  `.cycle-counter == 0` (i.e. its hard-bound comparison MUST be
  per-sprint, not cumulative across sprints). This is the
  observable downstream of FR-1 + FR-2 and is what the binding
  Acceptance Criteria document MUST anchor a behavioral acceptance
  criterion to.
- **FR-4:** The sprint-advance prose in `skills/implement/SKILL.md`
  MUST be updated to name the reset of `.yoke/runtime/.cycle-counter`
  alongside the existing reset of `cycle_count:` in `progress.md`,
  so the persisted-counter-file reset stops being elided. Lines
  74, 193 and 425–428 are the touch points.
- **FR-5:** A behavior test under `tests/smoke/` MUST be added (or
  an existing per-sprint-walk test extended) to assert the
  invariant: after a simulated sprint advance, `.cycle-counter`
  reads `0`. The test name MUST follow the behavior-named
  convention from `CLAUDE.md :: ## Testing` (e.g.
  `tests/smoke/cycle-counter-reset-on-sprint-advance.test.sh`)
  and use the documented internal watchdog
  (`sleep 600 && kill -TERM $$ &`) where it interacts with any
  hook subprocess.

## Non-Goals (Out of Scope)

- **NOT** consolidating `progress.md :: cycle_count` and
  `.yoke/runtime/.cycle-counter` into a single source of truth.
  That is the scope of issue #14 — explicitly out of this fix.
- **NOT** changing the value of `cycles_max` or the Trigger-4
  escalation contract.
- **NOT** rewriting `hooks/check-hard-bounds.sh` to read from
  `progress.md` frontmatter instead of `.cycle-counter`. The dual-
  source decision belongs to issue #14, not here.
- **NOT** introducing a generalized "wm reset everything in
  runtime on sprint advance" helper. The reset is scoped to the
  cycle counter file alone; other runtime artifacts
  (cycle slices under `cycles/`, snapshots under
  `snapshots/`) keep their existing lifecycle.
- **NOT** changing the per-cycle increment site
  (`hooks/post-iteration.sh`).
- **NOT** modifying any other task's archive files
  (other tasks' `prds/*.md`, `specs/*.md`,
  `acceptance-criteria/*.md`, etc.).

## Risks

- **Reset fired in the wrong place** — placing the reset before
  sprint advance has actually committed (i.e. before
  `completed_sprints:` is appended and `current_sprint:` is
  incremented) would zero the counter mid-sprint and let
  `check-hard-bounds.sh` accept additional cycles in the **current**
  sprint. Signal: the smoke test asserting `.cycle-counter == 0`
  passes, but the per-sprint cycle count exceeds 8 in a longer
  test. Mitigation: place the reset call immediately after the
  `completed_sprints:` append and the `current_sprint:` increment
  in the chosen helper.
- **Test sees stale counter from a previous run** — if the smoke
  test does not fully wipe `.yoke/runtime/` before exercising
  sprint advance, it can pass against a coincidentally-zero
  counter rather than against the helper's effect. Signal: the
  test passes when `wm_reset_cycle_counter` is intentionally
  removed (i.e. it's not measuring the contract). Mitigation: the
  test seeds a non-zero `.cycle-counter` value before the
  sprint-advance call, then asserts post-advance value `== 0`.
- **Documentation drift after merge** — leaving
  `skills/implement/SKILL.md` lines 74/193/425 unchanged would
  reintroduce the elision the moment a future contributor reads
  the prose to bootstrap a related change. Signal: a second
  occurrence of the same bug shape arises from a nearby refactor.
  Mitigation: FR-4 is binding, not optional.
- **Hook ordering regression** — if `hooks/post-iteration.sh`
  ever runs before the sprint-advance reset on the boundary cycle,
  the reset would zero out a value that the hook had just
  incremented. Signal: counter momentarily reads `0` mid-sprint.
  Mitigation: place the reset only on the convergence branch of
  step 9 (where the counter is no longer needed for the just-
  completed sprint), not on every iteration of the inner loop.

## Regression Surface (optional)

- `hooks/check-hard-bounds.sh:93` — must keep reading
  `wm_cycle_counter_path()` and tripping at `cycles_max`. Any
  observable change in its trigger behaviour for the **first**
  sprint of a run is a regression.
- `lib/ralph-loop/status-snapshot.sh:75` — secondary reader of
  `.cycle-counter`; its rendered status must keep showing the
  current sprint's cycle count, not a cumulative one.
- Existing smoke tests under `tests/smoke/`, in particular any
  ralph-loop sprint-walk test, MUST keep passing. The new test
  in FR-5 is the targeted backfill.
- `wm_wipe_runtime` (called by Phase-1 skills like `/yoke:fix`,
  `/yoke:discover`) — must continue to clear `.cycle-counter`
  along with the rest of `.yoke/runtime/`; the new
  `wm_reset_cycle_counter` is a distinct call site, not a
  replacement.
