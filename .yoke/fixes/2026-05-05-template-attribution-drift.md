## Introduction

Both `templates/task.md` and `templates/sprint.md` carry attribution
metadata that has been false since the Phase-2.5 cutover landed (commit
`358dea2`, "feat(generate-sprints): split Phase 2.5 sprint synthesis
from tech-spec"). The two templates' opening blockquote (and, in the
sprint template, the closing trailer) declare:

> Generated by `/yoke:tech-spec` (stage 3) from `.yoke/specs/<slug>.md`.
> Status flips to `approved` when Trigger 2 approves the parent spec.

Two facts make that statement wrong today:

1. `/yoke:tech-spec` no longer has a stage 3. `skills/tech-spec/SKILL.md`
   line 14 states explicitly: "Phase 2 NEVER writes any sprint file and
   NEVER \[writes a task file\]". The single Phase-2.5 producer of sprint
   runtime bundles is `/yoke:generate-sprints`
   (`skills/generate-sprints/SKILL.md`).
2. The human gate that flips a sprint file's status from `draft` to
   `approved` is **Trigger 2.5** (the sprint plan ratification rendered
   by `/yoke:generate-sprints`), not Trigger 2 (the Tech Spec
   ratification rendered by `/yoke:tech-spec`).
   `skills/generate-sprints/SKILL.md` line 13: "the shared approval menu
   (`templates/approval-menu.md`) — Trigger 2.5 — and on `approve` /
   `approve_and_continue` flips every produced sprint file's frontmatter
   `status: draft` → `status: approved` atomically."

The contract under violation is **template-metadata fidelity**: a
template's opening blockquote names the skill that generates instances
of the template and the trigger that ratifies them. When a reader
(Tech Spec author, implementation agent, junior developer) opens a
template to learn the lifecycle of the artifact, the template's
self-description must match the actual lifecycle in the codebase. The
two templates today instruct the reader to look in the wrong place
twice: wrong skill, wrong trigger.

A separate but adjacent fact: `templates/task.md` is **unreferenced by
product code**. A repository-wide search (`grep -rn 'templates/task.md'`)
returns hits only inside historical Acceptance Contracts under
`.yoke/acceptance-contracts/` (frozen artifacts that document a past
sprint's deliverables) and never inside `skills/`, `lib/`, `hooks/`,
`agents/`, `tests/`, `docs/`, `CLAUDE.md`, or `README.md`. Sprint files
aggregate tasks inline as `### Task <ID>` subsections per
`templates/sprint.md`'s "Tasks" section; the standalone `task.md`
template is dead code. The remediation declared by this fix-spec is
**deletion** (FR-4) — guarded by an extended pre-deletion search that
covers non-product directories (`.github/`, `.claude-plugin/`, plugin
metadata) before the file is removed.

To prevent the same drift from re-appearing after the next producer
rename, this fix-spec also declares a new template-metadata-fidelity
sensor (FR-7) that pins the producer / trigger lines of every
template whose lifecycle is governed by a producer skill. The sensor
fails when a template's opening blockquote or closing trailer cites a
producer skill or human trigger that does not match the actual
producer / trigger in `skills/<producer>/SKILL.md`.

## What Broke

Two product files in `templates/` carry false attribution metadata:

- **`templates/sprint.md`** — opening blockquote (lines 14–16) and
  closing trailer (lines 116–117) name `/yoke:tech-spec` (stage 3) as
  the producer and Trigger 2 as the ratifying human gate. Both are
  wrong post-cutover. The mid-file legacy-flow carve-out at lines 89–90
  (the `(Realizes: US-<NNN>)` US-trace clause's exception for
  pre-cutover legacy sprint files) cites `/yoke:tech-spec` stage 3
  intentionally as a historical statement and is **not** in scope for
  this fix.
- **`templates/task.md`** — opening blockquote (lines 13–15) and the
  per-paragraph aside at lines 23–24 name `/yoke:tech-spec` (stage 3)
  as the producer and Trigger 2 as the ratifying human gate. Same
  attribution drift. Additionally, the file as a whole has zero
  product-code references; it is consumed only by historical
  Acceptance Contracts.

The contract violated is template-metadata fidelity:

- Real producer of sprint runtime bundles: `/yoke:generate-sprints`
  (`skills/generate-sprints/SKILL.md`).
- Real human gate: **Trigger 2.5** (the sprint plan ratification), not
  Trigger 2 (the Tech Spec ratification).
- `/yoke:tech-spec` does not author sprint files at all
  (`skills/tech-spec/SKILL.md:14`).

## Root-Cause Hypothesis

Sprint synthesis was extracted out of `/yoke:tech-spec` (stage 3) into
the standalone `/yoke:generate-sprints` skill in commit `358dea2`
(merged via PR #43, "feat(generate-sprints): split Phase 2.5 sprint
synthesis from tech-spec"). The cutover updated:

- `skills/tech-spec/SKILL.md` — added the explicit "Phase 2 NEVER
  writes any sprint file" sentence.
- `skills/generate-sprints/SKILL.md` — bodied as the new single
  producer.
- The Trigger registry — added Trigger 2.5 as the sprint plan
  ratification.

But the cutover did not propagate to the **template attribution
metadata** in `templates/sprint.md` and `templates/task.md`. The
templates predate the cutover; the opening blockquotes were authored
when `/yoke:tech-spec` stage 3 was still the producer and Trigger 2
was the only relevant gate. The cutover commit modified neither file.

The dead-file status of `templates/task.md` is a separate, longer-
running drift: tasks are aggregated inline inside sprint files (see
`templates/sprint.md` "Tasks" section starting line 48) rather than
materialized as standalone files; the standalone `task.md` template
was never wired into the post-cutover producer.

## Functional Requirements

- **FR-1:** `templates/sprint.md` opening blockquote (currently lines
  14–16) MUST cite `/yoke:generate-sprints` (Phase 2.5) as the
  producer and Trigger 2.5 as the ratifying human gate. The wording
  MUST make explicit that the status flip happens on Trigger 2.5
  approval (the sprint plan ratification), not on Trigger 2 (the Tech
  Spec ratification).
- **FR-2:** `templates/sprint.md` closing trailer (currently lines
  116–117) MUST carry the same updated attribution as FR-1. The
  trailer is a duplicate of the opening blockquote and the two MUST
  stay textually consistent.
- **FR-3:** `templates/sprint.md` legacy-flow carve-out at lines
  89–90 (the US-trace clause's exception for pre-cutover sprint files
  generated by `/yoke:tech-spec` stage 3) MUST be preserved verbatim
  unless and until the historical statement is no longer load-bearing.
  The carve-out is a historical statement, not a current-attribution
  claim, and is out of scope for this fix.
- **FR-4:** `templates/task.md` MUST be deleted from the repository.
  The file has zero product-code references (only historical
  Acceptance Contracts under `.yoke/acceptance-contracts/` cite it,
  and frozen historical artifacts are out of scope). Tasks are
  aggregated inline inside sprint files per `templates/sprint.md`'s
  `## Tasks` section, so the standalone task template is dead code.
  Pre-deletion verification is required (Risk: hidden non-product
  reference) — the Tech Spec MUST extend the search beyond
  `skills/`, `lib/`, `hooks/`, `agents/`, `tests/`, `docs/`,
  `CLAUDE.md`, and `README.md` to cover `.github/`, `.claude-plugin/`,
  plugin metadata, and any other non-historical surface, and confirm
  zero non-historical references before the deletion lands.
- **FR-5:** A repository-wide search after the fix (`grep -rn '/yoke:tech-spec.*stage 3' templates/`) MUST return zero matches in
  `templates/sprint.md`'s opening blockquote and closing trailer (the
  legacy-flow carve-out remains by FR-3). The path
  `templates/task.md` MUST not exist post-fix (per FR-4), so any grep
  scoped to it returns zero by absence.
- **FR-6:** A repository-wide search after the fix (`grep -rn 'Trigger 2 approves' templates/`) MUST return zero matches in any
  template's attribution metadata. The phrase appears today only in
  the false-attribution blockquotes / trailer; no legitimate use
  remains.
- **FR-7:** A new template-metadata-fidelity sensor MUST be added that
  pins the producer / trigger lines of every template under
  `templates/` whose lifecycle is governed by a producer skill. The
  sensor MUST fail when any template's opening blockquote or closing
  trailer cites a producer skill or human trigger that does not match
  the actual producer / trigger in `skills/<producer>/SKILL.md`. The
  sensor lives at `lib/sensors/<id>.sh` and is exercised by
  `tests/sensors/<id>.test.sh`. The sensor's exact id, scope (sprint
  template only vs all templates), and validation logic (regex pin
  vs producer-skill cross-reference) are Tech Spec design calls.
- **FR-8:** No skill file, lib helper (other than the new sensor),
  hook, agent, or test (other than the new sensor's self-test) is
  modified by this fix. The change set is bounded to
  `templates/sprint.md` (edited), `templates/task.md` (deleted), the
  new sensor at `lib/sensors/<id>.sh`, and the new self-test at
  `tests/sensors/<id>.test.sh`.

## Non-Goals (Out of Scope)

- Changing the lifecycle of sprint files or the trigger semantics —
  the fix updates documentation metadata, not behaviour.
- Touching `templates/spec.md`, `templates/prd.md`, or any other
  template — the violation is scoped to the two templates named in
  the issue.
- Editing the legacy-flow carve-out at `templates/sprint.md` lines
  89–90 (a historical statement, intentionally retained).
- Modifying historical Acceptance Contracts under
  `.yoke/acceptance-contracts/` that reference `templates/task.md`.
  Historical artifacts are frozen.
- Changing `skills/tech-spec/SKILL.md` or `skills/generate-sprints/SKILL.md` — they are already correct; the templates are out
  of date with them.
- Adding sensors beyond the single template-metadata-fidelity sensor
  declared by FR-7 (e.g. a generalised "any template's frontmatter
  shape" sensor, a producer-skill round-trip sensor). FR-7 mandates
  one targeted sensor; broader template hygiene tooling is a future
  concern.
- Implementing the deletion mechanically without the FR-4
  pre-deletion search. The deletion MUST be guarded by the broader
  search; uncovering an unexpected non-historical reference flips
  FR-4 from option (a) deletion back to attribution correction and
  surfaces the find as a new finding for the Tech Spec.

## Risks

- **Carve-out erasure.** A naive global rewrite of
  `/yoke:tech-spec.*stage 3` → `/yoke:generate-sprints` in
  `templates/sprint.md` would also rewrite the legacy-flow carve-out
  at lines 89–90 and erase its historical meaning. **Signal:** the
  AC-002-4 sensor in `.yoke/acceptance-criteria/2026-05-03-generate-sprints-skill.md`
  (`grep -c 'legacy-flow' templates/sprint.md` ≥ 1) drops to 0.
  **Mitigation:** target only the opening blockquote (lines 14–16)
  and closing trailer (lines 116–117) — not the carve-out paragraph.
- **Hidden task.md reference.** A consumer outside `skills/`, `lib/`,
  `hooks/`, `agents/`, `tests/`, `docs/`, `CLAUDE.md`, and `README.md`
  may still refer to `templates/task.md`; FR-4 deletion is the
  declared remediation, so any missed reference becomes a
  post-deletion break. **Signal:** any post-deletion test or skill
  execution that fails with "no such file templates/task.md".
  **Mitigation:** the FR-4 pre-deletion search is mandatory and
  must extend beyond product directories (`.github/`,
  `.claude-plugin/`, hook configurations, plugin metadata, any
  GitHub workflow). If the search uncovers a non-historical
  reference, FR-4 flips from option (a) deletion back to attribution
  correction and the find surfaces as a new finding for the Tech
  Spec.
- **Sensor over-fit / under-fit.** FR-7's new template-metadata-
  fidelity sensor could false-positive on templates whose lifecycle
  is intentionally producer-less (e.g., `templates/approval-menu.md`
  is a shared rendering surface, not a producer-owned artifact), or
  false-negative if the regex is too narrow to catch the next
  rename. **Signal:** a future producer rename lands without the
  sensor catching the template drift, OR the sensor blocks a
  legitimate template edit. **Mitigation:** the sensor's exact
  scope (which templates it covers) and validation logic (regex
  pin vs producer-skill cross-reference) are Tech Spec design
  calls; the design must enumerate which templates are
  producer-owned and explicitly carve out the rest.
- **Template-shape sensors.** Tests
  `tests/smoke/scaffold-sprints-callable-from-phase-3.test.sh` and
  `tests/acceptance/2026-05-03-generate-sprints-skill/sprint-template-documents-realizes-clause.test.sh`
  assert the 5 H2 sections, the `(Realizes:)` clause count, and the
  legacy-flow carve-out count in `templates/sprint.md`. **Signal:** any
  of these tests fails. **Mitigation:** the fix touches only the
  opening blockquote and the closing trailer — H2 section count
  (currently 5: `## Sprint objective`, `## Sprint DoD`, `## Tasks`,
  `## Functional acceptance criteria`, `## Sensors`) does not change;
  `(Realizes:)` and `legacy-flow` substrings stay untouched.
- **CLAUDE.md migration history.** `CLAUDE.md` documents the v3.0.0
  council cutover and the v4.0.0 acceptance-criteria cutover but
  predates the Phase-2.5 split. **Signal:** none — `CLAUDE.md` does
  not reference `templates/task.md` or `templates/sprint.md` directly,
  so the templates' attribution drift is not echoed there.
  **Mitigation:** confirmed by `grep -rn 'templates/task.md' CLAUDE.md`
  returning zero matches.
