## Context and Scope

This spec materializes the fix-spec FR set into a concrete change
inside the Yoke plugin's working-memory tier. Two surfaces are
involved: `lib/working-memory/paths.sh` (the only sanctioned writer
of files under `.yoke/`) and `skills/implement/SKILL.md` (the
authoritative prose for the council coordinator's sprint-advance
sequence). A third surface is touched read-only:
`hooks/check-hard-bounds.sh:93`, the consumer that decides Trigger 4
based on `.yoke/runtime/.cycle-counter`. No other module changes.

**In scope:** add a deterministic, idempotent
`wm_reset_cycle_counter` helper next to the existing
`wm_cycle_counter_path` in `lib/working-memory/paths.sh`; document
its invocation in the sprint-advance bullets of
`skills/implement/SKILL.md` (lines 74, 193, 425–428) so the council
coordinator's prose contract names the deterministic primitive
instead of leaving the `.cycle-counter` reset implicit; add one
behavior smoke test under `tests/smoke/` named for the contract.

**Out of scope:** consolidating
`progress.md :: cycle_count` and `.yoke/runtime/.cycle-counter` into
a single source of truth (issue #14); rewriting the hard-bound
consumer to read frontmatter; introducing a multi-step
`wm_advance_sprint` helper that bundles the full sprint-advance
sequence; modifying `hooks/post-iteration.sh` or any other task's
archive files.

## Goals and Non-Goals

**Goals**

- After sprint advance, `.yoke/runtime/.cycle-counter` reads exactly
  the byte `0` before the first cycle of the new sprint runs.
- The new helper is idempotent: calling it on a missing file creates
  it; calling it on a file already at `0` leaves it at `0`; calling
  it on a file at any other integer overwrites it with `0`.
- The behavior smoke test is fast: it completes in ≤ 10s wall-clock.
- The change introduces no regression in the first sprint of any
  multi-sprint task (zero observable behavior change for
  `current_sprint == 01`).
- The fix-spec's five FRs are each lifted into exactly one
  Technical Use Case subsection below — no silent drops, no ad-hoc
  reframings.

**Non-Goals**

- NOT consolidating the two cycle-count surfaces (issue #14).
- NOT changing the value of `cycles_max` or the Trigger-4 escalation
  contract.
- NOT introducing a multi-step `wm_advance_sprint` helper that
  bundles `completed_sprints` append + `current_sprint` increment +
  `wm_reset_cycle_counter` + `contracts.md` append. That refactor
  belongs to a follow-up scoped explicitly against issue #14.
- NOT modifying `hooks/check-hard-bounds.sh` or
  `lib/ralph-loop/status-snapshot.sh` (both stay read-only consumers
  of `wm_cycle_counter_path()`).
- NOT modifying `hooks/post-iteration.sh` (per-cycle increment site
  is correct and stays put).
- NOT touching any other task's archive files.

## Architecture

**Pattern: deterministic working-memory primitive within the
existing path-helper convention.** The architecture inherits from
two canonical patterns:

- `concepts/yoke-pattern-memory-model` — working memory is per-task
  ephemeral; only the path helper (`lib/working-memory/paths.sh`)
  writes to `.yoke/`.
- `concepts/yoke-pattern-plugin-structure` — `lib/working-memory/`
  is the canonical home for working-memory primitives; the file
  `paths.sh` is the canonical home for `wm_*` functions.

The chosen architecture adds exactly one bash function
(`wm_reset_cycle_counter`) inside `paths.sh`'s existing
`# --- runtime paths ---` region, immediately below
`wm_cycle_counter_path`. The function:

1. Resolves the target via `wm_cycle_counter_path()` (already exists
   at line 407).
2. Ensures the parent directory exists (`mkdir -p
   "$(dirname "$target")"`) — necessary because Phase-1 skills
   (`/yoke:fix`, `/yoke:discover`) call `wm_wipe_runtime` which
   deletes the entire runtime directory.
3. Writes the literal string `0` to the target with `printf '0' >
   "$target"` — no trailing newline, matching the existing
   `wm_set_active` convention (line 96–117).
4. Returns 0 on success; surfaces `wm:`-prefixed stderr on
   filesystem error.

**Invariants the architecture guarantees:**

- After a successful call, `cat .yoke/runtime/.cycle-counter` prints
  exactly `0` (no newline, no spaces).
- The function is idempotent — repeated calls leave the file at
  `0`.
- The function does not interact with `progress.md` frontmatter —
  that surface is the council coordinator's responsibility (issue
  #14 territory).

**Failure modes the architecture explicitly does NOT handle:**

- Concurrent writes by two coordinator instances on the same
  worktree. Out of scope: there is exactly one coordinator per
  `/yoke:implement` run.
- Filesystem ENOSPC. The helper surfaces `printf`'s stderr and
  exits non-zero; the caller (the coordinator) decides recovery.
- Cross-task drift. `wm_wipe_runtime` (called at every Phase-1
  skill start) flushes the file along with the rest of `runtime/`;
  the helper does not need to reason about cross-task state.

## APIs and Data Model

The change introduces one new bash function and modifies one
existing markdown file's prose. No JSON / YAML / network schemas
change.

- **Contract: `wm_reset_cycle_counter` (new bash function in
  `lib/working-memory/paths.sh`).**
  Signature: `wm_reset_cycle_counter()`. Inputs: none (target
  resolves through `wm_cycle_counter_path()`). Outputs: writes the
  byte `0` to `wm_cycle_counter_path()`; exit 0 on success;
  surfaces `wm:`-prefixed stderr on filesystem error and exits
  non-zero. Idempotency: required and tested. The function MUST
  NOT trigger any subshell side effect beyond the file write
  (no logging to `progress.md`, no canonical-memory call).

- **Contract: `skills/implement/SKILL.md` step-9 prose.** Lines
  74, 193 and 425–428 are the touch points. The amended prose
  names `wm_reset_cycle_counter` alongside the existing
  `cycle_count: 0` frontmatter reset, so a coding agent reading
  the prose discovers the deterministic primitive without having
  to reverse-engineer it. The amendment is plain markdown text;
  no schema changes.

- **Contract: `tests/smoke/cycle-counter-reset-on-sprint-advance.test.sh`
  (new).** Exercises three cases: (a) helper called when file is
  absent → file exists with content `0`; (b) helper called when
  file contains `7` → file contains `0`; (c) helper called twice
  → file still contains `0`. Each case uses a temporary
  `WM_RUNTIME_DIR` override (export the env var) so the test does
  not pollute the worktree's actual `.yoke/runtime/`.

## Non-Functional Requirements

- **Latency:** the helper completes in < 50ms on the hot path
  (single file write + `mkdir -p`).
- **Throughput:** the helper sustains ≥ 100 qps under the smoke
  test's tight loop (idempotency case calls it twice in succession
  — the test budget assumes ≥ 100 qps so contention is impossible).
- **Disk footprint:** ≤ 1 MB total under
  `.yoke/runtime/.cycle-counter` — the file carries exactly one byte
  (`0`); the rest is filesystem overhead per the worktree
  filesystem (well below 1 MB on every supported FS).
- **Test runtime:** ≤ 10s wall-clock for the new smoke test (the
  internal watchdog at `600s` is the safety bound, not the target).
- **Backward compatibility:** 0% regression in `current_sprint == 01`
  paths — by construction, `wm_reset_cycle_counter` is only called
  on sprint advance (`current_sprint > 01`).

## Alternatives Considered

### Alt: read `cycle_count:` from `progress.md` frontmatter inside `hooks/check-hard-bounds.sh`

**Trade-off vs. chosen:** removes the dual source of truth between
`progress.md :: cycle_count` and `.yoke/runtime/.cycle-counter`,
collapsing the two surfaces into a single read mediated by
`progress.md` frontmatter.
**Reason for rejection:** the dual-source consolidation is the
explicit scope of issue #14, called out in this fix-spec's "Related"
line and in its `## Non-Goals`. Doing the consolidation here would
break the narrowness contract (component breadth + surface
containment proxies would soft-fail in retrospect) and conflate two
fix shapes in one PR.
**Source:** `concepts/yoke-pattern-memory-model`

### Alt: introduce a single `wm_advance_sprint` helper bundling the full sprint-advance sequence

**Trade-off vs. chosen:** the coordinator's sprint-advance prose
collapses into a single deterministic call, eliminating the chance
that any future contributor forgets one of the four side effects
(append `completed_sprints`, increment `current_sprint`, reset
`cycle_count:` in frontmatter, reset `.cycle-counter` file, append
sprint-scoped contract section).
**Reason for rejection:** the bundled helper would also have to
write `progress.md` frontmatter, which today is the council
coordinator's responsibility (council personas and the coordinator
share `progress.md` as joint working memory). Wrapping that write
inside a path helper changes the writer convention and risks
silent races with the coordinator's own Edit calls. The narrower
fix is a single-purpose deterministic primitive (`wm_reset_cycle_counter`)
plus a prose update that names it. A bundled `wm_advance_sprint`
remains a viable follow-up under issue #14.
**Source:** internal experience

### Alt: zero `.cycle-counter` from inside `hooks/post-iteration.sh` when it detects a sprint boundary

**Trade-off vs. chosen:** keeps the reset close to the
per-cycle increment, in the same hook, so a future contributor sees
both writes in one file.
**Reason for rejection:** `hooks/post-iteration.sh` runs at every
cycle and would need to re-read `progress.md` frontmatter to detect
the boundary. That introduces a cross-surface read in a hook whose
current contract is "increment + snapshot, no decisions". The
sprint-advance decision lives in the coordinator's step 9
(per-sprint convergence) — that is the correct call site. Putting
the reset in the hook would also make the smoke test harder
(the test would have to fake a sprint boundary in `progress.md`).
**Source:** `concepts/yoke-pattern-sprint-runtime-bundle`

## Trade-offs

- **Two writers for one logical counter remain.** The chosen approach
  intentionally leaves the dual-source-of-truth situation
  (`progress.md :: cycle_count` and `.yoke/runtime/.cycle-counter`)
  in place. Issue #14 carries the responsibility for the
  consolidation; this fix only restores the contract that doctrine
  already promises.
- **Prose-driven coordination remains the contract.** The council
  coordinator (LLM) is responsible for invoking
  `wm_reset_cycle_counter` based on `skills/implement/SKILL.md`'s
  amended prose. A determined contributor could still skip the
  call by editing the prose without editing the helper. The
  smoke test in FR-5 catches the absence of the helper itself, not
  the absence of the call — the second guarantee belongs to
  end-to-end ralph-loop coverage (already exists at
  `tests/smoke/ralph-loop-sprint-walk.test.sh`).
- **No per-cycle visibility of the reset.** The reset is invisible to
  any consumer that only inspects `progress.md` frontmatter — the
  fix targets the file-side surface, not the frontmatter-side.

## Cross-cutting Concerns

- **Observability:** the helper does not log to `progress.md` (per
  `concepts/yoke-pattern-memory-model` rule "reads are not loggable
  working-memory events"; the same applies to deterministic helper
  writes — `progress.md` events are coordinator decisions, not
  primitive side effects).
- **Security:** no secret handling, no auth boundary, no network
  call. The threat model is bounded to local filesystem state of
  the host project repo.
- **Error handling:** filesystem errors surface as `wm:`-prefixed
  stderr and a non-zero exit; the caller decides recovery
  (typically: surface to the user and abort the run).
- **i18n / a11y:** n/a — internal tooling.

## Technical Use Cases

### FR-1 — Add `wm_reset_cycle_counter` helper

**Components involved:** `lib/working-memory/paths.sh` (insertion
point: immediately below `wm_cycle_counter_path` at line 407, inside
the existing `# --- runtime paths ---` region).
**Contracts used:** `wm_cycle_counter_path()` (existing); standard
shell builtins (`printf`, `mkdir -p`, `dirname`).
**NFRs applied:** Latency, Throughput, Disk footprint.
**Edge cases:** target file absent → `mkdir -p` then create the file
with content `0`; target file present with content `0` → leave it at
`0` (idempotent overwrite); target file present with any other
integer (e.g. `7`) → overwrite with `0`; parent directory absent
(post-`wm_wipe_runtime` state) → `mkdir -p` recreates it then writes
the file; filesystem ENOSPC or EROFS → surface `wm:`-prefixed
stderr and exit non-zero.

### FR-2 — Sprint-advance call site invokes the helper

**Components involved:** `skills/implement/SKILL.md` (the council
coordinator's prose contract; the LLM is the runtime invoker, not a
shell helper).
**Contracts used:** `wm_reset_cycle_counter` (FR-1 contract); the
existing step-9 prose for sprint advance.
**NFRs applied:** Backward compatibility (0% regression on first
sprint).
**Edge cases:** the helper must be invoked **after** `current_sprint:`
has been incremented and `completed_sprints:` appended in
`progress.md` (so the inner `cycle_count < 8` loop on the next
iteration reads the post-reset value); calling it before the
frontmatter writes would zero out the counter mid-sprint and let
`check-hard-bounds.sh` accept additional cycles in the
just-completed sprint (this is the dominant risk in the fix-spec's
risk register).

### FR-3 — First cycle of any new sprint observes `.cycle-counter == 0`

**Components involved:** `hooks/check-hard-bounds.sh` (read-only
consumer; line 93 already reads `wm_cycle_counter_path()`).
**Contracts used:** the integer comparison against `cycles_max`
(consumer behavior unchanged); the helper's post-condition (file
contains exactly `0`).
**NFRs applied:** Backward compatibility.
**Edge cases:** for tasks with exactly one sprint, the helper is
never called and the consumer sees the same behavior as today (no
regression); for tasks where the sprint-advance bullets execute the
helper but the next iteration of the outer loop is interrupted
(crash, signal), the file remains at `0` — a subsequent resumption
sees the post-reset state, which is the correct semantics for the
incoming sprint.

### FR-4 — Update `skills/implement/SKILL.md` prose

**Components involved:** `skills/implement/SKILL.md` (lines 74,
193, 425–428).
**Contracts used:** the markdown structure of the file; no schema
contract changes.
**NFRs applied:** none directly (prose change).
**Edge cases:** the amendment must use the helper name verbatim
(`wm_reset_cycle_counter`) so a future grep for the helper's call
sites picks the SKILL.md prose up; the amendment must not
introduce a `## Sprints` section or any `### Task` anchor (those
are Phase-3 / Phase-2.5 concerns, not Phase-2 prose touch points
inside SKILL.md).

### FR-5 — Add behavior smoke test

**Components involved:** new file
`tests/smoke/cycle-counter-reset-on-sprint-advance.test.sh`; the
existing smoke-test harness it inherits from.
**Contracts used:** `wm_reset_cycle_counter` (FR-1);
`wm_cycle_counter_path` (existing); the documented internal
watchdog convention from `CLAUDE.md :: ## Testing`.
**NFRs applied:** Test runtime (≤ 10s wall-clock).
**Edge cases:** the test must export an isolated `WM_RUNTIME_DIR`
(temporary directory) so it does not pollute the actual
`.yoke/runtime/` of the worktree it runs in; the test must seed a
non-zero counter value (e.g. `printf '7' > "$tmp/.cycle-counter"`)
before invoking the helper, then assert post-helper value is
exactly `0` — without the seed, the test could pass against a
coincidentally-zero counter (the dominant test-design risk in
the fix-spec); the watchdog is required because the test reads
no subprocesses, but the harness convention in `CLAUDE.md`
applies uniformly.
