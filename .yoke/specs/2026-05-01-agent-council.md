## Overall objective

Replace Yoke's v2.x binary Generator/Validator/Orchestrator runtime
with a 3-persona council (Sr Eng, Sr QA, Sr Staff) governed by an
explicit synchronous protocol. Each cycle: Phase A (parallel persona
execution, gated by a deterministic file-marker barrier), Phase B
(council ponderation across capped réplica rounds with quiescence +
LLM contradiction detection), and Phase C (next-cycle entry on
consensus, or Trigger 4 escalation on unresolved divergence). The
runtime ships pluggable persona definitions in Claude Code's agent
format (extended with Yoke-specific frontmatter keys), per-persona
slice files merged at council open, a Trigger 4 generalized to N=3,
and Sr Staff's `/review` integration. v3.0 is a breaking change at
the Phase 4 boundary; no backward-compat runbook is required.

Sr QA objective: prove the code wrong, writes acceptance-contract-

invokes the configured review-skill (default `/review`) and consults
canonical memory for sustainability and pattern alignment.
End-of-sprint state: a council cycle on a real Yoke task surfaces at
least one finding from each persona's distinct lens, demonstrably
unreproducible by the v2.x runtime alone.

**Tasks:** see `.yoke/sprints/2026-05-01-agent-council-s03.md` `## Tasks` section.

## Contracts and interfaces

### Persona spec frontmatter
**Description.** Claude Code agent format (`name`, `description`,
`tools`, optional `model`) extended with three Yoke-specific keys.
Claude Code's loader ignores unknown keys, so the file serves both
loaders without forking.

**Schema (YAML frontmatter, all keys required unless noted):**

- `name` — persona id (one of `sr-eng`, `sr-qa`, `sr-staff` for
  Yoke-shipped defaults; arbitrary kebab-case for host overrides).
- `description` — Claude Code agent description string.
- `tools` — comma-separated Claude Code tool list available to the
  persona (e.g. `Read, Write, Edit, Grep, Glob, Bash, Skill`).
- `model` — optional model id (resolves through
  `lib/runtime/agent-config.sh::yoke_resolve_model`); falls back to
  `.yoke/config.yaml :: overrides.runtime.models.default` when
  absent.
- `objective` — Yoke. Single sentence stating the persona's success
  criterion. Used by the runtime to compose the persona's prompt
  prefix.
- `sensor-toolkit` — Yoke. List of sensor IDs the persona is allowed
  to invoke (referenced against `.yoke/sensors/`). Empty list means
  "no sensors"; missing key is invalid (validated at startup).
- `review-skill` — Yoke. Optional. Slash-command identifier of the
  code-review skill the persona invokes during Phase A. Sr Staff's
  default is `/review`. Other personas leave this empty.

**Default file paths.** Yoke ships at plugin-root `agents/sr-eng.md`,
`agents/sr-qa.md`, `agents/sr-staff.md`. Host overrides at the host
project's `.claude/agents/` directory; Claude Code's resolution order
picks the override automatically.

**Tests:** schema-conformance sensor on every persona file at
`/yoke:implement` startup; fixture-based loader test under
`tests/runtime/persona-loader.test.sh`.

### Per-persona slice file
**Description.** Each cycle owns a directory at
`.yoke/runtime/cycles/<N>/`. Each persona writes exactly one slice
file in that directory: `.yoke/runtime/cycles/<N>/<persona>.md`. The
flat layout is the carry-forward decision (chosen over the nested
per-round shape — réplica history is preserved as sections inside
the persona slice, not as separate files, to keep merge logic
trivial).

**Schema (markdown with frontmatter):**

```yaml
---
cycle: <N>
persona: <name>
created_at: <iso8601>
status: in-progress | done
---

## Phase A — own progress

<persona's account of what it executed in Phase A; references its own
sensors invoked, files touched, verdicts produced>

## Phase B round 1 — readings

<persona's interpretation of every other persona's Phase A entry;
flags any disagreement with its own objective>

## Phase B round 1 — réplica

<persona's response to other personas' readings, if any. Empty when
the persona has no objection to raise.>

## Phase B round 2 — readings

...

## Phase B round 2 — réplica

...
```

The number of round sections is bounded by the configured round cap
(default 3). The persona only appends; never modifies its own prior
sections. The slice file's `status` field flips to `done` when the
persona's last action this cycle is complete (either consensus
reached or round-cap exhausted).

**Tests:** slice-isolation sensor (assert no persona modifies another
persona's slice during the cycle); round-cap sensor (assert no slice
contains more round sections than configured cap).

### Sync-barrier file marker
**Description.** Each persona writes an empty file
`.yoke/runtime/.phase-a-done.<persona>` immediately before exiting
its Phase A Task call. `/yoke:implement` checks for the presence of
all three markers (one per persona) before opening Phase B. Markers
are deleted at cycle end (or at cycle entry, idempotent cleanup).

**Tests:** sync-barrier sensor asserts every Phase B read of a
slice file happens with mtime ≥ the latest Phase-A marker mtime.
Sync-bug regressions become test failures, not silent runtime drift.

### Council merge view
**Description.** Read-only merged view of all per-persona slices in
a cycle. Produced by `lib/runtime/council-merge.sh` as a pure
deterministic function: merge order is alphabetical by persona name,
section order within each persona is the order written. The merged
view is consumed by the contradiction-detection arbiter and by
Trigger 4's user-facing escalation message.

**Schema:** structured markdown with one `## <persona>` H2 per
persona, then the persona's own slice sections nested as H3.

**Tests:** merge-determinism sensor — the merge of a fixed input set
produces a byte-identical output across runs.

### Contradiction-detection arbiter
**Description.** A new dedicated subagent (carry-forward decision
chosen over the rotating-duty shape — cheaper, cleaner) defined at
`agents/council-arbiter.md`. Spawned by `/yoke:implement` between
réplica rounds when a round produced ≥ 1 réplica. Reads the merged
view + the round's réplicas; emits a structured JSON verdict.

**Output schema (JSON):**

```json
{
  "round": <integer>,
  "consensus": <true | false>,
  "contradictions": [
    {
      "personas": ["<persona-a>", "<persona-b>"],
      "summary": "<one-line description of the disagreement>",
      "evidence": "<quote from the merged view>",
      "category": "direct-contradiction | importance-disagreement"
    }
  ],
  "tone_only_pairs": [
    {
      "personas": ["<persona-a>", "<persona-b>"],
      "summary": "<phrasing differs but no semantic gap>"
    }
  ]
}
```

The `tone_only_pairs` list is informational (does NOT count for
Trigger 4 per Resolved 7 of the PRD). The `contradictions` list is
load-bearing: empty → consensus; non-empty → council enters another
round (capped) or fires Trigger 4 if cap reached.

**Dispute rubric** (carry-forward closed in this spec):

- *Direct contradiction*: persona A asserts X, persona B asserts ¬X
  in the same scope. Counts.
- *Importance disagreement*: persona A says "good enough", persona B
  says "rework needed" on the same artifact. Counts.
- *Tone-only*: phrasing differences with no semantic gap (e.g., "this
  is suboptimal" vs "this could be cleaner" applied to the same
  artifact, neither persona blocking). Does NOT count.

**Tests:** fixture-based arbiter test using engineered slice triples
(consensus / direct-contradiction / importance-disagreement /
tone-only) under `tests/runtime/council-arbiter.test.sh`.

### Trigger 4 escalation message
**Description.** When the council exhausts its round cap with
unresolved contradictions, `/yoke:implement` writes a user-facing
escalation message and pauses the cycle for human arbitration. The
escalation surface is the same as today's Trigger 4 (no new channel).

**Schema:** markdown render of the merged view + the arbiter's last
verdict + a directive line ("user: pick a persona's verdict to
ratify, or supply a third resolution"). The user's reply is parsed
deterministically by `/yoke:implement` (existing parser, possibly
extended).

**Tests:** Trigger 4 sensor — fixture cycle with engineered
divergence escalates with the message rendered correctly; user
reply is parsed and applied as the round's resolution.

## Dependencies

### External services and libraries
- **Claude Code's Task tool.** Required for Phase A's parallel
  persona spawning and for the contradiction-detection arbiter
  invocation. Blocking semantics on Task return are load-bearing for
  the sync-barrier (defended additionally by file-marker per
  Resolved 1).
- **Claude Code's `/review` skill.** Sr Staff's default
  `review-skill`. No version pin; assumed shipped with Claude Code
  itself.
- **Claude Code's agent loader.** Resolves `agents/<name>.md` and
  `.claude/agents/<name>.md` automatically; the loader's tolerance
  of unknown frontmatter keys is what makes the persona-spec
  extension safe (see Risks in PRD).

### Internal prior work
- **`/yoke:implement`** (`skills/implement/`). Heavy refactor in
  Sprint 2: cycle structure changes from "spawn G/V/O in parallel,
  consolidate" to "Phase A parallel personas + Phase B council
  rounds + Phase C cycle entry/escalation."
- **`/yoke:drift-sense`** (`skills/drift-sense/`). Used in Sprint 1
  Task t01 to capture the baseline metric.
- **`lib/working-memory/*`**. Path helpers; new `cycles/<N>/` layout
  added in Sprint 1.
- **`lib/runtime/agent-config.sh`**. Existing model resolver;
  extended in Sprint 1 for persona-specific resolution.
- **`lib/sensors/*`**. Existing sensor harness; new sensors
  (sync-barrier, slice-isolation, merge-determinism, arbiter,
  Trigger-4) plug in via the same shape.
- **Existing sensor harness** under `tests/sensors/`. New tests
  follow the `*.test.sh` convention.
- **Acceptance Contract reader.** Sr QA's test-writing references
  acceptance-contract criterion IDs; existing reader resolves them.

### Cross-team coordination
- None. Single-user dogfood.

## Out of scope

What this Spec does NOT cover. Prevents scope creep during runtime.

- **Sr DevOps persona** and the pipeline / metrics / observability
  sensor category. Deferred to a follow-up PRD.
- **Realtime / chat-shaped inter-persona communication.** All
  council communication is file-based async (per-persona slices +
  merge view + arbiter verdict). No streaming, no socket layer.
- **Per-persona sensor gating beyond `sensor-toolkit` field.** v0
  honors the field as a list; runtime enforcement of "persona X
  cannot invoke sensor Y if Y not in toolkit" is a v3.x tightening,
  not a v0 concern.
- **Renaming canonical-memory entities** (`concepts/yoke-pattern-roles`
  and the 30 decisions referencing Generator/Validator). Phase 5
  canonization work after v3.0 ships, not the spec's deliverable.
- **Multi-tenant / multi-org persona registries.** v0 ships defaults
  + single-host override.
- **Cycle-level token budget enforcement per persona.**
  `cycles_max` covers full implementation cycles; per-persona token
  budgets are a future tightening.
- **`/ultrareview` automation.** `/ultrareview` is a human-only
  escalation that the user invokes manually after Trigger 4. Sr
  Staff cannot fire it autonomously.
- **Sub-array `review-skill` chains.** v0 is a single value; an
  array fallback chain is a v3.x tightening.
- **Backward-compat verification work item.** Resolved 10 of the
  PRD removes this from scope. Migration is "drain in-flight v2.x
  cycles before upgrading."
- **Phase 5 / Orchestrator-canonize changes.** The Orchestrator's
  canonize mode survives unchanged. Council does not touch Phase 5.

### Rationale

The first dogfood task on v3.0 must clear three bars simultaneously:

- **Low blast radius.** The change MUST be small enough that a
  failure during dogfood does not destabilize Yoke's own runtime.
  `agents-have-current-sprint` extends the existing
  `lib/runtime/persona-loader.sh` to surface the active
  `current_sprint:` value (already in
  `.yoke/runtime/progress.md`) into every persona's prompt header
  via `lib/runtime/cycle.sh pre-spawn`. Pure additive read; no
  state machine change; no Acceptance-Contract-shape change.
- **Clear acceptance criterion.** The change is binary-observable:
  for any cycle on any sprint, the merged view at
  `.yoke/runtime/cycles/<N>/<persona>.md` MUST start with a single
  line of the form `<!-- current_sprint: <NN> -->`. Sensors:
  `tests/runtime/agents-have-current-sprint.test.sh` (computational)
  + a calibrated llm-as-judge that asserts the persona slices
  reference the active sprint when their reasoning depends on it.
- **Exercises all three personas.** Sr Eng writes the loader
  patch + unit tests; Sr QA writes the contract-anchored acceptance
  test under `tests/acceptance/<slug>/` carrying
  `# criterion: <id>`; Sr Staff invokes `/review` against the
  diff and consults canonical memory for prior persona-prompt-
  header decisions. The change forces the council to converge on a
  shared interpretation of "what state belongs in a persona prompt
  header" — exactly the sort of small architectural detail the
  council protocol is designed to mediate without escalating
  Trigger 4.

The `agents-have-current-sprint` slug was chosen over alternatives
(e.g. `wm-helper-polish`, `sensor-toolkit-validation-tighten`,
`council-merge-byte-stable-on-utf8`) because the first-dogfood
task's primary value is **demonstrating the council protocol on a
real change**, not solving the largest backlog item. The other
candidates remain in the backlog of the v3.0-dogfood follow-up PRD.
