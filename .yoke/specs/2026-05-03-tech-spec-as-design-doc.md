## Overall objective

Reshape Phase 2 (`skills/tech-spec/SKILL.md` + `templates/spec.md`)
into an architecture-first **design doc** that (a) negotiates stack
with the user via a curated market menu plus host-project
auto-detection from manifest files, (b) queries canonical memory for
applicable architectural patterns with a `WebSearch` fallback gated by
`overrides.tech_spec.canonical_pattern_threshold` (default 3), and (c)
produces a single coherent file at `.yoke/specs/<slug>.md` carrying
exactly twelve H2 sections in fixed order: Context and Scope; Goals
and Non-Goals; System Context; Architecture; Stack and Dependencies;
APIs and Data Model; Non-Functional Requirements; Alternatives
Considered; Trade-offs; Cross-cutting Concerns; Technical Use Cases;
Open Questions. Phase 2 stops emitting any `### Task <ID>` anchor and
stops writing any file under `.yoke/sprints/`. Phase 3
(`skills/acceptance-contract/SKILL.md`) absorbs sprint partition and
task breakdown after drafting the binding BDD scenarios, preserving
the `concepts/yoke-pattern-sprint-runtime-bundle` shape downstream —
only the producer of sprint files changes from Phase 2 to Phase 3.
The cutover is atomic at the Sprint 01 boundary so the framework's
end-to-end contract is never broken between sprints.

## Sprints

Each sprint has a delivery objective (what is shippable at the end)
and is rendered as a self-contained **sprint runtime bundle** at
`.yoke/sprints/<slug>-s<NN>.md`. The sprint file is the cycle's
working set during `/yoke:implement` (one ralph cycle = one sprint
file as the working set, per the 2026-04-27 sprint-as-cycle PRD); it
carries the per-task `### Task <ID>` subsections inline (with the
four labels `**Story:**`, `**Technical implementation:**`,
`**Validation:**`, `**Acceptance criterion:**`), the sprint
acceptance-criterion ID list, and the sprint sensor ID list. **This
file carries no inline task entries** — it lists the sprint headers
and points at the per-sprint runtime bundle for the body.

Sprint ID shape: `<slug>-s<NN>`, where `<slug>` matches the
existing working-memory slug regex (`<YYYY-MM-DD>-<kebab-slug>`) and
`<NN>` is the sprint number zero-padded to 2 digits. Padding is what
makes lexical sort = positional order in `wm_list_sprint_paths`.

## Contracts and interfaces

### `templates/spec.md` body shape (twelve H2 sections, fixed order)

The new `templates/spec.md` and every spec body produced by
`/yoke:tech-spec` carry exactly these H2 headings in this order:

```
## Context and Scope
## Goals and Non-Goals
## System Context
## Architecture
## Stack and Dependencies
## APIs and Data Model
## Non-Functional Requirements
## Alternatives Considered
## Trade-offs
## Cross-cutting Concerns
## Technical Use Cases
## Open Questions
```

A self-check post-draft (deterministic grep) asserts the headings
appear, in order, with no extra H2s in between. Missing or
out-of-order headings abort the skill non-zero with a
`wm:`-prefixed message and the offending offset. Tests:
`tests/smoke/tech-spec-design-doc-shape.test.sh`.

### `### US-### — <title>` subsection shape (under "Technical Use Cases")

Each PRD `US-###` lifts to a subsection of the form:

```
### US-001 — <story title>

**Components involved:** <bullet list or comma-separated names>
**Contracts used:** <bullet list>
**NFRs applied:** <NFR-name list referencing the NFR section>
**Edge cases:** <bullet list>
```

The self-check post-draft asserts every PRD `US-###` appears in this
section (or is marked `Deferred: <reason>` with the deferral surfaced
in `## Open Questions`). Silently dropping a US-ID aborts the skill
non-zero. Tests: `tests/smoke/tech-spec-design-doc-shape.test.sh`.

### `## Non-Functional Requirements` quantitative-target rule

Each NFR is a bullet of the form `- **<NFR-name>:** <quantitative target>`
where `<quantitative target>` matches the regex
`\d+(\.\d+)?\s*(ms|s|%|rps|qps|req/s|MB|GB|TB|users)` (case-insensitive).
A self-check rejects adjective-only entries ("performant", "secure",
"reliable" without numbers). Tests:
`tests/smoke/tech-spec-design-doc-shape.test.sh`.

### `## Alternatives Considered` triple-shape rule

Each alternative is a `### Alt: <name>` subsection carrying three
labelled lines:

```
**Trade-off vs. chosen:** <text>
**Reason for rejection:** <text>
**Source:** <canonical-memory entity wikilink OR WebSearch URL OR "internal experience">
```

The self-check rejects entries missing any of the three labels.
WebSearch sources MUST be URLs returned by an actual `WebSearch`
invocation in the same skill session — fabricated URLs fail review.
Tests: `tests/smoke/tech-spec-design-doc-shape.test.sh`.

### Stack auto-detection contract

`/yoke:tech-spec` reads (when present) these manifest files via the
`Read` tool to populate the stack-default offer:

- `package.json` → Node.js / TypeScript family
- `go.mod` → Go family
- `Cargo.toml` → Rust family
- `requirements.txt`, `pyproject.toml` → Python family
- `pom.xml` → Java / JVM family
- `Gemfile` → Ruby family

When ≥ 2 manifest files are detected, the skill MUST list every
detected stack as a candidate in the dialogue and refuse to
auto-pick. The user must reply.

### Canonical-memory threshold contract

`/yoke:tech-spec` invokes `/yoke:search-canonical-memory` with a
domain-scoped query before drafting. Define `applicable_count` as
the number of pattern-typed entities in the response. If
`applicable_count >= overrides.tech_spec.canonical_pattern_threshold`
(default 3, configurable in `.yoke/config.yaml`), the skill skips
`WebSearch`. Otherwise, the skill loads `WebSearch` via `ToolSearch`
and runs a single targeted query, then surfaces the top 2-3
industry patterns with explicit trade-offs in the architecture
round of the dialogue. The chosen alternatives are cited in the
spec's `## Alternatives Considered` section with their `Source:`
labels populated.

### `lib/working-memory/scaffold-sprints.sh` invocation-site change

The script's interface is preserved: it takes a single argument
that points at a markdown file containing `### Sprint <NN> — <name>`
headings and creates one `.yoke/sprints/<slug>-s<NN>.md` per heading
seeded from `templates/sprint.md`. The change is the **caller**:

- Before: `/yoke:tech-spec` invokes it (stage 2 of the legacy
  3-stage blueprint) against the spec file.
- After: `/yoke:acceptance-contract` invokes it (stage B of the new
  Phase 3 flow) against a **sprint plan** the contract draft
  produces inline. The sprint plan reuses the
  `### Sprint <NN> — <name>` heading shape so the script's parser is
  unchanged.

The script itself is untouched (no flag changes, no behavior
changes, no signature changes). Tests:
`tests/smoke/scaffold-sprints-callable-from-phase-3.test.sh`.

### `/yoke:acceptance-contract` two-stage flow contract

Phase 3 is a 2-stage blueprint (per
`concepts/yoke-conventions :: blueprints wrapping agentic nodes`):

- **Stage A — BDD drafting (LLM).** Read approved PRD + approved
  spec; draft `.yoke/acceptance-contracts/<slug>.md` with one BDD
  scenario per PRD `US-###` (mapped through the spec's "Technical
  Use Cases") plus one per `FR-N` not covered by a US-### scenario.
- **Stage B — sprint+task partitioning.** Sub-stages:
  - **B.1 (LLM)** — draft a sprint plan section inside the
    contract carrying `### Sprint <NN> — <name>` headings with
    delivery objectives and ordered task references back to BDD
    scenario IDs.
  - **B.2 (bash)** — invoke `scaffold-sprints.sh` against the
    sprint plan section to materialize empty sprint files at
    `.yoke/sprints/<slug>-s<NN>.md`.
  - **B.3 (LLM-per-sprint)** — for each empty sprint file in
    lexical order, fill the five required H2 sections (`## Sprint
    objective`, `## Sprint DoD`, `## Tasks` with `### Task <ID>`
    subsections carrying the four inline labels, `## Functional
    acceptance criteria` with criterion IDs only, `## Sensors` with
    sensor IDs only). Each per-sprint call carries only the
    sprint preamble and the single empty sprint file — no
    siblings, no full contract, per the progressive-disclosure
    rule.

Trigger 3 covers the contract and every sprint file together.
Atomic approval — partial state aborts non-zero before the menu.

### `templates/sprint.md` shape: unchanged

The structural shape is preserved exactly (frontmatter +
`# Sprint <NN> of <MM>: <name>` + the five H2 sections). Only the
producer changes from Phase 2 to Phase 3. This honors
`concepts/yoke-pattern-sprint-runtime-bundle :: applies_to`.
