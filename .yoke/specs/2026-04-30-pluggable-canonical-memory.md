# Spec: Pluggable canonical-memory provider

## Overall objective

Reduce Yoke's canonical-memory surface to two provider-agnostic facade
skills (`/yoke:search-canonical-memory`, `/yoke:canonize`) that
dispatch to provider plugins through a curated `providers.yaml`
manifest. Extract the current Bedrock-specific implementation into a
peer plugin (`claude-bedrock`) so Yoke + Bedrock together preserve
every capability Yoke ships today, while leaving room for alternative
providers (`claude-mem`, custom vaults) without forking Yoke. Ship
the change as v2.0.0 with a hard-break migration enforced at
`/yoke:bootstrap`.

## Sprints

Each sprint has a delivery objective (what is shippable at the end)
and is rendered as a self-contained **sprint runtime bundle** at
`.yoke/sprints/<slug>-s<NN>.md`. The sprint file is the cycle's
working set during `/yoke:implement` (one ralph cycle = one sprint
file as the working set, per the 2026-04-27 sprint-as-cycle PRD); it
carries the per-task `### Task <ID>` subsections inline (with the
four labels `**Story:**`, `**Technical implementation:**`,
`**Validation:**`, `**Acceptance criterion:**`), the sprint
acceptance-criterion ID list, and the sprint sensor ID list. **This
file carries no inline task entries** — it lists the sprint headers
and points at the per-sprint runtime bundle for the body.

Sprint ID shape: `<slug>-s<NN>`. Lexical order = positional order
under `wm_list_sprint_paths`.

Sprint sequencing follows
`yoke-decision-2026-04-24-vertical-slice-before-horizontal-completeness-spri`:
each sprint ships an installable plugin version per
`yoke-decision-2026-04-24-each-sprint-produces-an-installable-exercisable-pl`.
Skill placement honors
`yoke-decision-2026-04-25-skills-deliberate-subagents-adapt-new-invariant`
— the two new facade skills are pure deliberation surfaces (no
subagents spawned at runtime).

### Sprint 01 — Provider abstraction layer (v2.0-alpha)
**Delivery objective:** A user installing Yoke at the end of Sprint 1
can run `/yoke:search-canonical-memory "<query>"` and `/yoke:canonize`
and have those calls dispatch through `providers.yaml` into the
existing in-Yoke skills (`/yoke:ask`, `/yoke:teach`). The legacy
skills remain intact and continue to work — Sprint 1 is purely
additive. This sprint validates the abstraction shape against real
callers without extracting Bedrock yet.

**Tasks:** see `.yoke/sprints/2026-04-30-pluggable-canonical-memory-s01.md` `## Tasks` section.

### Sprint 02 — Bedrock peer plugin + internal switchover (v2.0-beta)
**Delivery objective:** A user installing Yoke + the new
`claude-bedrock` peer plugin at the end of Sprint 2 can run a full
`/yoke:implement` cycle end-to-end with all internal canonical-memory
operations going through the new facades. The Bedrock plugin owns
its skills under the `/bedrock:` namespace, including a new
`/bedrock:canonize` that consumes `.yoke/` working memory per the
contract authored in Sprint 1. Yoke's internal call-sites (agent
prompts, spec-phase skills, `/yoke:implement`, sensors, tests)
reference only the facade verbs. The legacy `/yoke:ask`,
`/yoke:preserve`, `/yoke:teach`, `/yoke:compress`, `/yoke:memory`,
`/yoke:confluence-to-markdown`, `/yoke:gdoc-to-markdown` skills
remain present in the Yoke plugin source as inactive duplicates —
their removal happens in Sprint 3. This split keeps Sprint 2
reversible without forfeiting end-to-end coverage.

**Tasks:** see `.yoke/sprints/2026-04-30-pluggable-canonical-memory-s02.md` `## Tasks` section.

### Sprint 03 — Cleanup, hard-break migration, v2.0.0 (v2.0.0)
**Delivery objective:** A user upgrading from Yoke v1.1.x at the end
of Sprint 3 must re-run `/yoke:bootstrap` to migrate
`.yoke/config.yaml` before any Yoke skill works again — there is no
silent default. The legacy canonical-memory skills are deleted from
the Yoke plugin source. Documentation, templates, the user-facing
`CLAUDE.md`, and the plugin manifest are aligned with v2.0.0. A user
running a fresh `/yoke:bootstrap` against a project with the
`claude-bedrock` peer plugin installed completes setup interactively,
with `bedrock` selected as the provider, and proceeds straight into
`/yoke:discover`.

**Tasks:** see `.yoke/sprints/2026-04-30-pluggable-canonical-memory-s03.md` `## Tasks` section.

## Contracts and interfaces

The artifacts below are the interfaces Sprint 1 freezes; subsequent
sprints consume them without renegotiation.

- **`providers.yaml` (plugin root)** — curated registry of canonical-memory
  providers. Schema:

  ```yaml
  schema_version: 1
  providers:
    <provider-name>:
      description: "<one-line description>"
      requires:
        plugin: "<plugin-id-on-marketplace>"     # nullable for in-Yoke seed
        min_version: "<semver>"                  # nullable
      skills:
        search: "<plugin>:<skill>"               # mandatory
        canonize: "<plugin>:<skill>"             # mandatory
      config_passthrough:
        - <key-in-canonical_memory-block>        # forwarded to provider opaquely
  ```

  Sprint 1 seeds:

  ```yaml
  schema_version: 1
  providers:
    bedrock:
      description: "Markdown frontmatter graph in a separate git repository (Yoke v1 reference implementation)"
      requires:
        plugin: yoke
        min_version: "2.0.0"
      skills:
        search: "yoke:ask"
        canonize: "yoke:teach"
      config_passthrough: [url, name, default_branch]
  ```

  Sprint 2 rewrites the `bedrock` entry's `requires.plugin` to
  `claude-bedrock`, `requires.min_version` to the Bedrock plugin's
  initial release, and `skills.{search,canonize}` to `bedrock:ask` /
  `bedrock:canonize`.

- **`.yoke/config.yaml :: canonical_memory` block** — extended schema:

  ```yaml
  canonical_memory:
    provider: bedrock                            # required at v2.0.0
    # provider-specific options forwarded opaquely
    url: "https://github.com/.../iury-brain.git"
    name: "iury-brain"
    default_branch: main
  ```

  The legacy `url` / `name` / `default_branch` keys remain as
  provider-passthrough during Sprints 1 and 2; their interpretation
  moves entirely into the Bedrock plugin in Sprint 2 (Yoke does not
  read them). The `provider` key is REQUIRED at v2.0.0; the
  hard-break check in Sprint 3 enforces it.

- **`/yoke:search-canonical-memory <query>`** — the argument is the
  natural-language query string. The skill resolves the active
  provider, invokes `${provider.skills.search} "<query>"` via the
  `Skill` tool, and returns the provider's textual answer verbatim
  to the caller. No parsing, no validation, no schema. Read-only;
  never writes.

- **`/yoke:canonize`** — no arguments. The skill resolves the active
  provider, invokes `${provider.skills.canonize} --working-memory
  "$(pwd)/.yoke/"` via the `Skill` tool, and propagates the
  provider's exit code. The provider is responsible for reading
  `.yoke/`, classifying what is consolidated, and applying its own
  governance protocol. Yoke does not pre-process, bundle, or
  validate.

- **Working-memory provider contract**
  (`docs/canonical-memory-provider-contract.md` authored in
  Sprint 1) — versioned document describing the layout under
  `.yoke/` that providers SHOULD read when receiving the
  `--working-memory` flag: `prds/<slug>.md`, `specs/<slug>.md`,
  `sprints/<slug>-s<NN>.md`, `acceptance-contracts/<slug>.md`,
  `contracts/<slug>.md`, `runtime/progress.md`. The document carries
  a `contract_version: 1` field; future layout changes bump the
  version and update `providers.yaml.schema_version`. Compliance is
  provider-side; Yoke does not enforce it.

- **Provider exit-summary convention (soft)** — providers SHOULD
  print a single-line summary to stdout on canonize completion
  (e.g., `canonize: created=3 updated=1 skipped=2`). Yoke logs
  whatever it receives into `.yoke/runtime/progress.md` final-cycle
  entry but does not parse or fail on format mismatches. (PRD
  Open Question Q2 closed as soft.)

- **Hard-break pre-flight contract (Sprint 3)** — every `/yoke:*`
  skill invokes a shared bash helper
  (`lib/yoke-prelude.sh::yoke_require_provider`) before its body.
  The helper aborts non-zero with the message
  `wm: canonical_memory.provider not configured. Run /yoke:bootstrap
  to migrate.` if `.yoke/config.yaml` lacks the key. Skills that
  must run without an active project (notably `/yoke:bootstrap`
  itself) opt out by not sourcing the helper.

## Dependencies

### External services and libraries

- **Claude Code Skill tool** — required at runtime for the facade
  skills to invoke provider skills via cross-plugin dispatch. Already
  a baseline assumption (every Yoke skill uses it).
- **`claude-bedrock` peer plugin** (Sprint 2 onward) — distributed
  via the same marketplace channel as Yoke; the user installs it
  alongside Yoke. v0 distribution = standalone repo
  `iurykrieger/claude-bedrock` with its own `.claude-plugin/plugin.json`.
  Marketplace listing is out of scope for v0 (deferred).

### Internal prior work

- `concepts/yoke-pattern-memory-model` — defines the two-tier memory
  model and the `/yoke:ask` / `/yoke:preserve` mediation contract.
  Refined (not superseded) by the renamed facades — the contract
  shape is preserved; only the verb names and provider boundary
  change.
- `concepts/yoke-pattern-plugin-structure` — directory-layout
  invariant enforced by `lib/sensors/no-vibeflow-refs.sh`. Sprint 3
  updates the sensor's allowlist after the legacy directories move
  out.
- `lib/working-memory/paths.sh` — `wm_*` path helpers. Sprint 1
  reuses these to resolve `.yoke/` for the `--working-memory`
  argument to `/yoke:canonize`.
- `concepts/yoke-pattern-sprint-runtime-bundle` — runtime-bundle
  layout the working-memory contract document references in Sprint 1.

### Cross-team coordination

- **Solo-maintainer (Iury)** — owns both Yoke and `claude-bedrock`
  during v0. No cross-team coordination required, but the maintainer
  must publish both plugins in the same release window so users
  upgrading to Yoke v2.0.0 can install the peer plugin without
  delay.

## Out of scope

What this Spec does NOT cover. Prevents scope creep during runtime.

- **A second functional provider beyond Bedrock.** v2.0.0 ships with
  `bedrock` as the only working entry in `providers.yaml`. Adding
  `claude-mem` or any other provider is a separate follow-up PRD —
  the abstraction must prove itself with one provider before chasing
  diversity.
- **Yoke-built-in stub provider for tests.** Integration tests use
  the real `claude-bedrock` plugin installed alongside Yoke. A
  hermetic stub provider is deferred to v2.x. (PRD Open Question Q8
  closed.)
- **Backward-compatible aliases.** `/yoke:ask` and `/yoke:preserve`
  do not survive as deprecated aliases pointing to the new facades.
  Hard rename per PRD invariant. Users on v1.x scripts must update
  call-sites.
- **Multi-memory-per-project support.** A project's `.yoke/config.yaml`
  declares exactly one provider with one config block. The
  `/yoke:memory` registry-management skill is removed entirely; if a
  project needs to switch providers it edits `.yoke/config.yaml` and
  re-runs the relevant provider's setup.
- **Migration tooling for legacy entities inside an existing
  canonical memory.** Existing Bedrock vaults (e.g., `iury-brain`)
  keep working unchanged because Bedrock remains the active provider;
  entities are not rewritten. Cross-provider migration (Bedrock →
  claude-mem, etc.) is the user's problem.
- **Marketplace publication of `claude-bedrock`.** v0 ships the peer
  plugin via direct GitHub install (`/plugin install
  iurykrieger/claude-bedrock`). Marketplace listing follows in a
  later release.
- **Refactor of doctrine entities inside `iury-brain` that cite
  `/yoke:ask` / `/yoke:preserve` by name.** Outdated references stay
  in canonical memory until the next dogfood `/yoke:canonize` pass
  rewrites them; Sprint 3 does not include a doctrine-rewrite task.
  This is acceptable because `/yoke:ask` callers are agents/skills
  (now rewritten) and the canonical-memory text is a historical
  record, not executable.
- **Marketplace-style auto-discovery of providers** beyond the
  curated `providers.yaml`. PRD specified curated (option I);
  convention-based scanning and hybrid local-override layers are
  deferred.
