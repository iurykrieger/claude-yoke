## Context and Scope

The Orchestrator persona prompt (`agents/orchestrator.md`) is the
literal text loaded by `/yoke:implement` (`skills/implement/SKILL.md`)
into a `Task` call when it spawns the Orchestrator subagent at full-run
loop termination. The prompt's job is to teach that subagent to invoke
`/yoke:canonize` opaquely — `/yoke:canonize` is the v2.0.0 facade verb
that resolves `canonical_memory.provider` from `.yoke/config.yaml`,
dispatches the active provider's namespaced canonize skill, and
internalizes the five-criterion cascade and Model C impact
classification as implementation detail of the dispatch.

The v2.0.0 cutover (Part 4 of the bedrock canonical-memory port,
documented in `CLAUDE.md`'s migration history at the
`2026-04-30 (v2.0.0)` entry) retired
`lib/canonical-memory/canonization-criteria.sh` — the helper that
v1.x co-located with the Orchestrator persona for criterion evaluation
and impact classification. The retirement is doctrine. The persona
prompt was updated in three sites to acknowledge the retirement
(the v3.0 cutover note at lines 31–54, and the prose at lines 81–82,
97–98, 192–193 all say "Part 4 of the bedrock canonical-memory port
retired that primitive"). The same prompt nonetheless continues to
cite the retired script as a live invocation surface in four other
sites (lines 78, 100, 142, 190), producing a self-contradictory
document.

**Scope.** This spec changes exactly one file
(`agents/orchestrator.md`) by rewriting four paragraphs so they
describe `/yoke:canonize` as the opaque dispatch surface (per
`concepts/yoke-pattern-facade-vs-provider-verbs`) without naming any
internal helper of the canonize skill. Every site that previously
named the retired script names `/yoke:canonize` instead — that is the
literal substitution the rewrite enforces. The spec does NOT change
`skills/canonize/SKILL.md`, any other persona prompt
(`agents/sr-eng.md`, `agents/sr-qa.md`, `agents/sr-staff.md`,
`agents/council-arbiter.md`), or any file under `lib/canonical-memory/`.
The spec does NOT reintroduce the retired script.

## Goals and Non-Goals

**Goals**

- After the fix lands, `grep -nE "canonization-criteria"
  agents/orchestrator.md` returns exactly 0 lines.
- Every paragraph in the rewritten file is internally consistent: the
  five-criterion cascade and impact classification are described as
  happening inside `/yoke:canonize` Phase 3, not as Orchestrator-side
  shell-outs.
- Every retirement statement currently present (lines 31–54, 81–82,
  97–98, 192–193) has its semantic content preserved at least once
  in the rewritten file.
- Every formerly-script-named site cites `/yoke:canonize` (the
  facade verb) explicitly in its replacement prose.

**Non-Goals**

- Rewriting `/yoke:canonize` itself or any sub-skill of
  `skills/canonize/`. The skill's internal Phase 3 implementation is
  unaffected.
- Reintroducing or renaming `canonization-criteria.sh`. The v2.0.0
  retirement stands.
- Editing other persona prompts (Sr Eng / Sr QA / Sr Staff / Council
  Arbiter). Cross-persona doctrine drift is out of scope and no
  follow-up `/yoke:fix` is opened by this spec or its implementation.
- Authoring a global regression sensor that asserts the absence of
  retired v2.0.0 primitives across `agents/*.md` and
  `skills/**/SKILL.md`. The fix is doc-shaped; the regression
  surface is the file-scoped `grep` assertion in FR-1.
- Authoring User Stories. Phase 3 (`/yoke:acceptance-criteria`)
  owns US authoring; this spec emits FR-N walkthroughs only.

## System Context

The Orchestrator persona prompt is read by `/yoke:implement` and
loaded as the prompt body of a `Task` subagent call at full-run
termination. The subagent then invokes `/yoke:canonize` via the Skill
tool. `/yoke:canonize` is the framework-owned facade verb that
dispatches to the active canonical-memory provider's namespaced
canonize skill (e.g. `bedrock:canonize`).

```
/yoke:implement (coordinator)
   │
   │  Task(prompt=<agents/orchestrator.md body>, mode=canonize)
   ▼
Orchestrator subagent
   │
   │  Skill(skill="yoke:canonize")          ◄── the literal
   ▼                                            invocation the
/yoke:canonize  ───────► resolve-provider.sh    rewritten prompt
   │                                            teaches
   │  Skill(skill="${YOKE_PROVIDER_CANONIZE_SKILL}")
   ▼
bedrock:canonize (provider-internal phases:
   - five-criterion cascade
   - Model C impact classification
   - PR opening)
```

Per `concepts/yoke-pattern-facade-vs-provider-verbs` ("Facade contract
(Yoke side)" rules 1–5), facade verbs MUST treat the provider as
opaque. The Orchestrator persona prompt is upstream of the facade —
naming a provider-internal helper inside the prompt leaks the
substrate-specific implementation into the framework's persona
contract. The four offending sites violate that boundary; the
replacement prose names `/yoke:canonize` as the dispatch surface and
nothing below it.

## Architecture

The fix is a **single-file prose rewrite constrained by the facade
boundary**. Inheriting from
`concepts/yoke-pattern-facade-vs-provider-verbs`, the rewrite enforces:

1. **Opaque dispatch with explicit facade naming.** Every paragraph
   that previously named
   `lib/canonical-memory/canonization-criteria.sh` is rewritten so the
   literal slash-command identifier `/yoke:canonize` appears in its
   place. The rewrite is a substitution at the contract layer, not a
   deletion: the persona prompt now teaches the subagent to invoke
   `/yoke:canonize` (and only `/yoke:canonize`) for the operations
   the retired helper used to perform.
2. **Phase-number anchoring.** Where the rewritten prose references a
   step inside `/yoke:canonize`, it cites "Phase 3" of the canonize
   skill, matching the existing language at lines 81–82 and 97–98 and
   the structure of `skills/canonize/SKILL.md`. Cross-checking phase
   numbers is a regression-surface invariant (Risk #1 / Risk #3 in
   the fix-spec).
3. **Retirement-statement preservation.** The declarative content
   "Part 4 of the bedrock canonical-memory port retired that
   primitive" or its semantic equivalent survives at least once in the
   rewritten file (FR-7).
4. **No structural reshape.** The fix does NOT reorder sections,
   rename headings, or split paragraphs across boundaries the v3.0
   cutover note (lines 31–54) anchors. Section-internal prose flow
   may be tightened, but the Behaviors / Memory scope / Allowed tools
   skeleton stays intact.

The architecture is a **deterministic markdown edit**. There is no
agentic node — the rewrite is a series of `Edit` calls bounded by the
fix-spec's FR set, and the post-fix invariants are enforceable by
`grep`-shaped sensors.

## Alternatives Considered

### Alt: Rewrite the entire Orchestrator persona prompt

**Trade-off vs. chosen:** Pure rewrite would let us reorganize
sections (Single runtime mode → Behaviors → Memory scope → Allowed
tools) for narrative cleanliness, not just delete provider-internal
helper names. The chosen approach keeps the structure and only
reshapes four paragraphs.
**Reason for rejection:** The fix-spec's FR-6 explicitly forbids
broader reshape; a full rewrite bloats the diff, makes the change
hard to review, and risks introducing fresh contradictions outside
the four offending sites. The fix-spec also names the v3.0 cutover
note at lines 31–54 as load-bearing prose to preserve verbatim.
**Source:** internal experience

### Alt: Delete the four offending paragraphs without replacement

**Trade-off vs. chosen:** Pure deletion is the smallest possible
diff. The chosen approach reframes each paragraph to name
`/yoke:canonize` explicitly as the dispatch surface.
**Reason for rejection:** The four offending paragraphs each carry
load-bearing prose beyond the offending citation: line 78 frames the
five-criterion cascade hand-off, line 100 carries the impact-keyword
heuristics table, line 142 anchors a `### Never` clause, line 190
justifies the `Bash` tool allowance. Deleting the paragraphs would
lose that load-bearing context and re-open the very contracts the
prose was meant to teach the persona.
**Source:** internal experience

### Alt: Reintroduce a thin shim `canonization-criteria.sh`
that shells out to `/yoke:canonize`

**Trade-off vs. chosen:** Reintroducing a shim would let the prompt
keep its existing prose and have the script exist again.
**Reason for rejection:** The v2.0.0 retirement is doctrine
(`concepts/yoke-decision-2026-04-30-extract-bedrock-as-peer-plugin`);
reintroducing a shim re-couples Yoke to a single provider's
implementation and violates
`concepts/yoke-pattern-facade-vs-provider-verbs`'s "Yoke skills MUST
NOT invoke provider verbs directly" rule. It also doubles the
maintenance surface — every future provider would need a parallel
shim.
**Source:** [[yoke-pattern-facade-vs-provider-verbs]]

## Trade-offs

- **Diff vs. structural cleanup.** Keeping the existing section
  skeleton means the rewritten prose sits inside paragraphs that may
  not be the most narratively pure organization for the post-v2.0.0
  doctrine. The trade-off is review-friendliness over editorial
  perfection.
- **Regression surface scope.** The regression assertion is
  file-scoped (one `grep` against `agents/orchestrator.md`). It will
  not catch the same drift if it appears in a different file. The
  trade-off is keeping the spec's surface tight (one file edited,
  one assertion authored) over global doctrine-drift coverage. Per
  the fix-spec's Non-Goals and the user's revise feedback, neither a
  global sensor nor a follow-up `/yoke:fix` for cross-prompt drift
  is in scope.
