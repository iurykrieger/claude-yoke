## Context and Scope

This spec adds a second authoring path to Phase 1 of the Yoke
lifecycle. Today, every change funnels through `/yoke:discover` (a
Product-Manager grill that produces `.yoke/prds/<slug>.md`).
Decision 3B during PRD authoring widened the alternative-path scope
beyond bugfixes to include narrow refactors, dependency bumps, and
infra tweaks — all of which are engineering-shaped, not
product-shaped. This spec realises that widening as a new skill
`/yoke:fix` that produces a fix-spec at `.yoke/fixes/<slug>.md` and
threads through the unchanged downstream chain
(`/yoke:tech-spec` → `/yoke:acceptance-criteria` → `/yoke:implement`
→ `/yoke:canonize`).

**In scope.** New skill `skills/fix/SKILL.md`; new template
`templates/fix.md`; new path helpers `wm_fix_path` and
`wm_phase1_artifact_path` in `lib/working-memory/paths.sh`;
existence-aware "both exist" abort with structured recovery
diagnostic; `wm_set_active` invariant on write; Mode-tag convention
in skill personas (backfilled into `/yoke:tech-spec`); migration of
five downstream skills from `wm_prd_path` to
`wm_phase1_artifact_path`; new sensor at
`tests/sensors/no-direct-prd-path.test.sh`; plugin version bump.

**Out of scope.** No changes to Phase 2's twelve H2 sections; no
fix-shaped tech-spec template; no Phase-3 exception path
(acceptance-criteria still mandatory); no migration of historical
`.yoke/prds/` content; no automated detection picking
`/yoke:fix` vs `/yoke:discover`; no special-casing of fix-specs in
the canonize cascade. The fix-spec is read as opaque Phase-1 input
by all downstream skills.

## Goals and Non-Goals

**Goals**

- Produce `.yoke/fixes/<slug>.md` with `Status: approved` ratified
  through Trigger 1's shared approval menu — same surface as
  `/yoke:discover`'s Trigger 1.
- Enforce the "exactly one Phase-1 artifact per slug" invariant
  through three layers (FR-4 collision detection, FR-9 resolver
  abort, FR-9a `wm_set_active` gate).
- Encode the four narrowness proxies (FR-6) verbatim in the persona
  body so the dialogue is deterministic in its challenge shape and
  the runtime LLM has no judgment to invent.
- Migrate every `wm_prd_path` read site outside the two Phase-1
  authoring skills to `wm_phase1_artifact_path` in the same change,
  with a sensor that traps regressions.

**Non-Goals**

- Unifying `/yoke:discover` and `/yoke:fix` into a single skill
  with a `--mode` flag; the personas are deliberately distinct.
- Refactoring `lib/working-memory/paths.sh` to a generalised
  I/O-aware contract; the existence-aware resolver is a documented
  exception, not a precedent.
- Authoring a Phase-3 acceptance-criteria document inside this spec
  — that work happens in `/yoke:acceptance-criteria` after Trigger
  2, against the current spec.

## Architecture

The skill is a **blueprint wrapping agentic nodes** per
`concepts/yoke-conventions`: a deterministic outer scaffold (bash
pre-flight, working-memory path resolution, post-draft self-check,
shared approval menu) wrapping a single LLM stage (the Senior
Engineer persona dialogue). The architecture inherits from
`yoke-pattern-roles` (spec-phase Generator persona inline) and
`yoke-pattern-plugin-structure` (skills/, templates/, lib/, tests/
top-level layout).

**Invariants the architecture guarantees:**

- Exactly one Phase-1 artifact exists per slug at any time, enforced
  at three layers (FR-4 / FR-9 / FR-9a).
- The fix-spec is read as opaque Phase-1 input by every downstream
  skill — no skill branches its core logic on PRD-vs-fix-spec
  identity per `yoke-pattern-phase-flow`.
- The narrowness gate (FR-6) is graduated, not binary: 4/4 silent,
  3/4 → frontmatter `scope_caution:` field, ≤ 2/4 abort with
  re-route to `/yoke:discover`. The graduation gives Phase 6 drift
  sensing a structured field to scan.
- The `wm_phase1_artifact_path` resolver is the canonical I/O-aware
  exception in `lib/working-memory/paths.sh` — its docstring states
  the existence-aware contract does not propagate to future
  helpers, which remain pure path computers by default.
- Structured failure surfaces follow `yoke-pattern-sensors`'
  back-pressure principle: success is silent; failures carry
  violation identification, location, and correction instruction.

**Failure modes the architecture explicitly does not handle:**

- Concurrent skill invocations on the same slug across two terminals
  — the slug-collision check (FR-4) is single-process; CI parallelism
  on the same machine is out of scope. Scenario III in PRD OQ-3.
- Mid-dialogue session abort leaving a partial fix-spec on disk —
  the user re-runs `/yoke:fix` with the same slug; FR-4 fires.

## APIs and Data Model

The skill exposes no network APIs. The "API" is a set of
working-memory contracts and skill invocation surfaces.

- **`/yoke:fix [<problem-statement>]`** — slash-command surface.
  Optional positional argument for the initial problem statement;
  if omitted, the dialogue opens with "Describe what's broken." The
  skill reads `Skill` tool availability and degrades the approval
  menu's option 1 per `templates/approval-menu.md`'s fallback.
- **`wm_fix_path "<slug>"`** — pure path helper exported from
  `lib/working-memory/paths.sh`. Returns
  `.yoke/fixes/<slug>.md` deterministically. No I/O. Tests:
  unit cases for slug regex acceptance, kebab-only output.
- **`wm_phase1_artifact_path "<slug>"`** — existence-aware resolver
  exported from `lib/working-memory/paths.sh`. Returns the existing
  Phase-1 path with exit 0; aborts non-zero with the structured
  recovery diagnostic on "neither" or "both" cases. Tests: unit
  cases for each branch (neither / only-PRD / only-fix / both),
  diagnostic substring assertions, exit code assertions.
- **`wm_set_active "<slug>"`** — extended to enforce the "exactly
  one Phase-1 artifact" invariant on write. Refuses to record a
  slug whose archives violate the invariant, printing the FR-9
  diagnostic verbatim. Tests: regression case for both-exist
  refusal; happy-path case retained.
- **Fix-spec frontmatter schema** —

  ```
  > Generated by `/yoke:fix` on <iso8601-date>.
  > Status: <draft | approved>
  > Approved by: <user>
  > Approved at: <iso8601>
  > scope_caution: <empty | component-breadth | contract-shape | trigger-specificity | surface-containment>
  ```

  The `scope_caution:` field is mandatory. Empty value when 4/4
  narrowness proxies pass; one of the four proxy identifiers when
  3/4 pass. Tests: schema-shape sensor at
  `tests/sensors/fix-spec-frontmatter-shape.test.sh`.
- **Mode-tag schema** — every engineering-flavored skill body opens
  the "Your role" section with one line of the form
  `**Mode:** <kebab-value>`. Initial vocabulary: `diagnose-first`,
  `design-first`. Open vocabulary; future skills append values. The
  Phase-3 acceptance-criteria document for this spec authors at
  least one Acceptance Criterion whose pool sensor scans
  `skills/*/SKILL.md` for the Mode tag's presence and shape.
- **Sensor at `tests/sensors/no-direct-prd-path.test.sh`** — bash
  sensor that grep-audits `skills/` for `wm_prd_path` reads outside
  `skills/discover/SKILL.md` and `skills/fix/SKILL.md`. Emits a
  `wm:`-prefixed structured failure on any other reader. Runs in
  CI per `.github/workflows/tests.yml`.

## Non-Functional Requirements

- **Skill startup latency:** p95 < 500ms on a developer laptop for
  the bash pre-flight (sourcing `yoke-prelude.sh`, `paths.sh`,
  `config-overrides.sh`, `wm_active_slug` resolution, PRD/fix-spec
  existence checks). Measured via the test harness's `time`
  wrapper.
- **Resolver latency:** p95 < 50ms for `wm_phase1_artifact_path`
  (two stat calls + branch). Measured via a unit benchmark in
  `tests/lib/`.
- **Disk footprint:** ≤ 1 MB per fix-spec under
  `.yoke/fixes/<slug>.md` (markdown body, no embedded binaries).
  Sensor asserts on each new fix-spec write.
- **Per-invocation walltime:** ≤ 30s for the happy-path draft on a
  4/4-readiness + 4/4-narrowness input (single dialogue turn,
  one Write call, post-draft self-check). Measured against
  `.yoke/runtime/progress.md` event-time lines.
- **Backward-compat surface:** 100% of existing PRD-backed tasks
  pass through the migrated downstream skills with no path errors.
  The acceptance-criteria document for this spec authors a
  regression suite of ≥ 5 representative PRD-backed scenarios.
- **CI runtime:** ≤ 2s added to the total CI test suite p95 wall
  time by the new sensor at
  `tests/sensors/no-direct-prd-path.test.sh`. Measured against
  `.github/workflows/tests.yml` baseline.

## Alternatives Considered

### Alt: PRD with `kind: fix` frontmatter (decision 1A from PRD Quick Round)

**Trade-off vs. chosen:** Zero downstream skill changes (`/yoke:tech-spec`
reads `wm_prd_path` unchanged) at the cost of overloading the PRD
artifact with two semantically distinct shapes — product-shaped and
engineering-shaped.
**Reason for rejection:** The user picked 1B at Quick Round time
(`.yoke/fixes/` separate path). Chosen path keeps the working-memory
schema honest — one directory per artifact shape, no
frontmatter-discriminated polymorphism.
**Source:** `concepts/yoke-pattern-memory-model`

### Alt: LLM-evaluated narrowness gate without `scope_caution:` frontmatter (option 3 of PRD OQ-1)

**Trade-off vs. chosen:** Simpler skill body (no frontmatter field
to write) at the cost of giving Phase-6 drift sensing nothing
structured to scan.
**Reason for rejection:** PRD OQ-1 resolution picked option 4
(hybrid graduated refusal) explicitly because it gives Phase-6 a
field to act on. Without `scope_caution:`, the only Phase-6 signal
is LLM judgment over fix-spec body — expensive and
non-deterministic.
**Source:** `concepts/yoke-pattern-sensors`

### Alt: Manufactured persona name "Diagnostic Engineer" for `/yoke:fix` (option b of PRD OQ-2)

**Trade-off vs. chosen:** Strict literal-naming uniqueness across
skills at the cost of inventing a role abstraction
("Diagnostic Engineer") that does not exist in
`yoke-pattern-roles`'s three-role taxonomy.
**Reason for rejection:** PRD OQ-2 resolution picked option (c)
two-tier (literal name uniform + Mode tag). Future engineering
skills inherit a clean convention without vocabulary sprawl per
the threat model in
`yoke-decision-2026-04-24-model-c-governance-contextual-authority-by-impact`.
**Source:** `concepts/yoke-pattern-roles`

### Alt: Soft-warning resolver when both Phase-1 archives exist (option β of PRD OQ-3)

**Trade-off vs. chosen:** Diagnostic surface (`/yoke:status`)
keeps working during a corruption event at the cost of letting the
wrong artifact drive Phase 2 silently.
**Reason for rejection:** Yoke's canonical pattern for archive
corruption is fail-loudly; defaulting to a warning trades
correctness for convenience and violates `yoke-pattern-sensors`'
structured-output rule. Resolved by PRD OQ-3 with option (δ) hard
abort + structured recovery.
**Source:** `concepts/yoke-pattern-sensors`

### Alt: Read-vs-write split in the resolver contract (option γ of PRD OQ-3)

**Trade-off vs. chosen:** Preserves diagnostic surface for
read-only callers at the cost of introducing a contract layer in
`lib/working-memory/paths.sh` (read-mode vs write-mode flag) that
does not exist anywhere else in the helper layer.
**Reason for rejection:** The split-contract precedent ripples to
every future caller of every helper — pure path computers do not
care whether they are called for read or write today, and the
resolver is the only existence-aware exception. Single uniform
abort is simpler to maintain and to reason about.
**Source:** `concepts/yoke-pattern-plugin-structure`

## Trade-offs

The chosen approach itself accepts these costs:

- **Diagnostic blackout during Phase-1 archive corruption.** The
  hard-abort resolver (FR-9 / option δ) blocks `/yoke:status` and
  any read-only caller until the user resolves the conflict. The
  cost is acceptable because the structured recovery diagnostic
  carries paths + first-100-bytes excerpts + commit shas + a
  remediation recipe; the user goes to git to investigate, not to
  `/yoke:status`.
- **Two literal personas with the same name.** `/yoke:fix` and
  `/yoke:tech-spec` both declare "Senior Engineer persona". The
  `**Mode:**` tag carries the disambiguation, which works only if
  every reader (human or council subagent) reads the body's first
  line. The cost is paid in convention discipline; the Phase-3
  acceptance-criteria document authors a sensor that asserts the
  Mode tag is present and well-formed.
- **Existence-aware exception in `paths.sh`.** The resolver is the
  only I/O-aware helper in the file. Future contributors may copy
  its shape by analogy and create new I/O-aware helpers without
  realising the exception status. The mitigation is the
  resolver's docstring, which states the contract does not
  propagate. The cost is documentation discipline.
- **Same-change scope expansion into `/yoke:tech-spec`.** The
  Mode-tag backfill (FR-2) is technically out of scope for a PRD
  primarily about `/yoke:fix`, but deferring it would leave
  `/yoke:tech-spec` without its disambiguator and the OQ-2
  resolution incomplete. The cost is a slightly larger blast
  radius for this single change.

## Cross-cutting Concerns

- **Observability:** the skill emits `wm:`-prefixed structured
  diagnostics on every abort path (pre-flight failure, FR-9
  resolver abort, FR-9a `wm_set_active` abort, narrowness-gate
  abort). The runtime captures dialogue rounds in
  `.yoke/runtime/progress.md` per the existing skill convention;
  no new logging surface.
- **Security:** no PII handled. No network calls. Internal tooling
  for Yoke users.
- **Error handling:** every failure surfaces a `wm:`-prefixed
  diagnostic carrying violation identification + location +
  correction instruction per `yoke-pattern-sensors`. Failures do
  not silently degrade — every abort path returns non-zero.
- **i18n / a11y:** n/a — internal tooling. The dialogue follows the
  user's session language per the shared approval menu's
  `language:` input contract.
- **Backward compatibility:** zero breakage for existing
  PRD-backed tasks. The migration of five downstream skills to
  `wm_phase1_artifact_path` is the load-bearing change; the
  acceptance-criteria document for this spec authors a regression
  suite that runs the existing PRD flow end-to-end.

### FR-5 — Clarity-driven dialogue (4/4 readiness checks)

**Components involved:** `skills/fix/SKILL.md` (persona body).

**NFRs applied:** Token cost.
**Edge cases:** user provides 4/4 ready input on first turn → skip
to draft; user provides 0/4 ready input → ask all four; safety

### FR-6 — Narrowness gate (graduated refusal) and FR-6a `scope_caution:` field

**Components involved:** `skills/fix/SKILL.md` (persona body),

acceptance-criteria document for this spec.
**Contracts used:** `scope_caution:` frontmatter field; four-proxy
evaluation embedded in persona body.
**NFRs applied:** Token cost; backward-compat surface (the gate
must not regress `/yoke:discover`'s flow).
**Edge cases:** 4/4 narrowness pass → silent draft; 3/4 →
`scope_caution: <proxy-id>` written into frontmatter; ≤ 2/4 →
abort with re-route prompt; mid-dialogue scope inflation → re-run
proxies on accumulated answers, abort if threshold trips.

### FR-7 — Fix-spec template at `templates/fix.md`

**Components involved:** `templates/fix.md` (new file).
**Contracts used:** Section ordering matches PRD FR-7's list;

**NFRs applied:** Disk footprint.
**Edge cases:** template drift between sections list in
`templates/fix.md` and skill body's draft logic → covered by

### FR-8 — Trigger 1 via shared approval menu

**Components involved:** `skills/fix/SKILL.md`,

### FR-9 — `wm_phase1_artifact_path` resolver with hard-abort + structured recovery
