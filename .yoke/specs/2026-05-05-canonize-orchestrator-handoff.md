## Context and Scope

The v2.0.0 facade extraction (`2026-04-30-pluggable-canonical-memory`)
reshaped `/yoke:canonize` into a zero-argument verb that resolves the
active slug from `.yoke/runtime/.current` and the active provider
from `.yoke/config.yaml :: canonical_memory.provider`. Per
`skills/canonize/SKILL.md:71-82`, any non-empty `$ARGUMENTS` aborts
with `wm: /yoke:canonize takes no arguments at v2.0.0`. The v3.0.0
council cutover (`2026-05-01-agent-council`) reshaped the
Orchestrator into canonize-only mode but inherited the v1.x handoff
prose at `agents/orchestrator.md:73-78` and `skills/implement/SKILL.md:486-490`,
both of which still instruct the subagent to invoke `/yoke:canonize`
"with `--from-orchestrator`" plus the active task's
`.yoke/<task-slug>/` directory path. The two contracts cannot
co-exist; every full-run termination handoff that reaches the
documented Orchestrator path aborts on entry to `/yoke:canonize`.

**In scope.** Prose-only changes to `agents/orchestrator.md` and
`skills/implement/SKILL.md` to drop the retired flag and the
directory-path argument; one new computational sensor at
`.yoke/sensors/tests-orchestrator-canonize-handoff.md` plus its backing smoke-test script at
`tests/smoke/orchestrator-canonize-handoff.test.sh`; one canonical-memory doctrine entry
authored at `/yoke:canonize` time recording the contract decision
(supersedes any historical reference to the v1.x
`/yoke:preserve --from-orchestrator` shape).

**Out of scope.** Any modification to `skills/canonize/SKILL.md`
(the v2.0.0 zero-argument facade is the contract authority; it
remains untouched). Any new positional argument, env var, or
wrapper subskill introducing a caller-identity discriminator.
Migration of pre-v2.0.0 historical references in canonical memory
older than the new doctrine entry.

## Goals and Non-Goals

**Goals**

- The three surfaces (`agents/orchestrator.md`,
  `skills/implement/SKILL.md`, `skills/canonize/SKILL.md`) document
  the canonize-invocation contract identically: zero-argument,
  caller-agnostic, slug from `.yoke/runtime/.current`.
- The documented Orchestrator → `/yoke:canonize` path completes the
  five-criterion cascade end-to-end on `merge-ready` without
  tripping the v2.0.0 hard-rejection guard.
- Manual `/yoke:canonize` invocations continue to work end-to-end
  unchanged.
- A computational sensor at `.yoke/sensors/tests-orchestrator-canonize-handoff.md` with a valid
  `command:` field exercises the regression path and fails closed
  on re-introduction of the retired flag.
- The Model C governance pattern entry in canonical memory is
  superseded with bidirectional supersession links to the new
  doctrine entry.

**Non-Goals**

- Reshaping the v2.0.0 facade contract beyond what FR-1 through
  FR-7 require.
- Adding any caller-identity discriminator (positional argument,
  flag, env var, or wrapper subskill).
- Migrating manual `/yoke:preserve --from-orchestrator` references
  in canonical-memory entities authored before the new doctrine
  entry; these are historical and out of scope.
- Changing the Model C impact-classification cascade in
  `lib/canonical-memory/canonization-criteria.sh`. Routing remains
  diff-driven, not caller-driven.
- Changing slug-resolution semantics. `.yoke/runtime/.current`
  remains the single source of active-slug truth.

## System Context

The fix touches three plugin-side surfaces and adds two new files;
the canonize skill itself stays inert. Data flow at full-run
termination:

```
/yoke:implement (coordinator)
   │  exit reason = merge-ready
   ▼
agents/orchestrator.md  (mode = canonize, spawned via Task)
   │  Skill(skill: "/yoke:canonize")          ← updated prose: zero arguments
   ▼
skills/canonize/SKILL.md  (untouched; v2.0.0 contract)
   │  resolves slug from .yoke/runtime/.current
   │  resolves provider from .yoke/config.yaml :: canonical_memory.provider
   │  applies five-criterion cascade
   ▼
provider canonize verb (e.g. /bedrock:teach)
   │  classifies impact under Model C
   ▼
canonical-memory PR (auto-apply | notify-and-apply | synchronous)
```

Cite `concepts/yoke-pattern-roles` for the canonize-only Orchestrator
authority class and `concepts/yoke-pattern-facade-vs-provider-verbs`
for the zero-argument facade contract.

The new sensor `.yoke/sensors/tests-orchestrator-canonize-handoff.md` is read at `/yoke:implement`
spawn time by `lib/sensors/ack-sensors.sh --mode readiness`; its

## Architecture

The chosen architecture is **prose alignment of consumer surfaces
plus a deterministic computational sensor**, inheriting from
`concepts/yoke-pattern-facade-vs-provider-verbs` (zero-argument
facade as contract authority) and `concepts/yoke-pattern-sensors`
(computational sensor with `command:` shell invocation, backed by
a smoke-test script). The architecture treats `skills/canonize/SKILL.md`
as the **single contract authority** for the canonize-invocation
shape; all other surfaces are consumers that converge to it under
future migrations.

Invariants the architecture guarantees:

- **Single contract authority.** The zero-argument shape is defined
  in exactly one place (`skills/canonize/SKILL.md:71-82`); the
  Orchestrator and implement prose cite it rather than restating
  it, so a future migration that touches the contract updates one
  file and the consumers automatically follow.
- **Caller-agnostic dispatch.** The canonize skill cannot
  distinguish Orchestrator-driven from manual invocations.
  Consequently, no caller-identity-routed code path can exist on
  the canonize side; Model C lane selection is derived from the
  staged diff via the five-criterion cascade in
  `lib/canonical-memory/canonization-criteria.sh`.
- **Sensor-gated readiness.** The new sensor is enumerated by
  `lib/sensors/ack-sensors.sh --mode readiness`; any future
  reintroduction of the retired flag causes the smoke test to fail
  and `/yoke:implement` to refuse spawn.

Failure modes the architecture explicitly does not handle:

- A future migration that re-derives caller-identity routing from
  somewhere other than the canonize-invocation contract (e.g. by
  reading `progress.md` to infer Orchestrator presence). Out of
  scope; surface as an open question for the next migration.

- **Regression coverage:** ≥ 99.9% of full-run termination handoffs

## Alternatives Considered

### Alt: Argument-as-flag (`/yoke:canonize --from-orchestrator`)

**Trade-off vs. chosen:** the discriminator is visible at the
invocation site (the Orchestrator's Skill-tool call shows the flag
immediately), at the cost of partially walking back the v2.0.0
zero-argument facade decision — the verb is no longer purely
zero-argument.
**Reason for rejection:** the v2.0.0 facade-shape decision was
ratified end-to-end on 2026-04-30 (`concepts/provider-agnostic-verbs-yokesearch-canonical-memory-yokecanonize`)
specifically to remove caller-identity coupling from the canonize
verb; reopening that contract for a single caller is a regression
in coherence, and the prose-only path achieves the same Model C
outcome with smaller surface area.
**Source:** `concepts/yoke-pattern-facade-vs-provider-verbs`

### Alt: Env-var discriminator (`YOKE_FROM_ORCHESTRATOR=1`)

**Trade-off vs. chosen:** preserves the v2.0.0 zero-argument shape
exactly, at the cost of an invisible discriminator at the call site
(readers of `agents/orchestrator.md` cannot tell the canonize skill
is being routed differently) and a leakage risk if the env var is
ever exported in a developer's shell profile.
**Reason for rejection:** the env-var leak risk is real and
asymmetric — a manual `/yoke:canonize` running under
`YOKE_FROM_ORCHESTRATOR=1` would silently classify writes under
Model C's auto-apply lane intended for Orchestrator runs, violating
the Model C invariant that the Orchestrator is the only writer
under that lane. Mitigations (inline-export, scope-bound) add
complexity without solving the underlying coupling.
**Source:** internal experience

### Alt: Wrapper subskill (`/yoke:canonize-from-orchestrator`)

**Trade-off vs. chosen:** keeps both surfaces clean (facade stays
zero-argument; wrapper carries Orchestrator routing) at the cost of
one more public skill verb on the platform and one more contract to
keep coherent under future migrations.
**Reason for rejection:** the underlying routing decision (Model C
lane selection) belongs to the diff-classification cascade in
`lib/canonical-memory/canonization-criteria.sh`, not to caller
identity; a wrapper that adds a discriminator is solving the wrong
problem. The prose-only alignment removes the caller-coupling
entirely and makes the canonize skill genuinely caller-agnostic.
**Source:** `concepts/yoke-pattern-roles`

## Trade-offs

The chosen approach (prose-only alignment + caller-agnostic
canonize) accepts:

- **Loss of caller-aware Model C routing.** The Orchestrator can no
  longer short-circuit a Model C lane (e.g. auto-apply for `low`
  impact) via caller identity. All routing flows through the
  five-criterion cascade. This forces every Orchestrator-driven
  write to be classified by diff content, which is slightly more
  conservative but removes the coupling between caller identity and
  governance lane.
- **Reliance on prose discipline + sensor coverage.** The contract
  authority is a single skill body (`skills/canonize/SKILL.md`); the
  consumer surfaces converge to it but their convergence is enforced
  only by FR-7's regression sensor and FR-6's doctrine entry. A
  future PR that re-introduces the retired flag must trip the
  sensor; if the sensor is not load-bearing, drift recurs.
- **No new runtime API.** The fix introduces no observability hook
  for "Orchestrator-driven canonize completed successfully" beyond
  what `progress.md` already records. Phase 4 termination success
  remains inferred from the existing termination-reason logging.

## Cross-cutting Concerns

## Technical Use Cases

### FR-1 — Three surfaces document the same canonize-invocation contract

**Components involved:** `agents/orchestrator.md`, `skills/implement/SKILL.md`, `skills/canonize/SKILL.md` (read-only reference).
**Contracts used:** canonize-invocation contract (zero-argument shape).
**NFRs applied:** Disk footprint, Documentation drift response time.
**Edge cases:** prose deltas must drop both the directory-path argument and the `--from-orchestrator` flag in the same edit (partial migration leaves the contract still incoherent); citation links to `skills/canonize/SKILL.md` must use stable section anchors (`### Pre-flight` / `### Phase 0`) rather than line numbers (line drift across migrations).

### FR-2 — Orchestrator-driven `/yoke:canonize` completes without v2.0.0 abort

**Components involved:** `agents/orchestrator.md`, `skills/implement/SKILL.md`, `agents/orchestrator.md` (mode=canonize), `skills/canonize/SKILL.md` (read-only).
**Contracts used:** canonize-invocation contract; Skill-tool dispatch.
**NFRs applied:** Sensor latency, Regression coverage.
**Edge cases:** `/yoke:implement` reaching `merge-ready` with an empty `.yoke/runtime/.current` (canonize aborts with the existing slug-resolution diagnostic; not the v2.0.0 argument-rejection diagnostic — separate failure mode); `/yoke:canonize` invoked when `.yoke/config.yaml :: canonical_memory.provider` is unset (separate hard-break path; out of scope for this fix).

### FR-3 — Manual `/yoke:canonize` continues unchanged

**Components involved:** `skills/canonize/SKILL.md` (untouched).
**Contracts used:** canonize-invocation contract; manual user invocation.
**NFRs applied:** LLM-dispatch overhead (0% at runtime).
**Edge cases:** developer invocation with stale `.yoke/runtime/.current` from a prior task (canonize uses the stale slug; covered by the existing slug-clearing discipline at task boundaries — no new edge case introduced).

### FR-4 — Active slug from `.yoke/runtime/.current`

**Components involved:** `lib/working-memory/paths.sh::wm_active_slug`, `skills/canonize/SKILL.md` Phase 0.
**Contracts used:** active-slug invariant; working-memory path helpers.
**NFRs applied:** none directly (this FR is a contract pin, not a perf concern).
**Edge cases:** missing `.current` file → existing canonize diagnostic surfaces unchanged; the fix does not introduce a new slug-resolution path.

### FR-5 — No caller-identity discriminator

**Components involved:** `skills/canonize/SKILL.md` (untouched), `agents/orchestrator.md` (no env-var setting), `skills/implement/SKILL.md` (no flag passing).
**Contracts used:** caller-agnostic canonize contract; Model C diff-driven classification.
**NFRs applied:** Documentation drift response time.
**Edge cases:** future PR introducing a discriminator (env var, positional arg, or wrapper) trips FR-7's sensor; doctrine entry from FR-6 records this as the binding decision so reviewers have a citation.

### FR-6 — Doctrine entry in canonical memory with bidirectional supersession

**Components involved:** canonical memory (concept entry authored via `/yoke:canonize` post-implementation), `concepts/yoke-pattern-model-c-governance` (superseded section).

**NFRs applied:** none directly (canonization-time work, not runtime).
**Edge cases:** existing `concepts/yoke-pattern-model-c-governance` body sections that cite `/yoke:preserve --from-orchestrator` must receive a supersedes-link block pointing at the new entry; the new entry must reciprocate. `/yoke:canonize` runs after implementation; this spec records the requirement, the canonize skill executes it.
