## Sprint objective

Land the breaking change — Yoke v2.0.0 — by enforcing migration,
deleting the legacy artifacts left behind by Sprint 2, rewriting
documentation and templates, and bumping the plugin version. By
sprint end, a user upgrading from v1.1.x runs `/yoke:bootstrap` once
to migrate `.yoke/config.yaml` (no silent default), every legacy
canonical-memory artifact is gone from `claude-yoke`, every
user-facing doc and template references the facade verbs, and
`.claude-plugin/plugin.json` reports `2.0.0`. A user running a fresh
`/yoke:bootstrap` against a project with `claude-bedrock` installed
completes setup interactively and proceeds straight into
`/yoke:discover`.

## Tasks

### Task 2026-04-30-pluggable-canonical-memory-s03-t01

**Story:** `/yoke:bootstrap` is the single entry point a user runs
against any project to set up Yoke. After v2.0.0 it is also the only
path through which `canonical_memory.provider` lands in
`.yoke/config.yaml`. Two flows must be covered: a fresh bootstrap
where the user picks a provider; and a migration bootstrap on a
pre-v2.0.0 project where Yoke detects the legacy state and rewrites
to the new schema.

**Technical implementation:** Rewrite `skills/bootstrap/SKILL.md`
end-to-end. Argument parsing: `--provider <name>` non-interactive
override (must match a key in `<plugin_dir>/providers.yaml`);
`--non-interactive` flag (requires `--provider`). Pre-flight sources
`lib/working-memory/paths.sh` and
`lib/canonical-memory/resolve-provider.sh` (for validation only —
bootstrap itself does NOT source `yoke_require_provider` from
s03-t02). Flow A — legacy detection: compute markers
`legacy_registry` (`<plugin_dir>/memories.json` exists) and
`legacy_config` (`.yoke/config.yaml` exists but lacks the
`canonical_memory.provider` key). On either being true, print
`wm: legacy Yoke v1.x state detected. Migrating to v2.0.0 schema.`,
read existing memory entry (`url`, `name`, `default_branch`),
default the migrated provider to `bedrock` (only viable v1.x option
— abort if `--provider` was given with a different value), confirm
interactively (skipped under `--non-interactive`), write the new
`.yoke/config.yaml` from `templates/yoke-config.yaml` with
`provider: bedrock` plus captured passthrough keys, remove
`<plugin_dir>/memories.json` after final confirmation. Flow B —
fresh bootstrap: list available providers from `providers.yaml`
(default to the only entry under `--non-interactive`); validate
selection; warn if `requires.plugin` is set and not installed;
prompt for `config_passthrough` keys; write `.yoke/config.yaml`
plus `.yoke/runtime/`, `.yoke/.gitignore`. Critical rules: never
proceed silently; never delete `memories.json` without explicit
confirmation; never overwrite an existing v2.0.0 config without
surfacing as `re-bootstrap?`.

**Validation:** Five tests under `tests/smoke/` —
(a) fresh-bootstrap with `--provider bedrock --non-interactive`
produces `.yoke/config.yaml` with the provider key;
(b) legacy-config migration preserves `url`/`name` and writes the
new provider key; (c) legacy-registry migration removes
`memories.json` and migrates the config; (d) multi-provider listing
test confirms the prompt offers both entries when `providers.yaml`
has two; (e) re-bootstrap-existing-config-no-op test asserts no
file is touched on `n` reply.

**Acceptance criterion:** Running `/yoke:bootstrap --provider bedrock --non-interactive` against a fresh fixture project produces `.yoke/config.yaml` with `canonical_memory.provider: bedrock`, AND running the same command against a fixture with pre-existing `<plugin_dir>/memories.json` results in `memories.json` being deleted and `.yoke/config.yaml` being created with `canonical_memory.provider: bedrock` plus the legacy `url`/`name`/`default_branch` preserved as passthrough.

### Task 2026-04-30-pluggable-canonical-memory-s03-t02

**Story:** The PRD invariant says: "Backward compatibility for
in-flight tasks is not promised. Existing projects that ran prior
Yoke versions must explicitly migrate via `/yoke:bootstrap` re-run
before any other Yoke skill works again. Hard break is preferable
to silent default." This task implements that hard break via a
single shared bash helper sourced by every Yoke skill.

**Technical implementation:** Create `lib/yoke-prelude.sh`
(top-level under `lib/`, not nested inside `canonical-memory/`,
because the helper applies to *every* Yoke skill). Export
`yoke_require_provider` as a shell function. The function reads
`.yoke/config.yaml`, parses `canonical_memory.provider` via `yq -r
'.canonical_memory.provider // ""'`, and aborts non-zero with one
of two stderr messages: `wm: <config_path> not found. Run
/yoke:bootstrap to initialize this project.` (file missing) or
`wm: canonical_memory.provider not configured. Run /yoke:bootstrap
to migrate.` (file present but key missing/empty). Idempotent and
side-effect-free apart from stderr and return code. Add the source
line `source "<plugin_dir>/lib/yoke-prelude.sh" && yoke_require_provider
|| exit 1` near the top of every eligible skill's pre-flight
section: `discover`, `tech-spec`, `acceptance-contract`,
`implement`, `search-canonical-memory`, `canonize`, `drift-sense`,
`status`, `ack-sensors`. Skills that explicitly do NOT source the
helper: `bootstrap` (migration entry point), and the seven legacy
skills scheduled for deletion in s03-t03. The placement matches
the existing source-pattern for `paths.sh`.

**Validation:** Four layers —
(a) helper unit test in `tests/canonical-memory/yoke-prelude.test.sh`
(happy / missing-file / missing-key / empty-value cases);
(b) source-line presence audit greps each eligible skill for the
helper invocation;
(c) end-to-end abort test invokes `/yoke:search-canonical-memory
"test"` against a fixture lacking the key and asserts the expected
stderr;
(d) end-to-end happy-path test invokes the same command after a
successful `/yoke:bootstrap`.

**Acceptance criterion:** Running `/yoke:search-canonical-memory "test"` against a fixture project whose `.yoke/config.yaml` lacks `canonical_memory.provider` exits non-zero with stderr containing the literal string `wm: canonical_memory.provider not configured. Run /yoke:bootstrap to migrate.`, AND every Yoke skill except `bootstrap` and the seven legacy skills sources `lib/yoke-prelude.sh` and calls `yoke_require_provider` in its pre-flight (verified by audit grep).

### Task 2026-04-30-pluggable-canonical-memory-s03-t03

**Story:** After Sprint 2 the legacy skill files and the
Bedrock-specific library, entity, and template artifacts live in
two places: in `claude-yoke` (unmodified, inactive) and in
`claude-bedrock` (active, in use). This task removes the duplicates
from `claude-yoke`. After it lands, `claude-yoke` is structurally
lean and provider-agnostic.

**Technical implementation:** Delete via `git rm` (with `-r` for
directories) to keep version-control history clean. Skills:
`git rm -r claude-yoke/skills/{ask,preserve,teach,compress,memory,confluence-to-markdown,gdoc-to-markdown}`.
lib scripts: `git rm` the eight files in
`claude-yoke/lib/canonical-memory/` other than `resolve-provider.sh`
(which stays). Entities and canonical templates:
`git rm -r claude-yoke/{entities,templates/canonical}`,
`git rm claude-yoke/templates/{canonical-entry-frontmatter.yaml,yoke-memory-config.json}`.
Update `lib/sensors/no-vibeflow-refs.sh` allowlist: remove
`entities/` and `templates/canonical/` from "expected" lists; add a
"must-not-reappear" rule that fails if either reappears in
`claude-yoke/`. Update
`tests/sensors/no-vibeflow-refs.test.sh` with a fixture that
injects `claude-yoke/entities/foo.md` and asserts the sensor fails
with the migration-pin message. Cross-sprint ordering: this task
runs only after s02-t05 has flipped every live call-site —
otherwise deletion would break runtime callers.

**Validation:** Five layers — (a) seven legacy skill directories
absent under `claude-yoke/skills/`; (b)
`claude-yoke/lib/canonical-memory/` contains exactly
`resolve-provider.sh`; (c) `entities/`, `templates/canonical/`, and
the two specific template files absent; (d) `bash
lib/sensors/no-vibeflow-refs.sh` exits 0 on the cleaned tree;
(e) the updated sensor test asserts the sensor fails on
re-introduction.

**Acceptance criterion:** `for s in ask preserve teach compress memory confluence-to-markdown gdoc-to-markdown; do [ ! -d "claude-yoke/skills/$s" ] || exit 1; done && [ "$(ls claude-yoke/lib/canonical-memory/)" = "resolve-provider.sh" ] && [ ! -d claude-yoke/entities ] && [ ! -d claude-yoke/templates/canonical ] && bash claude-yoke/lib/sensors/no-vibeflow-refs.sh` evaluates true and exits 0.

### Task 2026-04-30-pluggable-canonical-memory-s03-t05

**Story:** Templates `/yoke:bootstrap` copies into a host project
and templates referenced in spec-phase skills also reference legacy
verbs and a v1.x config shape, and the plugin manifest still says
`1.1.0`. The version bump to `2.0.0` signals the breaking change.
A new migration runbook gives users a single complete set of
instructions to upgrade.

**Technical implementation:** Six artifacts. (1)
`templates/acceptance-contract.md`: replace every `/yoke:ask` with
`/yoke:search-canonical-memory` and every `/yoke:preserve` with
`/yoke:canonize`. (2) `templates/task.md`: same swap, plus update
the canonization-seed comment block to reference the facade verb.
(3) `templates/project-claude-md.md` (the CLAUDE.md template
`/yoke:bootstrap` copies into a host project): swap legacy verbs for
facade verbs; update install-prereq and querying-canonical-memory
example sections. (4) `templates/yoke-config.yaml`: remove the
legacy `name:` field (registry concept retired); keep `url:` and
`default_branch:` as commented-passthrough documentation; add a top
comment stating `canonical_memory.provider` is required at v2.0.0
and pointing at `providers.yaml`. (5) `.claude-plugin/plugin.json`:
`"version": "1.1.0"` → `"version": "2.0.0"`; update `description`
to mention pluggable canonical-memory providers; refresh `keywords`
to add `pluggable-providers` and `canonical-memory-provider`. (6)
`docs/migration-v1-to-v2.md` (NEW): runbook covering *What changed*,
*Pre-upgrade checklist*, *Step 1: install `claude-bedrock`*,
*Step 2: upgrade Yoke*, *Step 3: re-bootstrap each project*,
*Step 4: verify*, *Common errors*, *Rollback*. Cross-reference from
the CHANGELOG v2.0.0 entry (s03-t04) and from
`docs/canonical-memory-setup.md`.

**Validation:** Five layers — (a) template stale-reference sweep
returns no lines under `claude-yoke/templates/`; (b) each modified
template contains at least one reference to a facade verb; (c)
`jq -re '.version' .claude-plugin/plugin.json` outputs `2.0.0`;
(d) `jq -re '.description'` contains the substring `pluggable
canonical-memory`; (e) migration runbook exists and contains the
`## Step 1: install` heading.

**Acceptance criterion:** `jq -re '.version' claude-yoke/.claude-plugin/plugin.json` outputs `2.0.0` AND `grep -rln '/yoke:ask\|/yoke:preserve\|/yoke:teach\|/yoke:compress\|/yoke:memory' claude-yoke/templates/` returns no lines AND `[ -f claude-yoke/docs/migration-v1-to-v2.md ]` evaluates true.
