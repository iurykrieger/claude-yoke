## Sprint objective

Extract the Bedrock-specific implementation out of Yoke into a
standalone peer plugin (`claude-bedrock`) and switch every Yoke
internal call-site to the new facade verbs. By sprint end, a user
running Yoke + the `claude-bedrock` plugin together completes a full
`/yoke:implement` cycle whose canonical-memory operations dispatch
through `/yoke:search-canonical-memory` and `/yoke:canonize` into
`/bedrock:ask` and `/bedrock:canonize`. The seven legacy skill
directories remain present in the Yoke source as inactive duplicates
— their deletion is Sprint 3 — so this sprint stays reversible
without forfeiting end-to-end coverage.

### Task 2026-04-30-pluggable-canonical-memory-s02-t01

**Story:** Before any skill, library, or template can move out of
Yoke into the new Bedrock peer plugin, the destination plugin must
exist with a valid manifest and directory shape. This task creates
that empty container so subsequent moves have somewhere to land,
keeping the diff for "create plugin shell" surgical.

**Technical implementation:** Create `claude-bedrock/` as a sibling
of `claude-yoke/` (in the developer's workspace; for v0 a sibling is
acceptable, marketplace listing deferred). Author
`.claude-plugin/plugin.json` with `name: claude-bedrock`, `version:
0.1.0`, `description: "Markdown frontmatter graph canonical memory
for Claude Code (Yoke-compatible provider)."`, `author`,
`repository: https://github.com/iurykrieger/claude-bedrock`,
`license: MIT`, `category: ai-development`, `keywords: [canonical-memory,
knowledge-graph, yoke-provider, second-brain, zettelkasten]`. Author
minimal `.claude-plugin/marketplace.json`. Copy `LICENSE` from Yoke
(MIT). Author `README.md` placeholder identifying the plugin as the
Yoke reference canonical-memory provider, citing the working-memory
contract document at `contract_version: 1`. Author `CHANGELOG.md`
with the initial-scaffold entry. Create empty subdirectories
(`skills/`, `lib/canonical-memory/`, `entities/`,
`templates/canonical/`, `templates/`, `docs/`, `tests/`) using
`.gitkeep`. Author minimal `.gitignore` mirroring Yoke's exclusions.
Initialize the git repository with the initial-scaffold commit. The
plugin obeys the same plugin-shape invariants Yoke does per
`concepts/yoke-pattern-plugin-structure`.

**Validation:** Three smoke checks: (a) `jq -e '.name == "claude-bedrock"
and .version == "0.1.0" and .license == "MIT"' claude-bedrock/.claude-plugin/plugin.json`;
(b) every required subdirectory exists; (c) governance files
(`LICENSE`, `README.md`, `CHANGELOG.md`) exist. No Claude Code
install integration test in this task — that lands at sprint end
once the plugin is populated.

**Acceptance criterion:** `jq -re '.name' claude-bedrock/.claude-plugin/plugin.json` outputs `claude-bedrock` AND every directory in the list `skills lib/canonical-memory entities templates/canonical docs tests` exists under `claude-bedrock/`.

### Task 2026-04-30-pluggable-canonical-memory-s02-t02

**Story:** Seven skills currently embedded in Yoke (`ask`,
`preserve`, `teach`, `compress`, `memory`, `confluence-to-markdown`,
`gdoc-to-markdown`) are Bedrock-specific. They were forked at
v0.1.0 per
`yoke-decision-2026-04-24-embed-upstream-skills-as-a-single-fork-at-creation`,
and that decision is what this PRD revokes. This task copies the
seven skills into `claude-bedrock` under the `/bedrock:` namespace
and rewrites internal cross-skill invocations.

**Technical implementation:** Copy the seven skill directories
(NOT git-mv — keep duplicates in Yoke through Sprint 2 to preserve
reversibility). In each copy under `claude-bedrock/skills/`, rewrite
every cross-skill reference from the `/yoke:` namespace to the
`/bedrock:` namespace: `/yoke:ask → /bedrock:ask`,
`/yoke:preserve → /bedrock:preserve`, `/yoke:teach → /bedrock:teach`,
`/yoke:compress → /bedrock:compress`, `/yoke:memory → /bedrock:memory`,
`/yoke:confluence-to-markdown → /bedrock:confluence-to-markdown`,
`/yoke:gdoc-to-markdown → /bedrock:gdoc-to-markdown`. References
to facade verbs introduced in Sprint 1 (`/yoke:search-canonical-memory`,
`/yoke:canonize`) are NOT rewritten — Bedrock is upstream of those
facades. References to `<plugin_dir>/entities/` and
`<plugin_dir>/templates/canonical/` and `lib/canonical-memory/`
inside the copies are correct as-is once s02-t03 fills the destination
plugin's directories. Update each skill's `name:` frontmatter to
the canonical Claude Code skill name without the plugin prefix.

**Validation:** Three layers — (a) `claude-bedrock/skills/` contains
exactly seven directories matching the migrated names, each with a
`SKILL.md`; (b) `grep -rln "/yoke:ask\|/yoke:preserve\|/yoke:teach\|/yoke:compress\|/yoke:memory\|/yoke:confluence-to-markdown\|/yoke:gdoc-to-markdown" claude-bedrock/skills/`
returns empty; (c) `grep -rln "/bedrock:ask\|/bedrock:preserve\|/bedrock:teach\|/bedrock:compress\|/bedrock:memory" claude-bedrock/skills/`
returns ≥ 1 path. The Yoke side is NOT modified by this task; an
inventory check on `claude-yoke/skills/` still shows the seven
legacy directories present.

**Acceptance criterion:** `grep -rln "/yoke:ask\|/yoke:preserve\|/yoke:teach\|/yoke:compress\|/yoke:memory\|/yoke:confluence-to-markdown\|/yoke:gdoc-to-markdown" claude-bedrock/skills/` returns empty AND `[ "$(ls -d claude-bedrock/skills/*/ | wc -l)" -eq 7 ]` evaluates true.

### Task 2026-04-30-pluggable-canonical-memory-s02-t03

**Story:** The seven Bedrock skills migrated in s02-t02 depend on
supporting library scripts (graph manipulation, registry access,
canonization criteria, scaffolding helpers, semantic-overlap
rewrites, trace analysis, promoted-concept writers) and on
entity-type definitions plus per-type templates that encode the
Bedrock entity model. All of those artifacts are Bedrock-specific by
construction. This task moves them to the destination where the
migrated skills already point.

**Technical implementation:** Three source-set migrations performed
by copying (not deleting on the Yoke side; deletions land in
Sprint 3): (1) eight scripts from `claude-yoke/lib/canonical-memory/`
to `claude-bedrock/lib/canonical-memory/` —
`canonization-criteria.sh`, `graph.sh`, `registry.sh`,
`resolve-memory.sh`, `scaffold-memory.sh`,
`semantic-overlap-rewrite.sh`, `trace-analyzer.sh`,

in Yoke. (2) Eight entity definitions from `claude-yoke/entities/`

**Validation:** Four layers — (a) inventory parity: 8 scripts in

### Task 2026-04-30-pluggable-canonical-memory-s02-t04

**Story:** Bedrock's existing skills cover external-source ingestion
(`/bedrock:teach <url>`) and entity-write (`/bedrock:preserve`),
but neither reads `.yoke/` working memory directly. This task adds
a new dedicated `/bedrock:canonize` skill that consumes `.yoke/`
per the contract written in Sprint 1 Task 5 and produces
canonical-memory writes. With this skill in place, the `bedrock`
entry in `providers.yaml` is repointed to the new `/bedrock:`
namespace, completing the dispatch loop.

**Technical implementation:** Create `claude-bedrock/skills/canonize/SKILL.md`.
Frontmatter `name: canonize`, description identifying it as "the
Yoke-compatible canonize entrypoint for the Bedrock provider."
Mandatory argument: `--working-memory <path>`. Pre-flight sources
the migrated `lib/canonical-memory/resolve-memory.sh` to identify
the active Bedrock vault for the *provider*; verifies
`<path>/config.yaml` is readable; reads `<path>/runtime/.current`
gracefully (file may be absent). Body: for each task slug in scope,
read working-memory artifacts per the contract; apply the migrated
`canonization-criteria.sh` to identify candidates (project actor
updates, new concepts, decisions, refined patterns, audit reports);
invoke `write-promoted-concept.sh` per surviving candidate (Model C
governed); print a single-line exit summary `canonize:
created=<N> updated=<M> skipped=<K>`. Critical rules: never write
to `<path>/.yoke/`; never bypass Model C; never invent canonization
criteria beyond the migrated v1.x policy. Update
`claude-yoke/providers.yaml` `bedrock` entry: `requires.plugin:
claude-bedrock`, `requires.min_version: "0.1.0"`, `skills.search:
"bedrock:ask"`, `skills.canonize: "bedrock:canonize"`.

**Validation:** Four layers — (a) skill file present; (b)
provider-table integrity: `yq -r '.providers.bedrock.skills.search,
.providers.bedrock.skills.canonize, .providers.bedrock.requires.plugin'
claude-yoke/providers.yaml` outputs `bedrock:ask`, `bedrock:canonize`,
`claude-bedrock` in order; (c) end-to-end fixture test invokes
`/yoke:canonize` from a fixture project and asserts the dispatch
chain reaches `/bedrock:canonize`, the Bedrock vault grows by ≥ 1
entity, and stdout matches the soft exit-summary regex; (d) negative
test asserts `/bedrock:canonize` without `--working-memory` exits
non-zero.

**Acceptance criterion:** Running the end-to-end smoke fixture results in `/bedrock:canonize` invoked with an absolute path, ≥ 1 new entity under the fixture Bedrock vault, and the dispatch chain exits 0 with a stdout line matching `^canonize: created=[0-9]+ updated=[0-9]+ skipped=[0-9]+$`.

### Task 2026-04-30-pluggable-canonical-memory-s02-t05

**Story:** After Sprint 1 the facades exist; after s02-t01 through
s02-t04 the Bedrock plugin can answer them. But Yoke's runtime —
agent prompts, spec-phase skills, `/yoke:implement`, sensors that
emit warnings citing skill names, and the test surface — still
mentions the legacy verbs directly. This task is the bulk text-rewrite
that switches those call-sites. After this task, every live Yoke
artifact that consults canonical memory does so through
`/yoke:search-canonical-memory`, and every artifact that writes does
so through `/yoke:canonize`.

**Technical implementation:** Five surface areas: (1) Agent prompts
under `agents/` (`generator.md`, `validator.md`, `orchestrator.md`,
`semantic-judge.md`) — replace `/yoke:ask` with
`/yoke:search-canonical-memory` and `/yoke:preserve` with
`/yoke:canonize`; remove references to other legacy verbs. The
Orchestrator subagent's canonize-mode behavior is preserved — what
changes is the verb it invokes. (2) Spec-phase skills — replace
`/yoke:ask` references in `skills/discover`, `skills/tech-spec`,
`skills/acceptance-contract`, `skills/implement`. Update
`/yoke:implement`'s loop terminator to invoke `/yoke:canonize`
directly via the `Skill` tool (the facade does the resolver lookup
and dispatches to `/bedrock:canonize`). (3) Other skills that touch
canonical memory (`skills/bootstrap`, `skills/drift-sense`,
`skills/status`) — swap legacy verbs for facade verbs without
changing workflow logic. (4) Sensors and `lib/`
(`lib/sensors/contract-promotion-bidirectional.sh`,
`lib/sensors/yoke-doctrine-round-trip.sh`,
`lib/sensors/templates/semantic-judge.md`,
`lib/working-memory/cleanup.sh`) — swap legacy verbs in error
messages, comments, and Skill-tool invocations. (5) Tests
(`tests/canonical-memory-read.test.sh`,
`tests/canonical-memory-write.test.sh`,
`tests/ack-sensors-inferential.test.sh`,
`tests/skills-surface.test.sh`,
`tests/canonical-memory/contract-promotion-bidirectional-integration.test.sh`)
— replace invocation lines. The Yoke-side legacy skill files are
NOT modified by this task — they survive untouched until s03-t03
deletes them. `templates/` and `docs/` are out of scope here
(rewritten in Sprint 3 Task 4 / 5).

**Validation:** Five layers — (a) live-call-site sweep: `grep -rln
"/yoke:ask\|/yoke:preserve\|/yoke:teach\|/yoke:compress\|/yoke:memory"
claude-yoke/{agents,lib,tests,hooks}
claude-yoke/skills/{discover,tech-spec,acceptance-contract,implement,drift-sense,status,bootstrap}/SKILL.md`
returns empty (the seven legacy SKILL.md files are scheduled for
deletion and explicitly excluded from this sweep); (b) facade-presence:
`/yoke:search-canonical-memory` ≥ 4 paths under `claude-yoke/agents/`,
`/yoke:canonize` ≥ 1 path under `claude-yoke/skills/implement/`;
(c) end-to-end smoke runs a complete `/yoke:implement` fixture cycle
and asserts both facades fire; (d) sensor self-tests pass with
rewritten messages; (e) full `tests/` suite exits 0 with Yoke +
Bedrock installed together.

**Acceptance criterion:** `grep -rln "/yoke:ask\|/yoke:preserve\|/yoke:teach\|/yoke:compress\|/yoke:memory" claude-yoke/{agents,lib,tests,hooks} claude-yoke/skills/{discover,tech-spec,acceptance-contract,implement,drift-sense,status,bootstrap}/SKILL.md` outputs no lines AND running the full test suite exits 0 with Yoke + `claude-bedrock` installed.
