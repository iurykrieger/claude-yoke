## Sprint objective

Ship the dispatching machinery that the next two sprints consume.
At sprint end, a user installing only Yoke (no peer plugin yet) can
invoke `/yoke:search-canonical-memory "<query>"` and `/yoke:canonize`
and have those calls dispatch through a curated `providers.yaml` to
the still-embedded `/yoke:ask` and `/yoke:teach` skills. The legacy
verbs continue to work untouched. The sprint validates the
abstraction shape end-to-end against real callers without yet
extracting Bedrock — which is what makes Sprint 2's extraction safe.
A document at `docs/canonical-memory-provider-contract.md`
(`contract_version: 1`) freezes the working-memory layout providers
must read; subsequent provider implementations consume it.

## Tasks

### Task 2026-04-30-pluggable-canonical-memory-s01-t01

**Story:** Without a single source of truth that names every
supported provider and pins their two skill verbs, `/yoke:search-canonical-memory`
and `/yoke:canonize` have nothing to dispatch against. This task
authors that source of truth — `providers.yaml` at the plugin root —
seeded with one entry (`bedrock`) wired to the legacy in-Yoke skills
so the abstraction is functional from day one of the sprint.

**Technical implementation:** Create `providers.yaml` at the plugin
root next to `.claude-plugin/`, `skills/`, `lib/`. Top-level keys are
exactly two: `schema_version: 1` and `providers:` (a mapping). Each
provider entry has five mandatory keys: `description`, `requires`
(carries `plugin` and `min_version`, both nullable for in-Yoke seed
entries), `skills` (carries exactly `search` and `canonize`, each a
`<plugin>:<skill>` string), and `config_passthrough` (a list of keys
under `.yoke/config.yaml :: canonical_memory` forwarded to the
provider opaquely). Seed the `bedrock` entry with `requires.plugin:
yoke`, `requires.min_version: "2.0.0"`, `skills.search: "yoke:ask"`,
`skills.canonize: "yoke:teach"`, and `config_passthrough: [url, name,
default_branch]`. The file is curated per
`yoke-decision-2026-04-24-each-sprint-produces-an-installable-exercisable-pl`
and `concepts/yoke-pattern-plugin-structure`. PRD Open Question Q1
closed by this task.

**Validation:** Append a test under `tests/smoke/` (named for the
behavior it asserts, not for a sprint number — per the sprint-as-cycle
discipline) that runs four checks against the file: (1) it exists at
the plugin root, (2) `yq '.schema_version'` returns `1`,
(3) `yq '.providers.bedrock.skills.search'` returns `yoke:ask`,
(4) `yq '.providers.bedrock.skills.canonize'` returns `yoke:teach`.
A negative test asserts that adding a sibling top-level key besides
`schema_version` and `providers` causes the resolver in s01-t02 to
exit with the unknown-key code.

**Acceptance criterion:** `yq -r '.schema_version, .providers.bedrock.skills.search, .providers.bedrock.skills.canonize' providers.yaml` outputs the three lines `1`, `yoke:ask`, `yoke:teach` (in that order) and exits 0.

### Task 2026-04-30-pluggable-canonical-memory-s01-t02

**Story:** The two facade skills (s01-t03, s01-t04) need a single
deterministic answer to "what provider is configured for this
project, and which skill verbs should I dispatch to?" — and they
need it as exported shell variables, not as a markdown response.
This task builds the bash function that answers the question and
extends the project config template so a fresh `/yoke:bootstrap` can
emit the new key.

**Technical implementation:** Create `lib/canonical-memory/resolve-provider.sh`.
Export `yoke_resolve_provider` as a shell function (sourced, not
exec'd). The function reads the active project's `.yoke/config.yaml`
(resolved relative to `$PWD`), parses `canonical_memory.provider`
via the same yq-style approach used in the existing
`resolve-memory.sh` (with an awk/grep fallback when `yq` is absent),
reads `<plugin_dir>/providers.yaml`, looks up the provider entry,
and exports four variables: `YOKE_PROVIDER_NAME`,
`YOKE_PROVIDER_SEARCH_SKILL`, `YOKE_PROVIDER_CANONIZE_SKILL`,
`YOKE_PROVIDER_CONFIG_PASSTHROUGH` (newline-separated). Exit codes:
`0` resolved, `3` config missing, `4` `canonical_memory.provider`
key missing (the unmigrated case, mirrored by the s03-t02 helper),
`5` provider name not found. Mirror the
`yoke_resolve_memory` pattern. Extend `templates/yoke-config.yaml`
to include `provider: "{{ canonical_memory_provider }}"` under
`canonical_memory:` (placeholder is filled by `/yoke:bootstrap` in
s03-t01). The legacy `resolve-memory.sh` stays in place for the
still-active legacy skills during Sprints 1 and 2.

**Validation:** Add `tests/canonical-memory/resolve-provider.test.sh`
with four cases — happy path (fixture with `provider: bedrock`,
assert exit 0 and `$YOKE_PROVIDER_SEARCH_SKILL == "yoke:ask"`);
missing config (assert exit 3); missing provider key (assert exit
4); unknown provider name (assert exit 5). Add a smoke test that
runs the resolver in concert with the seed `providers.yaml`
populated by s01-t01. Add a template-lint check confirming the
`provider:` placeholder line is present in `templates/yoke-config.yaml`.

**Acceptance criterion:** `bash -c 'cd /tmp/fixture && source <plugin_dir>/lib/canonical-memory/resolve-provider.sh && yoke_resolve_provider && echo "$YOKE_PROVIDER_NAME=$YOKE_PROVIDER_SEARCH_SKILL/$YOKE_PROVIDER_CANONIZE_SKILL"'` against a fixture project whose `.yoke/config.yaml` has `canonical_memory.provider: bedrock` outputs exactly `bedrock=yoke:ask/yoke:teach` and exits 0.

### Task 2026-04-30-pluggable-canonical-memory-s01-t03

**Story:** Every Yoke caller that today says "consult canonical
memory" — agent prompts, spec-phase skills, the runtime Orchestrator
subagent in consult mode — eventually invokes `/yoke:ask`. After
this task, those callers have a provider-agnostic alternative.
Internal call-site rewrites happen in s02-t05; in Sprint 1 the
legacy `/yoke:ask` continues to work and the new facade is purely
additive.

**Technical implementation:** Create `skills/search-canonical-memory/SKILL.md`
following `concepts/yoke-pattern-plugin-structure`. Frontmatter
`name: search-canonical-memory`. Pre-flight sources
`lib/working-memory/paths.sh` and
`lib/canonical-memory/resolve-provider.sh`. No active-task
pre-condition (canonical-memory queries are source-agnostic per
`concepts/yoke-pattern-memory-model`). Body: read the user-supplied
query argument (reject empty with `wm: query is required`), invoke
`yoke_resolve_provider` (surface resolver exit messages on
non-zero), then on exit 0 invoke
`Skill(skill: "${YOKE_PROVIDER_SEARCH_SKILL}", args: "<query>")`.
Return the response verbatim — no parsing, no reformatting, no
caching. Critical rules mirror `/yoke:ask`'s read-only discipline.

**Validation:** Smoke test invokes
`/yoke:search-canonical-memory "what is the claude-yoke project?"`
in a fixture project with `provider: bedrock` against the developer's
local Bedrock vault; asserts non-empty markdown response and exit 0.
Equivalence test in
`tests/canonical-memory/search-facade-equivalence.test.sh` invokes
`/yoke:search-canonical-memory` and `/yoke:ask` against the same
vault with the same query and asserts byte-equivalent responses.
Negative tests cover empty-query and resolver-exit-4 paths.

**Acceptance criterion:** `/yoke:search-canonical-memory "what is the claude-yoke project?"` returns a response byte-equivalent to `/yoke:ask "what is the claude-yoke project?"` and exits 0 against the developer's `iury-brain` Bedrock vault with `provider: bedrock` configured.

### Task 2026-04-30-pluggable-canonical-memory-s01-t04

**Story:** When `/yoke:implement` terminates, the working memory
under `.yoke/` carries the freshest signal the framework will ever
have. Today this signal flows to canonical memory via the
Orchestrator subagent in canonize mode invoking `/yoke:preserve`
with Bedrock-specific knowledge of how to read `.yoke/`. After this
task, the framework hands off via a single facade verb that knows
nothing about the destination beyond an absolute path and the
configured provider.

**Technical implementation:** Create `skills/canonize/SKILL.md`.
Frontmatter `name: canonize`. No arguments at v2.0.0. Pre-flight
sources paths and resolver; verifies `.yoke/` exists in the current
working directory. Body: resolve `wm_path="$(cd "$PWD/.yoke" && pwd)"`
so the path is absolute, invoke `yoke_resolve_provider` with the
same exit-code handling as the search facade, then on exit 0 invoke
`Skill(skill: "${YOKE_PROVIDER_CANONIZE_SKILL}", args:
"--working-memory ${wm_path}")`. Capture the provider's stdout and
append a single line beginning `canonize:` to
`.yoke/runtime/progress.md` as a final-cycle entry. Propagate the
provider's exit code. Critical rules: never bundle, summarize, or
pre-process the working memory; never classify maturity (provider
judgment); never silently swallow the provider's exit code.

**Validation:** Smoke test creates a fixture `.yoke/` representing a
converged task (PRD + spec + sprint files + a trivial
`runtime/progress.md`), runs `/yoke:canonize`, asserts the facade
dispatches with the expected absolute path and that the underlying
skill receives it. Path-resolution test invokes the facade from a
sub-directory of a Yoke project; asserts the path forwarded is
absolute. Negative tests: missing `.yoke/`, resolver exit 4,
provider-skill non-zero exit. Logging test asserts a final
`canonize:` line appears in `runtime/progress.md`.

**Acceptance criterion:** `/yoke:canonize` from a fixture Yoke project with `provider: bedrock` dispatches to `/yoke:teach --working-memory <abs-path-to-.yoke>`, exits 0, and appends a line beginning with `canonize:` to `.yoke/runtime/progress.md`.

### Task 2026-04-30-pluggable-canonical-memory-s01-t05

**Story:** `/yoke:canonize` hands the provider a path to `.yoke/`
and nothing else. For the provider to do its job it must know what's
inside that directory — which files are guaranteed, which are
optional, what their frontmatter shapes are. Without a versioned
contract every incidental change to `.yoke/` layout silently breaks
every provider. This document is the contract.

**Technical implementation:** Create `docs/canonical-memory-provider-contract.md`.
Carry `contract_version: 1` in a header line. Author the seven
required H2 sections in this order: `## --working-memory argument
semantics` (the path is read-only; providers MUST NOT modify
`.yoke/`); `## Directory tree` (REQUIRED/OPTIONAL annotation per
file under `.yoke/`, derived from `lib/working-memory/paths.sh`
helpers — `prds/`, `specs/`, `sprints/`, `acceptance-contracts/`,
`contracts/`, `sensors/`, `runtime/progress.md`); `## Frontmatter
shapes` (link to existing templates); `## runtime/progress.md log
conventions` (cite the soft `canonize:` line from s01-t04);
`## Soft exit-summary convention` (closes PRD Q2 as soft);
`## Versioning policy` (bumping `contract_version` requires bumping
`providers.yaml.schema_version`); `## Anti-patterns` (forbid
provider writes into `.yoke/`, structured-log parsing of cycle
entries, reliance on file presence beyond REQUIRED). Link from the
rewritten `docs/canonical-memory-setup.md` (s03-t04).

**Validation:** Three checks: file presence; `grep -q '^contract_version:
1$'`; section completeness (grep for the seven required H2
headings). No automated content review — this is human-read
material. Manual review at Trigger 3 confirms the directory tree
matches the live `paths.sh` helpers.

**Acceptance criterion:** `grep -c '^contract_version: 1$' docs/canonical-memory-provider-contract.md` outputs `1` AND `grep -cE '^## (--working-memory|Directory tree|Frontmatter shapes|runtime/progress.md|Soft exit-summary convention|Versioning policy|Anti-patterns)' docs/canonical-memory-provider-contract.md` outputs `7`.
