## Sprint objective

Fill the three load-bearing stages on top of the Sprint-2 skeleton:
the synthesis stage (LLM step that turns parsed spec + parsed AC into a
complete task list with explicit UC-realization linkage), the
deterministic partition stage (groups tasks into sprints with delivery
objectives and binary DoD lists), and the bundle render stage (writes
`.yoke/sprints/<slug>-s<NN>.md` files via `templates/sprint.md`). Cap
the sprint with the Trigger 2.5 approval gate via the shared approval
menu. After this sprint, `/yoke:generate-sprints` produces approved
sprint runtime bundles end-to-end against an approved spec + AC pair;
the produced bundles are consumable by the existing `/yoke:implement`
without any consumer-side changes.

The stage is the skill's primary agentic node — bracketed by deterministic bash on both sides (input parsers feed it; the partition stage consumes its output). Inputs to the synthesis prompt: (a) the JSON emitted by `parse_acceptance_criteria` (Sprint-2 helper); (b) the JSON emitted by `parse_spec_architecture`; (c) optional canonical-memory hits (the skill MAY invoke `/yoke:search-canonical-memory` for cross-task context — log each call once to `.yoke/runtime/progress.md` as a `search:` event). ### Task 2026-05-03-generate-sprints-skill-s03-t02

**Story:** As `/yoke:generate-sprints`, I need a deterministic partition stage that groups the synthesized tasks into sprints with delivery objectives and binary DoD lists, so the partition is auditable and re-runnable against the same inputs without LLM variance. (Realizes: US-004)

**Technical implementation:** Add a Partition section to the skill body. The stage is intentionally deterministic — the agentic step ended at synthesis. The partition algorithm: (1) Read `.yoke/runtime/.generate-sprints-plan.yaml :: tasks`. (2) Group tasks by their `applies_decisions` overlap (tasks sharing two or more spec anchors land in the same sprint). (3) Cap sprint size at 8 tasks (the established baseline mean is 5.4); when a group exceeds 8, split into two sprints by `acceptance_criterion` lexical clustering. (4) For each resulting sprint, compute a delivery objective by concatenating the realized UC names + the dominant spec anchor; compute a DoD by lifting each task's `acceptance_criterion` and rephrasing as a sprint-level binary check (deterministic: `<task_id>: <criterion>` → `<sprint-task-id-padded>: <criterion>`). (5) Assign final task IDs `<slug>-s<NN>-t<MM>` in walk order (sprint 1 t01, t02, …; sprint 2 t01, …). (6) Write the resulting partition into `.yoke/runtime/.generate-sprints-plan.yaml :: sprint_partition` via `yq -i`. Implementation lives in `lib/generate-sprints/partition.sh` (pure bash + `yq` + `jq`); zero LLM cost.

**Validation:** Smoke test `tests/smoke/partition-determinism.test.sh` runs the partition stage twice against the same task-list fixture and asserts byte-identical output (`diff -q` on the resulting `sprint_partition` blocks). A second branch asserts the per-sprint task count never exceeds 8 (cap enforced) and never falls below 1 (no empty sprints).

**Acceptance criterion:** `bash tests/smoke/partition-determinism.test.sh` exits 0 AND the test prints `PASS: byte-identical across two runs`.

### Task 2026-05-03-generate-sprints-skill-s03-t03

**Story:** As `/yoke:generate-sprints`, I need a render stage that materializes one `.yoke/sprints/<slug>-s<NN>.md` file per sprint partition entry, so that downstream consumers (`/yoke:implement`, the council personas) see the same `templates/sprint.md` shape they consume today. (Realizes: US-005)

**Technical implementation:** Add a Render section to the skill body. For each entry in `sprint_partition`: (1) Compute the target path via `wm_sprint_path "$slug" "$sprint_num"`. (2) Reuse `lib/working-memory/scaffold-sprints.sh` ONLY for the frontmatter scaffolding pattern — but call into it directly is impossible because that script reads sprint headings from a spec file. Instead, lift the placeholder-substitution logic into a new helper `lib/generate-sprints/render-bundle.sh :: render_sprint_bundle <slug> <sprint_num> <plan-yaml-path>`. The helper reads the plan's matching `sprint_partition` entry, reads `templates/sprint.md`, performs the same placeholder substitutions (`<slug>`, `<NN>`, `<N>`, `<iso8601>`), then fills the five body sections from the partition data: Sprint objective (from `delivery_objective`), Sprint DoD (from `dod`), Tasks (one `### Task <ID>` per task, four inline labels, `(Realizes: UC-N[, UC-M])` clause adjacent to `**Story:**`), Functional acceptance criteria (UC-IDs only, deduplicated across the sprint's tasks), Sensors (sensor IDs only, deduplicated). (3) Set frontmatter `traceability` to the literal string `.yoke/specs/<slug>.md; .yoke/acceptance-criteria/<slug>.md` (semicolon-separated per the spec's Contracts section). (4) Set frontmatter `model` to the calling skill's model id. (5) Write the file. Post-write, validate that all 5 H2 headings are present and ordered; if not, abort non-zero with `wm: render shape violation at <path>: missing heading <name>`.

**Validation:** Smoke test `tests/smoke/render-bundle-shape.test.sh` runs the renderer against the full-flow fixture and asserts: (a) each produced sprint file has exactly the 5 H2 headings in fixed order; (b) each `### Task <ID>` subsection contains the 4 inline labels (`**Story:**`, `**Technical implementation:**`, `**Validation:**`, `**Acceptance criterion:**`); (c) each `**Story:**` line ends with a `(Realizes: UC-N[, UC-M])` clause matching the regex `\(Realizes: UC-[0-9]+(, UC-[0-9]+)*\)`; (d) frontmatter `traceability` contains both spec and AC paths.

**Acceptance criterion:** `bash tests/smoke/render-bundle-shape.test.sh` exits 0 AND the test prints `PASS: bundle shape conforms` for every produced sprint file.
