## Sprint objective

Stand up the runtime infrastructure the council will run on, without
yet activating council semantics. At sprint end, the framework
carries: a captured drift baseline committed to the spec; three
shipped persona files (Sr Eng, Sr QA, Sr Staff) loadable by Claude
Code's agent loader and validated by Yoke's startup-time schema check;
a per-persona-slice directory layout under
`.yoke/runtime/cycles/<N>/`; a deterministic merge helper that
collapses persona slices into a read-only view; and a file-marker-
based sync barrier with a sensor that asserts mtime ordering between
Phase A markers and Phase B reads. The v2.x runtime continues to
operate unchanged in parallel — none of this infrastructure is wired
into `/yoke:implement` yet (that lands in Sprint 2).

### Task 2026-05-01-agent-council-s01-t02

**Story:** as a runtime caller about to load a council persona, I read its definition from a Claude-Code-loadable agent file extended with Yoke-specific frontmatter keys, with three shipped defaults available out of the box.

**Technical implementation:** create three files at plugin root: `agents/sr-eng.md`, `agents/sr-qa.md`, `agents/sr-staff.md`. Frontmatter for each follows the extended schema specified in the spec's `### Persona spec frontmatter` contract: standard Claude Code keys (`name`, `description`, `tools`, optional `model`) plus Yoke keys (`objective` — single sentence, `sensor-toolkit` — list of sensor IDs the persona may invoke, `review-skill` — slash command for code review, optional unless persona is Sr Staff). Body of each file carries the persona's prompt template (objective preamble + Phase A instructions + Phase B instructions). Sr Eng's `review-skill` is empty; Sr QA's `review-skill` is empty; Sr Staff's `review-skill` defaults to `/review`. Tool lists differ per persona: Sr Eng gets full implementer set; Sr QA gets read+test-writing+sensor; Sr Staff gets read+skill+canonical-memory query. Cite `concepts/yoke-pattern-roles` in the body header comment to link the persona to the architectural role it plays.

**Validation:** each file parses as valid YAML frontmatter via `awk` extraction; required keys are present; `sensor-toolkit` is a list (possibly empty); `review-skill` is set on Sr Staff only. A unit test at `tests/runtime/persona-files-shape.test.sh` parses each shipped file and asserts the schema. Manual: open one of the files in an editor and confirm Claude Code's agent loader resolves it (no syntax error reported).

**Acceptance criterion:** `tests/runtime/persona-files-shape.test.sh` exits 0 AND `awk '/^---$/{c++;next} c==1' agents/sr-staff.md | grep -E '^review-skill: ' | grep -q '/review'`.

### Task 2026-05-01-agent-council-s01-t03

**Story:** as `/yoke:implement` about to spawn personas, I validate every persona file at startup and fail fast with a clear diagnostic when any required Yoke-specific key is missing or malformed.

**Technical implementation:** add `lib/runtime/persona-loader.sh` exposing two callable subcommands — `validate <persona-file-path>` (per-file) and `validate-all <agents-dir>` (loops over every `.md` under the dir). The validator extracts frontmatter via `awk` and asserts presence + type of `name`, `description`, `tools`, `objective`, `sensor-toolkit` (list), and conditional `review-skill` (string when present). On any violation, write a `wm: <message>` line to stderr naming the file path AND the missing/malformed key, and exit non-zero. On success, exit 0 silently. The loader is sourced by `/yoke:implement`'s pre-flight in Sprint 2; this sprint only ships and tests the helper. Add fixture files under `tests/runtime/fixtures/`: one valid persona, one missing `objective`, one with `sensor-toolkit` as a string instead of a list, one with `tools` missing.

**Validation:** unit test at `tests/runtime/persona-loader.test.sh` runs the validator against each fixture and asserts the expected exit code + stderr message. Smoke test runs `validate-all agents/` against the three shipped persona files and expects exit 0. Both tests are added to `.github/workflows/tests.yml`'s smoke matrix.

**Acceptance criterion:** `tests/runtime/persona-loader.test.sh` exits 0 AND `bash lib/runtime/persona-loader.sh validate-all agents/` exits 0 with the three shipped persona files in place.

### Task 2026-05-01-agent-council-s01-t04

**Story:** as a council persona running Phase A, I write my own progress to a slice file under the cycle's directory and never touch another persona's slice; as the council reader at Phase B open, I merge the slices into a deterministic read-only view.

**Technical implementation:** introduce the per-cycle directory layout `.yoke/runtime/cycles/<N>/<persona>.md` (flat — réplica history is preserved as Phase B round sections inside each persona file, not as separate files). Add `lib/runtime/council-merge.sh` exposing `merge <cycle-dir>` which reads each `<persona>.md` file in alphabetical order, emits a structured markdown view to stdout (one `## <persona>` H2 per persona, persona's body inlined as H3s), and exits 0. The function is pure — no writes, no canonical memory queries, no LLM calls. Add path helpers in `lib/working-memory/paths.sh`: `wm_cycle_dir <slug> <N>`, `wm_persona_slice_path <slug> <N> <persona>`. Cite `concepts/yoke-pattern-memory-model` in the helper header to anchor the slice protocol to the working-memory model.

**Validation:** `tests/runtime/council-merge.test.sh` builds a cycle directory with three engineered persona slices, invokes `merge`, captures the output, invokes `merge` again, and asserts byte-equivalence (determinism). A second test ensures the merge order is alphabetical regardless of file mtime. A third test asserts that a slice file modified by a "wrong" persona — written by `sr-eng` containing content under a `## Phase A — own progress` from `sr-qa` — is detectable by a slice-isolation sensor (sensor logic lands here too).

**Acceptance criterion:** `tests/runtime/council-merge.test.sh` exits 0 AND two consecutive `bash lib/runtime/council-merge.sh merge tests/runtime/fixtures/cycle-3-personas/` invocations produce byte-identical stdout (verified by `diff -q`).

### Task 2026-05-01-agent-council-s01-t05

**Story:** as `/yoke:implement` about to open Phase B of a council cycle, I block until every persona has written its phase-A done marker; as a sensor, I assert no Phase B read of a persona slice happened before the latest Phase A marker write.

**Technical implementation:** define the marker filename convention `.yoke/runtime/.phase-a-done.<persona>` (one empty file per persona, written immediately before the persona's Phase A Task call exits). Add `lib/runtime/sync-barrier.sh` exposing `wait-all <slug> <N> <persona-list>` (polls for every named marker file with a small sleep, fails after a configurable timeout) and `clear-markers <slug> <N>` (removes any leftover markers idempotently at cycle entry). Add the sensor `tests/sensors/council-sync-barrier.test.sh` that engineers a cycle with three slice files plus three Phase A markers, then asserts every slice file's mtime is ≤ the latest marker mtime; a second engineered fixture flips one slice's mtime to BEFORE the latest marker, asserting the sensor exits non-zero with a clear violation message naming the offending slice. Cite `concepts/yoke-conventions` for the deterministic-sensor-output contract.

**Validation:** `tests/runtime/sync-barrier.test.sh` covers `wait-all` (success path, timeout path, idempotent `clear-markers`). The sensor test covers both pass and fail engineered cases. Both tests run in CI.

**Acceptance criterion:** `tests/runtime/sync-barrier.test.sh` exits 0 AND `tests/sensors/council-sync-barrier.test.sh` exits 0 on the pass fixture AND exits non-zero with a `wm: sync-barrier violation:` stderr line on the fail fixture.
