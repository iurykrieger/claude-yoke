# PRD: Promote recurring sprint contracts to canonical memory via the cascade

> Generated by `/yoke:discover` on 2026-04-27.
> Status: approved
> Approved by: iury.krieger@stone.com.br
> Approved at: 2026-04-27T22:17:55Z

## Product invariants

What must hold regardless of implementation. The shape of the product
that constrains every solution. Non-negotiable.

- **Sprint-contract semantics are unchanged.** The runtime contracts
  archive (working memory, per task, written by Generator and Validator
  on consensus) is not redefined. The contracts template is not
  rewritten. This PRD adds a *promotion path* from working memory into
  canonical memory; it does not touch the sprint-contract mechanism
  itself.
- **`/yoke:preserve` is the single write entry to canonical memory.**
  Promotion runs inside the existing cascade at loop termination, not
  as a parallel write authority. Model C governance applies to promoted
  concepts exactly as to any other canonical-memory write.
- **No new entity subtype.** Promoted contracts land in `concepts/` as
  ordinary concept entities — the same folder as the existing yoke
  pattern, decision, and conventions concepts. Provenance is encoded
  via tag, not via folder, filename prefix, or schema variant.
- **Provenance is graph-native.** Every promoted concept carries the
  `yoke` tag (marking that it emerged from a yoke-managed runtime loop)
  and a bidirectional wikilink to the project actor under `actors/`.
  The actor entity backlinks to the concept. Both directions of the
  edge MUST exist after promotion.
- **Hard contradictions escalate to human ratification.** When a third
  observation contradicts an already-promoted concept, the cascade
  escalates to Trigger 5 (canonization ratification) so the human
  settles which reading becomes doctrine. This is the design point of
  the framework, not a defect or a fallback — automated supersession
  of agent-derived doctrine is explicitly *not* a goal of this change.
- **No parallel doctrine layer.** Working memory does not become a
  second canonical store. If a contract is durable, it crosses the
  gate; if it is not, it stays in the per-task archive.
- **Threshold is observable from archives alone.** Reaching cascade
  evaluation requires the same `topic` (or topic-equivalent) being
  pinned in ≥ 2 distinct sprint-contract files across prior tasks. The
  count is computable from working-memory archives without an LLM
  call. Semantic similarity may layer on top (see Known constraints),
  but the floor — the gate that admits a contract into cascade scoring
  — remains LLM-free and reproducible.

## Business context

Two recent dogfood runs (`2026-04-26-light-dark-theme` and
`2026-04-27-yoke-doctrine-canonization`) produced sprint contracts
whose agreed interpretations are clearly generalizable beyond their
originating task: the `signOut({ redirectUrl: '/' })` quoting style,
the `.cl-scrollBox` selector substitution, and the additive-append
carve-out for the Generator's task-file write restriction. Today, each
of these contracts lives only in its task's sprint-contract archive.
The next task that hits the same ambiguity has no programmatic way to
discover the prior consensus — it will rediscover it (best case,
costing a cycle), re-negotiate it (medium case, costing two cycles
plus sensor-output drift), or escalate it as a fresh Trigger 4 (worst
case, blocking the loop on a question the framework has already
answered).

The pain is **cross-sprint reuse**, not the runtime sprint-contract
mechanism itself. The current mechanism is correct: contracts are
ambiguity-resolutions, negotiated by the agents at the moment of need,
inside the binding Acceptance Contract envelope. What is missing is a
gate that promotes the ones that have proven repeatable into the
layer the framework already uses for timeless project-core knowledge:
canonical memory, accessed via `/yoke:ask`.

The framework already has every primitive needed: `/yoke:preserve`
runs a five-criterion cascade (repeatability, generality, stability,
regulatory, non-contradiction) at loop termination; the `concepts/`
folder accepts new entities under Model C; `/yoke:ask` exposes them to
the spec phases and the runtime subagents; `/yoke:compress` already
handles vault alignment and pruning of stale or fragmented entities.
This PRD is a small composition over those primitives — not a new
architecture.

## Known constraints

What the implementation must respect, grouped by source.

### Technical

- **Cascade input shape.** `/yoke:preserve` already accepts structured
  entity lists, free-form text, and runtime working-memory paths. The
  promotion path must surface sprint contracts as candidate cascade
  input without altering the existing cascade signature.
- **Two-layer topic-match.** The threshold gate is exact-string match
  on the contract `topic:` field — deterministic, reproducible from
  archives alone. Layered on top, a semantic-overlap signal runs
  **inside `/yoke:preserve`** (the cascade's existing LLM step) so
  contracts that resolve the same underlying ambiguity with different
  prose are recognized as the same topic. Two layers, one write path:
  the deterministic floor admits the candidate; the semantic layer
  refines repeatability scoring during cascade evaluation; both run
  inside the single audited canonization step.
- **Pruning is delegated to `/yoke:compress`.** This PRD does NOT
  introduce a utilization tracker for promoted concepts. Stale,
  fragmented, or duplicated promoted concepts are detected and
  realigned by the existing `/yoke:compress` skill, which is the
  framework's vault-alignment engine. Treating pruning as a separate
  cycle (drift-sense → compress) keeps `/yoke:preserve` focused on the
  write decision and avoids coupling promotion to a new bookkeeping
  surface.
- **Slug derivation for promoted concepts is LLM-summarized.** The
  destination filename in `concepts/` is a shortened LLM-summarized
  title of the contract `topic:` field, kebab-cased and capped at the
  conventional concept slug length. The contract's full `topic:` prose
  is preserved verbatim in the concept's body and frontmatter
  description; only the filename is summarized. Slug collisions in the
  flat `concepts/` folder are resolved by the same regenerate-and-retry
  rule the working-memory paths helper uses for PRD slugs.
- **Project-actor resolution.** The promotion writes a bidirectional
  link to the project actor in the `actors/` folder. The host project
  is named in `.yoke/config.yaml`; the cascade resolves the host name
  to an actor entity at canonize time. If the actor entity does not
  exist, the cascade creates it on first promotion (subject to Model
  C, exactly like any other canonical-memory write).
- **Promoted concept structure follows the canonical-memory entity
  schema.** Mandatory rippability frontmatter (`ratified_at`,
  `model_calibrated_against`, `last_validated`, `traceability`,
  `impact_level`) plus graph relationships (`depends_on`, `supersedes`,
  `applies_to`, `contradicts_with`). The `traceability` field MUST
  cite each originating sprint-contract source.
- **Bidirectional link is non-optional.** The promoted concept's
  frontmatter `applies_to` lists the project actor; the actor's
  frontmatter or "Recent Activity" body section gains a wikilink to
  the new concept. A unidirectional link is treated as a
  promotion-incomplete state and must trip a sensor.

### Regulatory

- None. Internal framework plumbing; no PCI / LGPD / HIPAA surface.

### Organizational

- The framework is currently dogfooding canonization on its own
  substrate (`projects/claude-yoke`). The promotion path must work
  for that substrate at minimum. The actor-resolution rule
  (`.yoke/config.yaml` host name resolves to the matching actor entity in the `actors/` folder) is generic;
  the first executions will be against the `yoke-framework` actor.
- No team capacity blockers identified. The change is scoped to fit a
  single sprint.

## Risks

- **Topic-match false negatives at the deterministic floor.** Two
  contracts that resolve the same ambiguity with different `topic:`
  prose never reach count = 2 on exact-string alone. Signal: a third
  occurrence of the same ambiguity surfaces during canonize without a
  promotion candidate. Mitigation: the semantic-overlap signal layered
  inside `/yoke:preserve` (per Known constraints) catches these during
  cascade evaluation. The deterministic floor remains the gate, but
  the LLM layer rescues semantically-equivalent topics that the floor
  would otherwise miss.
- **Topic-match false positives.** Two genuinely distinct contracts
  with similar `topic:` prose get coalesced into a single concept that
  encodes neither correctly. Signal: the promoted concept's
  `traceability` cites two contracts whose `decision:` fields are
  incompatible. Mitigation: the cascade's existing `non-contradiction`
  criterion blocks contradictory promotions; the heuristic refuses to
  coalesce contracts whose `decision:` differs.
- **Doctrine pollution from low-quality contracts.** Two-sprint
  threshold is low; a poorly authored contract that gets copied into
  a follow-up sprint reaches threshold without earning the promotion.
  Signal: promoted concepts that no future sprint contract or PRD
  cites. Mitigation: `/yoke:compress` is the pruning surface — it
  detects fragmentation, duplication, and miscategorization in the
  vault and proposes realignment. Promotion is generous on entry;
  alignment is the corrective.
- **Bidirectional-link drift.** A promoted concept exists without its
  actor backlink, or vice versa, and the graph silently degrades.
  Signal: any orphaned half-edge between the concept and the named
  actor. Mitigation: a sensor that asserts the bidirectional invariant
  after each `/yoke:preserve` run; failure blocks the PR.
- **Repeatability calibration drift across models.** A contract pinned
  by an older model may not match a newer model's interpretation of
  the same ambiguity even when topic strings overlap. Signal: a
  promoted concept whose `model_calibrated_against` is stale relative
  to the new contract. Mitigation: the `last_validated` field is
  bumped on each occurrence the cascade observes; concepts that fall
  behind a staleness window get queued for re-validation by
  `/yoke:drift-sense` (out of scope for this PRD).
- **Hard contradictory third occurrence.** A promoted concept observes
  a third contract whose `decision:` directly contradicts the existing
  doctrine. Signal: cascade non-contradiction check fires.
  Mitigation: by design, escalate to human ratification (Trigger 5)
  rather than auto-supersede. The framework's design point is that
  hard contradictions are doctrine-settling decisions; humans, not
  agents, settle them.

## Anti-scope

- Do **not** redefine the sprint-contract template or its
  per-task/per-sprint semantics.
- Do **not** introduce a parallel doctrine layer inside working memory.
- Do **not** add Phase-3 surfacing of past contracts at acceptance-contract
  authoring time (that is a separate PRD; it is not in this scope).
- Do **not** add a utilization tracker for promoted concepts. Pruning is
  `/yoke:compress`'s responsibility.
- Do **not** auto-supersede a promoted concept on hard contradiction.
  Escalate to human ratification.
- Do **not** introduce a new canonical-memory entity subtype. Promoted
  contracts share the `concept` schema with every other concept entity.
