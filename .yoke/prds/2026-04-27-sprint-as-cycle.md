# PRD: Sprint files as ralph-cycle runtime bundles

## Product invariants

What must hold regardless of implementation. Non-negotiable.

- **One sprint = one ralph cycle.** The runtime atom is the sprint, not the task. A single ralph cycle reads exactly one sprint file as its working set, attempts to deliver every task in that sprint, and converges or escalates within the per-sprint hard bound. `/yoke:implement` walks sprints sequentially: `s01` to convergence → `s02` to convergence → … Per-task ralph iteration is retired.
- **Sprint files are runtime bundles, not sources of truth.** Every fact a cycle needs to execute lives in the sprint file *or* is referenced by a stable ID that resolves to a single source of truth elsewhere. Sensors are referenced by sensor ID (`.yoke/sensors/<id>.md`); functional acceptance criteria are referenced by criterion ID inside the binding `acceptance-contracts/<slug>.md`. **Inlining sensor bodies or duplicating AC criteria into sprint files is prohibited** — the binding contract and the sensor catalog stay authoritative; the sprint file projects them.
- **Phase artifacts stay one-file-per-task.** PRDs (`.yoke/prds/<slug>.md`), specs (`.yoke/specs/<slug>.md`), acceptance contracts (`.yoke/acceptance-contracts/<slug>.md`), and sprint contracts (`.yoke/contracts/<slug>.md`) remain one file per task. The only directory whose granularity changes is `.yoke/tasks/` → `.yoke/sprints/`, and its file shape collapses from per-task (`<slug>-s<NN>-t<MM>.md`) to per-sprint (`<slug>-s<NN>.md`). Tasks remain a concept *inside* the sprint file (objective, DoD, criterion-ID references), but they no longer carry their own file.
- **One contracts file per spec; sprints share the decision history.** `.yoke/contracts/<slug>.md` stays a single file across all sprints of the task. Sprint-scoped agreements append as `## Sprint <NN> contract` H2 sections at convergence. Decisions made during sprint 1 are visible to sprint 2's cycles by reading the same file — convergence on shared invariants is preserved without re-litigating them per sprint. The Generator and Validator co-write this file on consensus, exactly as today, just with sprint-scoped section headings instead of one monolithic body.
- **Sprints execute serially.** `/yoke:implement` walks sprint 1 → sprint 2 → … in lexical order (= positional order via zero-padded `s<NN>`). A sprint must converge (or escalate) before the next sprint loads. No parallel sprint execution; no sprint reordering at runtime. The serialization is what makes "one cycle = one sprint" meaningful — each cycle reads exactly one sprint file as its working set, with `progress.md` carrying a single `current_sprint:` pointer that advances on convergence.
- **Spec stays — sprint files do not subsume it.** `.yoke/specs/<slug>.md` keeps cross-sprint architecture: overall objective, contracts and interfaces, dependency direction, and the sprint index pointing at sprint files. This is the "what we're building" document; sprint files are "how each cycle executes". Conflating them buries cross-cutting context inside sprint 1 or duplicates it across every sprint.
- **Hard bounds are per-sprint, not per-task.** The 5–8 cycle ceiling and the 2–4h wall-clock ceiling apply to a single sprint. A 5-sprint task can therefore consume up to ~40 cycles end-to-end, but each sprint stands alone for convergence, divergence (Trigger 4), and escalation. `progress.md` resets cycle counters at sprint boundaries; a `current_sprint:` pointer tracks position in the walk.
- **Migration of legacy parts is mechanical.** Existing `.yoke/specs/<slug>-part-N.md` files are already sprint-sized executable chunks (each carries its own Objective and shipped as a separate PR during the `tech-spec-task-split` rollout). The migration is `git mv .yoke/specs/<slug>-part-N.md .yoke/sprints/<slug>-s<NN>.md` plus mechanical reframing of the in-file `Part N of M` headers. No LLM synthesis of "missing" cross-sprint specs is required — multi-part legacy tasks accept that `specs/<slug>.md` is absent for them.

## Business context

The framework's working-memory directory (`.yoke/`) over-splits per-task
artifacts in two distinct ways, and both hurt context-gathering by the
runtime subagents and any human reading the working memory:

1. **Phase-shaped split is fine; cycle-shaped split is missing.** Each
   task today spreads across `prds/`, `specs/`, `tasks/`,
   `acceptance-contracts/`, `contracts/`, and `sensors/` — five-to-six
   directories per task. The phase split is correct (each artifact has
   distinct lifetime, writer, and approval gate), so it stays. What
   does not exist today is a *cycle-shaped projection*: a single file
   that bundles everything one ralph cycle needs to execute. The
   runtime ends up loading the spec, the AC, N task files for the
   active sprint, and M sensor files — which is exactly the messy,
   hard-to-reason-about working set the user is reacting to.

2. **Legacy `-part-N.md` residue.** `.yoke/specs/` carries 62 files for
   24 distinct tasks: the multi-part spec convention from the pre-2026-04-25
   `tech-spec-task-split` rollout. The cleanup pass retired
   `wm_tech_spec_path`, but the on-disk files were never renamed. New
   contributors and any agent listing `.yoke/specs/` see noise that
   contradicts the active doctrine in [[yoke-pattern-memory-model]].

The trigger to address both at once is two-fold: (a) the user has
revisited the per-task-file decision two days after it landed and
prefers the per-sprint shape after observing it in the
doctrine-canonization run (16 task files for one task — too granular
to load efficiently), and (b) the legacy `-part-N` files are
*already* in the per-sprint shape this PRD is moving toward, so the
fix collapses two debts into one migration.

The cost of not doing this: every `/yoke:implement` cycle pays a
context-loading tax (5+ files per cycle), and every framework reader
needs to mentally filter "is this `-part-N` file legacy or current?"
The cost of doing it: supersession of two ratified decisions
(`yoke-decision-2026-04-25-task-ids-zero-pad-to-2-digits-filename-only`
gets refined to apply to sprint IDs only, and the per-task-file
clauses inside [[yoke-pattern-memory-model]] get superseded with new
canonization writes), plus a one-shot migration script.

## Known constraints

What the implementation must respect, grouped by source.

### Technical

- **Path helpers are the single chokepoint.** `lib/working-memory/paths.sh` exposes `wm_task_path`, `wm_list_task_paths`, `wm_validate_task_id`, and `WM_ARCHIVE_CATEGORIES`. The new shape requires `wm_sprint_path` / `wm_list_sprint_paths` / `wm_validate_sprint_id` (sprint IDs are `<slug>-s<NN>`). Live consumers of the old names — `lib/ralph-loop/orchestrate.sh`, the runtime agents (`agents/generator.md`, `agents/validator.md`, `agents/orchestrator.md`), `skills/tech-spec/SKILL.md`, `skills/acceptance-contract/SKILL.md`, `skills/implement/SKILL.md`, `skills/status/SKILL.md`, the smoke tests — must migrate inside this PRD's binding contract. **No backward-compat alias.** The rationale that retained `wm_tech_spec_path` (out-of-budget cascade across 12 files, per [[yoke-decision-2026-04-25-wm-tech-spec-path-retained-as-deprecated-soft-alia]]) does not apply here — the consumer surface is fully inside this PRD's scope.
- **Lexical = positional ordering preserved.** Sprint IDs use the existing zero-pad-to-2-digits convention (per [[yoke-decision-2026-04-25-task-ids-zero-pad-to-2-digits-filename-only]], refined to apply to sprint IDs after the task-as-file shape retires): `<slug>-s01.md` … `<slug>-s99.md`. `wm_list_sprint_paths` returns lexically-sorted paths == positionally-sorted sprints.
- **Sprint file = declarative bundle, not a free-form scratchpad.** The template under `templates/sprint.md` defines the load-bearing sections in order: (1) frontmatter (`sprint`, `slug`, `status`, `created_at`, `model`), (2) Sprint objective, (3) Sprint DoD, (4) Tasks (each: ID, one-line story, task DoD), (5) Functional acceptance criteria — referenced by criterion ID from `acceptance-contracts/<slug>.md`, (6) Sensors — referenced by sensor ID from `.yoke/sensors/<id>.md`. Cycle log / generator-validator scratch does NOT live in the sprint file; it routes to `.yoke/runtime/` per the existing pattern.
- **`/yoke:implement` walks sprints sequentially.** The orchestration loop reads `current_sprint:` from `progress.md`, loads the matching sprint file, runs ≤8 cycles to convergence, advances the pointer, and resumes. Divergence (Trigger 4) escalates inside the active sprint and does not advance the pointer. Successful sprint completion writes a sprint-scoped entry into `contracts/<slug>.md` and resets the cycle counter.
- **Per-sprint hard bound stays at 5–8 cycles for v0.** No recalibration in this PRD. Recalibration is a follow-up signal once real per-sprint cycle data accumulates.
- **Sensor cost tiering survives unchanged.** The sprint file references sensors by ID; the Validator-owned scheduling per [[yoke-decision-2026-04-27-sensor-cost-tiering]] (or whichever decision name resolves) continues to apply. No change to `lib/sensors/` or the sensor manifest.
- **Migration is loop-driven, not a one-shot script.** The migration of legacy `<slug>-part-N.md` spec files and the 16 existing doctrine-canonization task files happens *inside* `/yoke:implement` as a regular sprint with regular tasks. The Generator executes `git mv` and concatenation operations as sprint tasks; the Validator runs sensors that assert post-migration invariants (zero `-part-N.md` residue under `.yoke/specs/`, zero `-s<NN>-t<MM>.md` residue anywhere, every legacy spec has a sprint counterpart, line counts match modulo formatting). No standalone bash script artifact is produced — the migration is a first-class loop run, governed by the same Acceptance Contract as every other sprint. The 16 doctrine-canonization task files are **concatenated retroactively** into 5 sprint files: each task-file body becomes a `### Task <ID>` subsection inside the matching sprint file's Tasks section, with a `Migrated-from:` frontmatter array preserving the original task-file paths for audit.

### Organizational

- **Doctrine writes go through Phase 5 canonization.** The pattern doc supersession ([[yoke-pattern-memory-model]] gains a sprint-bundle section; the per-task-file clauses are superseded) and the decision refinement (`task-ids-zero-pad…` becomes scoped to sprint IDs only) ride out in the `/yoke:preserve` step at loop termination, under Model C. No mid-loop canonical-memory writes.
- **Smoke tests gate the PR.** `tests/smoke/sprint-2.test.sh` (working-memory invariants) and `tests/smoke/sprint-4.test.sh` (ralph-loop walking) gain assertions for the new shape: `.yoke/specs/` carries zero `-part-N.md` files post-migration; `.yoke/sprints/<slug>-s<NN>.md` exists for every sprint referenced by the spec; `wm_list_sprint_paths` returns lexically=positionally ordered; and a successful `/yoke:implement` run advances `current_sprint:` from `s01` to the final sprint. CI fails the PR otherwise.

## Scope v0

Closed list of in-scope deliverables.

1. **Path helpers.** Add `wm_sprint_path`, `wm_list_sprint_paths`, `wm_validate_sprint_id` to `lib/working-memory/paths.sh`. Hard-remove `wm_task_path`, `wm_list_task_paths`, `wm_validate_task_id`. `WM_ARCHIVE_CATEGORIES` swaps `tasks` → `sprints`.
2. **Skill rewrites.** Update `/yoke:tech-spec` to write sprint files under `.yoke/sprints/`. Update `/yoke:acceptance-contract` to reference task IDs as `<slug>-s<NN>-t<MM>` anchors *inside* the sprint file (criterion IDs unchanged). Update `/yoke:implement` to walk sprints sequentially with per-sprint hard bounds. Update `/yoke:status` to surface `current_sprint:` and per-sprint cycle progress. Update any incidental references in `/yoke:bootstrap`, `/yoke:discover`, `/yoke:ack-sensors`, `/yoke:preserve` if they touch task paths.
3. **Agent contracts.** Update `agents/generator.md`, `agents/validator.md`, `agents/orchestrator.md` to read sprint files as the cycle's working set. The four runtime subagents named in [[yoke-decision-2026-04-25-five-subagents-generator-validator-orchestrator-im]] continue to operate; only their input file shape changes.
4. **Sprint file template.** New `templates/sprint.md` with the load-bearing sections in order. Existing `templates/task.md` is retired.
5. **Migration as a loop sprint.** A dedicated migration sprint inside this PRD's `/yoke:implement` run executes the file moves: `git mv .yoke/specs/<slug>-part-N.md .yoke/sprints/<slug>-s<NN>.md` for every legacy spec part; concatenation of the 16 doctrine-canonization task files into 5 sprint files; in-file header reframing (`Part N of M` → `Sprint NN of MM`). The migration sprint includes its own pre-flight backup task that copies originals to `.yoke/.legacy-archive/2026-04-27-pre-migration/` (gitignored) before any move, and per-task validation runs the residual sensor (item 6) before declaring convergence.
6. **Validation sensor.** `lib/sensors/legacy-parts-zero-residual.sh` — fails on any remaining `<slug>-part-N.md` under `.yoke/specs/` or `<slug>-s<NN>-t<MM>.md` under any directory after migration. Wired into the standard sensor catalog and referenced by the migration sprint's sensor ID list.
7. **Pattern doc canonization.** Phase 5 writes a **new** pattern entity `concepts/yoke-pattern-sprint-runtime-bundle.md` capturing the sprint-as-cycle shape. [[yoke-pattern-memory-model]] gains a `refined_by: [yoke-pattern-sprint-runtime-bundle]` link in its frontmatter and the per-task-file clauses in its body get superseded by an inline reference to the new entity. [[yoke-decision-2026-04-25-task-ids-zero-pad-to-2-digits-filename-only]] gains a `superseded_by` pointer to a new decision entity that re-scopes the zero-pad rule to sprint IDs only.
8. **Progress file shape.** `.yoke/runtime/progress.md` gains a `current_sprint:` frontmatter field tracking the active sprint. The cycle log resets at sprint boundaries; a `completed_sprints:` array records sprints that converged, in order. No file split: `progress.md` stays a single file.
9. **Smoke tests.** Sprint-2 and Sprint-4 smoke tests gain the assertions enumerated under "Organizational" above. An additional smoke test asserts that `current_sprint:` advances monotonically through the sprint list during a successful `/yoke:implement` run, and that `progress.md` is never split into per-sprint files.

## Anti-scope

Explicitly out of scope. The Tech Spec MUST NOT plan work for any of these.

- **No change to PRD shape or directory.** `.yoke/prds/<slug>.md` stays one file per task.
- **No change to acceptance-contract shape or directory.** `.yoke/acceptance-contracts/<slug>.md` stays one file per task; AC remains the binding source of truth for "done".
- **No change to sensor shape or directory.** `.yoke/sensors/<id>.md` stays one file per sensor; reuse across tasks unchanged.
- **No collapsing of phase directories into a single per-task megafile.** PRD, spec, AC, contracts, sensors keep their separate directories. The sprint file is a *projection* over them, not a *replacement*.
- **No backward-compat alias for retired path helpers.** `wm_task_path` and friends are hard-removed. The rollout migrates every consumer in the same PR; no alias is retained.
- **No auto-regeneration of sprint files from spec + AC + sensors.** The `/yoke:tech-spec` skill writes them; humans/agents edit them in place. A future enhancement may add a `--regenerate` mode, but not in v0.
- **No recalibration of the cycle hard-bound.** Stays at 5–8 cycles, now scoped per-sprint instead of per-task. Recalibration after observation, not before.
- **No reshuffling of `.yoke/runtime/` shape.** `progress.md` gains a `current_sprint:` field; no other runtime files are split, renamed, or moved.
- **No changes to the canonical-memory substrate, MCP boundary, or `/yoke:ask` / `/yoke:preserve` surface.** Doctrine writes ride through the existing Phase 5 cycle.
- **No retroactive synthesis of "missing" cross-sprint specs for legacy multi-part tasks.** If a legacy task had only `-part-N.md` files and no top-level spec, the migration leaves `specs/<slug>.md` absent for that task. New tasks under the new shape always have one.

## Risks

What could go wrong. Each risk has an observable signal and a mitigation hint where known. The Validator may consume these in Phase 3 for sensor calibration.

- **Risk — Source-of-truth drift.** Sprint files reference AC criterion IDs and sensor IDs. If a Generator inlines criterion text or sensor logic into a sprint file (for "convenience"), the AC and sensor catalog stop being authoritative. **Signal:** any sprint file body contains substring matches against `acceptance-contracts/<slug>.md` criterion bodies or `.yoke/sensors/<id>.md` sensor bodies beyond the ID reference. **Mitigation:** a `sprint-files-reference-only` sensor that fails when a sprint file contains an AC criterion's text without the matching ID anchor, or a sensor's logic without the matching ID reference. Drafted in Phase 3.
- **Risk — Cycle hard-bound miscalibration.** A sprint may pack more work than a single cycle can deliver, blowing the 8-cycle ceiling more often than the per-task shape did. **Signal:** average cycles-to-convergence per sprint after migration trends > 6 across 5+ runs. **Mitigation:** recalibrate the hard-bound (out of v0 scope) or instruct `/yoke:tech-spec` to keep sprints small. Tracked but not pre-mitigated.
- **Risk — Loop-driven migration corrupts git history.** The migration uses `git mv` and in-place regex rewrites driven by Generator cycles. A bad regex on the `Part N of M` header or a partial-write on the concatenation pass could damage spec content. **Signal:** post-migration `git diff --stat` shows changes outside the renamed files or beyond the header rewrite. **Mitigation:** the migration sprint's first task is a pre-flight backup that copies originals to `.yoke/.legacy-archive/2026-04-27-pre-migration/` before any move; failure mode is restore-from-archive. The Validator's residual sensor blocks convergence until invariants pass. Smoke test `tests/smoke/sprint-2.test.sh` adds a pre/post diff invariant on file count and total line count, exercised in CI on the migration PR.
- **Risk — Doctrine drift between canonical memory and on-disk shape.** The pattern doc supersession is a Phase 5 write. If `/yoke:preserve` fails or the Model C window rejects, the on-disk shape moves but doctrine still says per-task. **Signal:** `/yoke:ask "what does Yoke decide about working-memory shape?"` returns the per-task answer post-merge. **Mitigation:** the `/yoke:preserve` ratification packet is drafted alongside this PRD's tech spec; the canonization PR is opened in the same change. Hard escalation if Model C blocks: revert the on-disk migration. Tracked as Open Question 1 below.
- **Risk — `.yoke/sprints/` collides with other tooling.** The directory name may shadow an existing convention in some host project's tooling. **Signal:** any sensor or test failure mentioning `sprints/` ambiguity. **Mitigation:** the smoke test asserts the directory is created only by `/yoke:bootstrap` under `.yoke/`, never at the project root. Low likelihood; tracked.
- **Risk — Reviewer load on the migration PR.** 78 file moves (62 spec parts + 16 task files) plus path-helper changes plus skill rewrites is a fat PR. **Signal:** reviewer asks for the PR to be split. **Mitigation:** the tech spec partitions into sprints (irony noted): sprint 1 = path helpers + sensor + template + bootstrap; sprint 2 = skill rewrites; sprint 3 = migration script + execution; sprint 4 = pattern-doc canonization + smoke-test wiring. Each sprint ships as a separate PR.
