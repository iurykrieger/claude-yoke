# PRD: /yoke:fix — Phase-1 entrypoint for fix-shaped tasks

> Generated by `/yoke:discover` on 2026-05-05.
> Status: approved
> Approved by: iury.krieger@stone.com.br
> Approved at: 2026-05-05T00:00:00Z

## Introduction / Overview

Yoke today routes every change — bugfix, dependency bump, narrow
refactor, brand-new feature — through `/yoke:discover`. That skill
embeds a Product-Manager (CPO-style) persona that grills the user on
audience specificity, observable success metrics, anti-scope
aggressiveness, and product framing. The grill is correct doctrine
for a product feature: it cuts scope, forces decisions, and produces
a PRD whose `FR-N` lift survives into the Acceptance Criteria's
Definition-of-Done and Acceptance-Criteria layers.

The grill is **wrong shape** when the user already knows what is
broken. A bug carries a contract that is being violated, a
reproduction path, an observed behavior, and an expected behavior.
The audience is whoever depends on the contract; the success metric
is binary ("the bug stops reproducing"). Forcing the user through a
PM dialogue to author this is ceremony tax — and worse, it leaks
product framing into engineering work where it does not belong.

This PRD specifies a new Phase-1 skill, `/yoke:fix`, that authors a
**fix-spec** under a separate path (`.yoke/fixes/<slug>.md`),
embodies a **Senior Engineer persona** (uniform with `/yoke:tech-spec`),
moves through a clarity-driven dialogue (no fixed round count;
proceed when the problem is clear), and chains into `/yoke:tech-spec`
exactly like `/yoke:discover` does — no parallel pipeline, no skip,
no Phase-3 exception. The downstream skills (`/yoke:tech-spec`,
`/yoke:acceptance-criteria`, `/yoke:implement`, `/yoke:canonize`)
gain a Phase-1-artifact-agnostic resolver so they consume *whichever*
of `prd.md` or `fix.md` exists for the active slug.

The change preserves every architectural invariant in
`yoke-pattern-phase-flow` (sequential phases, typed input/output,
binding gates) while widening the Phase-1 surface from a single
authoring path to two — one product-shaped, one engineering-shaped.

## Goals

- Cut Phase-1 ceremony for fix-shaped tasks: when the user submits a
  bug, narrow refactor, dependency bump, or infra tweak with the
  problem already shaped, `/yoke:fix` reaches Trigger 1 in zero
  dialogue rounds.
- Preserve every Phase-2/3/4/5 invariant: the rest of the cycle is
  unchanged. Tech Spec, Acceptance Criteria, Implement, and Canonize
  consume the fix-spec via a path-agnostic resolver, not via a
  branched pipeline.
- Keep the Phase-1 surface non-confusing: a clear, mechanical rule
  picks `/yoke:fix` over `/yoke:discover` so the choice is not a
  matter of taste.
- Avoid mission creep: the skill refuses (or degrades to
  `/yoke:discover`) when the input describes new desired behavior
  rather than broken existing behavior.

## Product invariants

- Phase-1 produces exactly one binding artifact per task — either a
  PRD or a fix-spec, never both.
- Phase 2, 3, 4, and 5 see the same lifecycle whether Phase 1 was
  authored via `/yoke:discover` or `/yoke:fix`. No skill downstream
  branches its core logic on Phase-1 author identity.
- The fix-spec carries `Status: approved` semantics identical to the
  PRD: Phase 2 only starts after Trigger 1 is satisfied.
- The Senior Engineer persona literal name in `/yoke:fix` matches the
  literal name in `/yoke:tech-spec`. Per OQ-2 resolution, the skill
  body opens with a `**Mode:** diagnose-first` tag (paired with
  `**Mode:** design-first` in `/yoke:tech-spec`); the Mode tag is
  the disambiguator, the literal persona name is the role
  abstraction. Convention ratified into `concepts/yoke-conventions`
  via the canonize handoff.
- The skill-mode of operation is clarity-driven, not round-counted: a
  problem statement is "ready" iff four readiness checks pass (what
  broke / reproduction or trigger / expected behavior i.e. the
  violated contract / blast radius). A second four-check set —
  the **narrowness gate** (component breadth / contract shape /
  trigger specificity / surface containment) — runs in parallel
  every dialogue turn; ≤ 2/4 passing the narrowness gate aborts
  with a re-route prompt to `/yoke:discover`, 3/4 passes a
  `scope_caution:` flag into the fix-spec frontmatter.

## Functional Requirements

- **FR-1:** A new skill at `skills/fix/SKILL.md` is registered as
  `/yoke:fix` and is the documented Phase-1 entrypoint for
  fix-shaped tasks (bugs, narrow refactors, dependency bumps, infra
  tweaks).
- **FR-2:** The skill embeds a **Senior Engineer persona** (literal
  name uniform with `/yoke:tech-spec`). The persona body opens with
  a one-line mode tag — `**Mode:** diagnose-first` — on the first
  line under "Your role". The dialogue asks about what broke, the
  reproduction or trigger path, the expected behavior (the contract
  being violated), the observed behavior, and the blast radius. It
  does **not** ask about audience, success metrics, or anti-scope
  in product-feature shape. **(Resolves OQ-2 with option (c).)**
  The implementation also backfills `**Mode:** design-first` into
  `/yoke:tech-spec`'s persona body in the same change, and ratifies
  the Mode-tag convention into `concepts/yoke-conventions` via the
  canonize handoff (valid initial values: `diagnose-first`,
  `design-first`; vocabulary is open, future skills append values
  without re-ratification).
- **FR-3:** The skill writes its artifact to `.yoke/fixes/<slug>.md`
  via a new path helper `wm_fix_path` exported from
  `lib/working-memory/paths.sh`. The directory is created lazily on
  first use, mirroring `.yoke/prds/`.
- **FR-4:** The skill validates the slug via the same regex used for
  `/yoke:discover` (`^[0-9]{4}-[0-9]{2}-[0-9]{2}-[a-z0-9][a-z0-9-]{0,49}$`).
  Slug-collision detection considers PRD slugs *and* fix-spec slugs:
  the same `<YYYY-MM-DD>-<slug>` cannot be used for both. The
  collision helper is renamed/extended to consider both directories;
  no semantic numeric-suffix fallback.
- **FR-5:** The skill runs a **clarity-driven dialogue**: it
  evaluates the four readiness checks (what broke / repro / expected
  / blast radius) on the initial input. If 4/4 pass, it skips
  directly to fix-spec draft. If any check fails, it asks **only**
  about the missing ones, in lettered-options format where the
  option set is enumerable, free-form otherwise. There is no fixed
  round cap; the dialogue terminates when 4/4 readiness checks pass
  AND the narrowness gate (FR-6) does not abort. A safety bound of
  5 dialogue turns applies before the skill writes the fix-spec
  with explicit `TODO` markers and surfaces them in
  `## Open Questions`.
- **FR-6:** **Narrowness gate (graduated refusal). (Resolves OQ-1
  with option 4 / hybrid.)** Every dialogue turn — including the
  initial input — the skill's persona evaluates four narrowness
  proxies: (a) **component breadth** — does the user name fewer
  than ~3 components / files / modules, anchored to the host
  project's structure read at skill startup; (b) **contract
  shape** — is a single named contract being violated (a
  documented behavior, a runtime invariant, a specification, a
  prior commit's intent), or is the change a design rethink
  (phrasings like "should support", "should handle", "should
  provide" without an existing contract anchor signal design
  rethink); (c) **trigger specificity** — is there a reproduction
  or single user/event flow, or is the problem diffuse /
  aspirational; (d) **surface containment** — does the change
  touch one logical surface (one auth flow, one CLI command, one
  cron job), or does it span multiple surfaces. The skill's
  response is graduated: 4/4 proxies pass → proceed silently;
  3/4 pass → proceed and write `scope_caution: <which proxy
  fired>` into the fix-spec frontmatter; ≤ 2/4 pass → abort the
  skill with a re-route prompt offering `/yoke:discover`. The four
  proxies are encoded in the persona body verbatim (not as a
  sensor) so the dialogue is deterministic in its challenge shape.
- **FR-6a:** The fix-spec frontmatter MUST include the field
  `scope_caution:` — set to the empty string when 4/4 narrowness
  proxies pass, set to the proxy identifier (`component-breadth`,
  `contract-shape`, `trigger-specificity`, or `surface-containment`)
  when 3/4 pass. The Phase-3 acceptance-criteria document for this
  PRD's implementation MUST author at least one Acceptance Criterion
  whose pool sensor scans `.yoke/fixes/<slug>.md` frontmatter for
  `scope_caution:` and (a) flags 3/4-passes for review during Phase
  6 drift sensing, (b) verifies the field exists in every
  fix-spec.
- **FR-7:** The fix-spec template at `templates/fix.md` carries the
  following sections in this order: Title, Generated-by + Status
  metadata + `scope_caution:` field (per FR-6a), Introduction (1–3
  paragraphs of context), What Broke, Reproduction / Trigger,
  Expected Behavior, Observed Behavior, Blast Radius, Root-Cause
  Hypothesis (optional), Functional Requirements (`FR-1`, `FR-2`,
  … — same numbered, sensor-decidable shape as PRD FRs), Non-Goals
  (Out of Scope), Risks, Regression Surface (optional), Open
  Questions.
- **FR-8:** The skill renders the **shared approval menu**
  (`templates/approval-menu.md`) at Trigger 1, identical to
  `/yoke:discover`, with `artifact_path = wm_fix_path "$slug"`,
  `artifact_label = Fix-spec`, `next_skill = /yoke:tech-spec`,
  `binding_statement = empty` (Trigger 1 is non-binding).
- **FR-9:** A new helper `wm_phase1_artifact_path "<slug>"` is
  exported from `lib/working-memory/paths.sh`. It resolves to
  whichever of `wm_prd_path` or `wm_fix_path` exists on disk for
  the slug. **(Resolves OQ-3 with option (δ) — hard abort with
  structured recovery.)** When **both** files exist (ambiguous
  Phase-1 state), the resolver hard-aborts non-zero with a
  `wm:`-prefixed structured diagnostic of the form:

  ```
  wm: ambiguous Phase-1 state for slug '<slug>'

    .yoke/prds/<slug>.md
      first 100 bytes: <excerpt>
      last commit:     <sha> by <author> on <iso8601>
    .yoke/fixes/<slug>.md
      first 100 bytes: <excerpt>
      last commit:     <sha> by <author> on <iso8601>

  Exactly one Phase-1 artifact must exist per slug. Resolve via:
    git rm .yoke/<dir>/<slug>.md && git commit
  or rename one slug. The canonical Phase-1 lifecycle expects
  one of (PRD, fix-spec) per slug, never both.
  ```

  When **neither** exists, the resolver hard-aborts with the same
  `wm:` prefix and a "Run `/yoke:discover` or `/yoke:fix` first."
  remediation. Every downstream skill (`/yoke:tech-spec`,
  `/yoke:acceptance-criteria`, `/yoke:implement`, `/yoke:canonize`,
  `/yoke:status`) switches its Phase-1-artifact reads from
  `wm_prd_path` to `wm_phase1_artifact_path` and inherits the
  abort. No skill downstream of Phase 1 branches its core logic on
  which artifact backed the slug; the artifact is read as opaque
  Phase-1 input. The resolver is the canonical I/O-aware exception
  in `lib/working-memory/paths.sh` — its docstring MUST state that
  the existence-aware contract does NOT propagate to future
  helpers, which remain pure path computers by default.
- **FR-9a:** `wm_set_active "<slug>"` enforces the same "exactly
  one Phase-1 artifact" invariant on write — refuses to record a
  slug whose archives contain both `prds/` and `fixes/` files,
  printing the FR-9 diagnostic verbatim. This is belt-and-suspenders
  against scenarios I and V (cross-branch merge collision; manual
  merge resolution accepting both sides) which bypass FR-4's
  collision check.
- **FR-10:** The plugin manifest exposes the new skill in
  `.claude-plugin/plugin.json` under the same surface area as
  `/yoke:discover` and `/yoke:tech-spec`. The plugin version is
  bumped per Yoke's "each sprint produces an installable plugin
  version" decision.
- **FR-11:** The skill chains into `/yoke:tech-spec` via the `Skill`
  tool on `approve_and_continue` selection in the approval menu —
  same fallback as `/yoke:discover` when the `Skill` tool is
  unavailable (option 1 receives the suffix
  `(manual: run /yoke:tech-spec after this step)`).
- **FR-12:** The skill enforces the v2.0.0 hard break: it sources
  `lib/yoke-prelude.sh` and aborts non-zero with the resolver's
  stderr when `canonical_memory.provider` is missing or empty,
  matching `/yoke:discover`'s pre-flight.

## Non-Goals (Out of Scope)

- Phase-3 exception path. Acceptance-criteria authoring is **not**
  bypassed for fix-shaped tasks. The cycle stays
  fix-spec → tech-spec → acceptance-criteria → implement →
  canonize.
- Generation of a "fix-shaped" tech-spec template. `/yoke:tech-spec`
  consumes the fix-spec exactly as it consumes a PRD; the twelve H2
  sections of the design doc remain authoritative.
- Migration of existing `.yoke/prds/` content to `.yoke/fixes/`.
  Historical PRDs stay where they are; this PRD applies only to
  net-new tasks invoked under `/yoke:fix`.
- Automated detection that picks `/yoke:fix` vs `/yoke:discover` for
  the user. Selection is the user's call. The framework documents
  the rule but does not gate or rewrite invocations.
- Renaming `/fix` to a more general label (e.g. `/yoke:task`,
  `/yoke:narrow`). The user's chosen invocation is `/fix`; broader
  scope (refactor, dependency bump, infra tweak) is captured by
  this skill under the same name.
- Special-casing fix-specs in canonical-memory canonize cascade.
  Concept promotion logic is artifact-agnostic.

## Design Considerations

- The skill's persona prompt body is structurally parallel to
  `/yoke:tech-spec` (Senior Engineer, CTO-style) but opens with
  `**Mode:** diagnose-first` (vs `/yoke:tech-spec`'s
  `**Mode:** design-first`) and tests a different four-check set:
  *what broke / repro / expected / blast radius* in place of
  tech-spec's *stack-fit / framework-trade-offs / sprint-partition*.
- The four readiness checks (FR-5) are encoded as a single LLM
  evaluation, not as four sequential heuristic gates. The skill's
  dialogue body describes the checks as bullets the persona reads
  off before deciding: "ready → draft" or "missing X, Y → ask only
  about X, Y".
- The four narrowness proxies (FR-6) are evaluated *every dialogue
  turn* — not just on initial input. Mid-dialogue scope inflation
  (a bug bump that grows into a 4-call-site refactor) re-evaluates
  the proxies and re-routes when the threshold trips. Encoded
  verbatim in the persona body, anchored to host-project structure
  read at skill startup.
- The lettered-options format (`templates/approval-menu.md` §usage)
  applies to clarification questions where the option set is
  enumerable (e.g. blast-radius bands: A. single function, B. one
  module, C. cross-module, D. cross-service). Free-form questions
  are reserved for what-broke / repro / expected when no option set
  fits.
- `templates/fix.md` is a new template file modeled structurally on
  `templates/prd.md`, not a fork. Sections that exist in the PRD
  template only because of product framing (Audience, Success
  Metrics in the success-metric sense, Design Considerations)
  collapse into a single "Blast Radius + Regression Surface" pair.
  Frontmatter carries the `scope_caution:` field (FR-6a) alongside
  Status / Approved-by / Approved-at.
- The `**Mode:**` tag convention (FR-2) is documented in
  `concepts/yoke-conventions` via the canonize handoff. Initial
  vocabulary is open: `diagnose-first` and `design-first` are the
  two ratified values; future engineering-flavored skills may
  append values (e.g. `review-first`, `stabilize-first`,
  `rollback-first`) without re-ratification.

## Technical Considerations

### Technical

- The `wm_phase1_artifact_path` resolver belongs in
  `lib/working-memory/paths.sh` to keep working-memory path
  resolution centralized — the canonical-memory code never imports
  `lib/working-memory/`, so the helper does not break the layered
  separation. The resolver is the **canonical I/O-aware exception**
  in the helper layer; its docstring MUST explicitly state that the
  existence-aware contract does not propagate to future helpers
  (which remain pure path computers by default). The resolver's
  contract: returns the existing path with exit 0; hard-aborts
  non-zero on "neither" or "both" with the FR-9 structured
  diagnostic verbatim. Read paths and write paths inherit the abort
  uniformly — no read-vs-write split.
- `wm_set_active` (FR-9a) gates a second time on write: it refuses
  to record a slug whose archives violate the "exactly one Phase-1
  artifact" invariant, printing the FR-9 diagnostic verbatim. This
  is belt-and-suspenders against scenarios I and V (cross-branch
  merge collision; manual merge resolution accepting both sides)
  which bypass FR-4.
- The five downstream skills (`/yoke:tech-spec`,
  `/yoke:acceptance-criteria`, `/yoke:implement`, `/yoke:canonize`,
  `/yoke:status`) must be edited in the same change to consume
  `wm_phase1_artifact_path`. A grep audit must confirm zero residual
  `wm_prd_path` reads outside `/yoke:discover` and the new
  `/yoke:fix`.
- Every downstream skill's pre-flight error message must update its
  remediation hint from "Run `/yoke:discover` first." to "Run
  `/yoke:discover` or `/yoke:fix` first." or equivalent — verbatim
  user-facing strings need an audit.
- A new test under `tests/sensors/no-direct-prd-path.test.sh`
  grep-audits the `skills/` tree for `wm_prd_path` reads outside
  the two Phase-1 authoring skills. New skills added without
  awareness of the migration trip the sensor.

### Regulatory

- None. The skill is internal tooling for Yoke users; no PII is
  handled, no logging surface is changed.

### Organizational

- The skill ships in the plugin's next minor or major version
  depending on the breaking-change classification of the
  `wm_phase1_artifact_path` migration. Downstream skills' read sites
  switch from `wm_prd_path` to the new resolver — that is a
  signature change in the plugin's internal contract, not a public
  API. Per Yoke's "each sprint produces an installable plugin
  version" decision, this PRD's implementation is one sprint.

## Risks

- **Persona-name collision with `/yoke:tech-spec`** — Both skills
  declare the literal "Senior Engineer persona". Resolved by
  OQ-2 / option (c): each skill's persona body opens with a
  `**Mode:**` tag (FR-2) so the disambiguation is structural, not
  naming-dependent. The 2026-04-25 literal-naming decision is
  amended via the canonize handoff to bless uniformity-with-mode-tag
  as the canonical pattern. Signal still worth watching: a future
  engineering skill skips the Mode tag and reintroduces the
  ambiguity. Mitigation: the Phase-3 acceptance-criteria grill
  authors at least one criterion that scans persona bodies for
  the Mode tag's presence and shape.
- **Mission creep — `/yoke:fix` becomes universal Phase-1 backdoor**
  — Without an enforceable threshold, every user types `/yoke:fix`
  for any small change to skip the PM grill. Resolved by OQ-1 /
  option 4 (hybrid graduated refusal): FR-6 evaluates four
  narrowness proxies every dialogue turn and aborts with re-route
  to `/yoke:discover` when ≤ 2/4 pass; FR-6a writes
  `scope_caution:` into the fix-spec frontmatter when 3/4 pass.
  Signal still worth watching: fix-specs whose `scope_caution:`
  field is populated *and* whose body still smells like a PRD
  after the gate let it through. Mitigation: Phase-6 drift sensor
  that LLM-judges fix-specs against the four proxies post-hoc and
  flags scope-cautioned ones for review.
- **Dual Phase-1 path invites both-files state** — A user could in
  theory create both `.yoke/prds/<slug>.md` and
  `.yoke/fixes/<slug>.md` with the same slug (or, worse, with
  semantically equivalent slugs that satisfy the regex but slip
  past collision detection). Resolved by OQ-3 / option (δ): FR-9
  hard-aborts with a structured recovery diagnostic (paths +
  excerpts + commit shas + recipe); FR-9a gates `wm_set_active`
  on write as belt-and-suspenders. The realistic scenarios (I:
  cross-branch merge; V: manual merge resolution accepting both)
  bypass FR-4 but trip FR-9 / FR-9a immediately. Signal: a real
  run produces the `wm: ambiguous Phase-1 state` diagnostic.
  Mitigation: the diagnostic itself is the mitigation — a
  Phase-3 acceptance criterion scans CI runs for the substring
  and fails the build if found in main-branch pipelines.
- **Downstream skill grep-audit gap** — A future skill added without
  awareness of the `wm_phase1_artifact_path` migration imports
  `wm_prd_path` directly and breaks for fix-spec-backed tasks.
  Signal: implementation of a new skill that reads working memory
  fails for the first user with a fix-spec slug. Mitigation: add a
  `tests/sensors/` smoke that grep-audits the skills/ tree for
  `wm_prd_path` reads outside `/yoke:discover`; flag any new
  reads as a sensor failure.
- **PRD vs fix-spec collision in canonical-memory canonize cascade**
  — The canonize skill walks Phase-1 artifacts when classifying
  promotion candidates. If fix-spec content (which deliberately
  lacks success-metric and audience framing) is fed into a cascade
  step that expects PRD-shaped content, the cascade may emit
  malformed promotion proposals. Signal: a canonize run on a
  fix-spec-backed task surfaces empty `actor_name` or
  `success_metric` fields in the proposal. Mitigation:
  `/yoke:canonize` reads the artifact opaquely (FR-9 invariant); if
  the cascade has hidden assumptions about PRD shape, those need
  to be documented and either relaxed or made fix-spec-aware in a
  follow-up PRD.

## Success Metrics

- For fix-shaped tasks where the user submits a shaped problem
  statement (4/4 readiness checks pass on initial input), Trigger 1
  is reached in **zero** dialogue rounds — measurable via
  `.yoke/runtime/progress.md` event counts during the skill's
  execution.
- The fraction of `.yoke/fixes/<slug>.md` artifacts that survive
  Phase-6 drift sensing without a "looks-like-a-PRD" signal stays
  above 90% over the first 20 fix-shaped tasks.
- Zero downstream-skill regressions: every PRD-backed task that
  worked before this change still reaches Trigger 5 with no path
  errors after the migration.
- The added Phase-1 surface area does not measurably degrade
  `/yoke:discover` adoption for genuine product features —
  observable via the ratio of new `.yoke/prds/` vs `.yoke/fixes/`
  artifacts over the first month, which should reflect actual work
  composition rather than skipping discovery wholesale.
