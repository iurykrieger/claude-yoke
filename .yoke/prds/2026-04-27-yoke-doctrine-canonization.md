## Product invariants

What must hold regardless of implementation. Non-negotiable.

- **`.yoke/` is working memory only.** `.yoke/` (per-task, archives versioned, `runtime/` gitignored) MUST NOT hold pattern, decision, policy, or convention content for the framework. Doctrine that should outlive a task lives in canonical memory (`iurykrieger/brain`). The PRD's title says "absorb into `.yoke/`" colloquially; the actual destination is canonical memory, with `.yoke/` only as the per-task scratchpad for executing the migration.
- **Same vault, retrieval-scoped by frontmatter tag.** Yoke's framework doctrine writes into `iurykrieger/brain` using the existing Bedrock-vault structure: `projects/claude-yoke.md` for the project entity, `actors/yoke.md` for the framework as an actor, and one entity in `concepts/` per pattern / decision / policy. **The retrieval-scoping primary is the frontmatter tag `tags: [yoke-framework]`** — every Yoke-doctrine entity carries it, every `/yoke:ask` query from this repo filters on it. Filenames stay semantically specific to avoid collisions with unrelated vault content (e.g., `concepts/yoke-runtime-roles.md`, not `concepts/role.md`), but filename prefixing is documentation, not retrieval. No new top-level folder; we adapt to the vault that already exists.
- **One-shot, not generic.** This is a single ingestion of THIS repo's `.vibeflow/`. The deliverable is the migrated content + the agent-skill cutover, not a reusable Vibeflow-to-Bedrock framework.
- **Dogfood the full Yoke flow.** This PRD is itself the test of Yoke v1.1. The migration is executed via `/yoke:discover` (this turn) → `/yoke:tech-spec` → `/yoke:acceptance-contract` → `/yoke:implement` → `/yoke:preserve`. If at any phase the framework cannot carry its weight and we fall back to manual `.vibeflow/` edits, the PRD has failed — that is the falsifiable signal.
- **Canonical-memory writes go through the Orchestrator under Model C.** No agent in the runtime loop writes directly to the vault. The `/yoke:implement` Generator may write to `.yoke/` working memory and stage proposals; canonization happens via `/yoke:preserve` post-loop, using `/yoke:teach` for content ingestion and Model C governance for ratification.
- **`.vibeflow/` is frozen as of this PRD and DELETED at end of v0.** All future task scratchpads write to `.yoke/` (per-task working memory). All future doctrine writes go through `/yoke:preserve` to canonical memory. During v0, `.vibeflow/` is read-only source-of-truth for the migration. v0 ends with `.vibeflow/` removed from the working tree (git history preserves it). The "no new writes" rule outlives v0 — it is the operating rule for every subsequent Yoke change.
- **Zero `.vibeflow/` references in framework code at end of v0.** Every skill, agent, hook, lib, and template under `skills/`, `agents/`, `hooks/`, `lib/`, `templates/` MUST NOT contain a path reference to `.vibeflow/` (anywhere — comments, examples, prose, or executable code). The `tests/`, `examples/`, `docs/lineage.md`, and the project's `CLAUDE.md` may retain historical references where appropriate (e.g., `lineage.md` documenting the Vibeflow fork). The Validator enforces this with a sensor that greps the framework surface; non-zero matches fail the Acceptance Contract.

## Migration mapping (Q1 resolved)

This is the entity-mapping decision the dialogue delegated to the
Generator persona. The tech-spec inherits these as fixed inputs and
turns them into per-task work; it does not re-litigate the mapping.

### What goes into canonical memory (`iurykrieger/brain`)

- **`projects/claude-yoke.md`** — the project entity. Contains repo URL,
  manifesto reference, sprint cadence, current version, status, and a
  backlinks index to every Yoke-doctrine concept entity. Created if
  absent; updated otherwise.
- **`actors/yoke.md`** — the framework as an actor. Persona-style
  description of Yoke (what it does, how it operates, how it relates
  to agents, vaults, and humans). Backlinks from every role concept.
  Created if absent.
- **`concepts/yoke-pattern-NAME.md`** — one entity per `.vibeflow/patterns/*.md`
  doc. Nine entities (the full set, by final filename):
  `yoke-pattern-acceptance-contract`, `yoke-pattern-human-triggers`,
  `yoke-pattern-memory-model`, `yoke-pattern-model-c-governance`,
  `yoke-pattern-phase-flow`, `yoke-pattern-plugin-structure`,
  `yoke-pattern-ralph-loop`, `yoke-pattern-roles`,
  `yoke-pattern-sensors`. Frontmatter carries `kind: pattern`. Body
  is the doc verbatim, lightly adapted for vault-context (backlinks,
  lifted asides).
- **`concepts/yoke-decision-DATE-NAME.md`** — one entity per
  decision in `.vibeflow/decisions.md`. Naming follows the form
  `yoke-decision-2026-04-25-three-runtime-subagents` (date prefix
  preserved from the original decision; kebab-case slug derived from
  the decision title). Frontmatter carries `kind: decision`, the
  original ratification date preserved verbatim under `ratified`, a
  `status` field of either `active`, `superseded`, or `deprecated`,
  and explicit `supersedes:` / `superseded_by:` backlinks where
  applicable. Superseded decisions are migrated as deprecated
  entities, not omitted — the supersession history is part of
  doctrine.
- **`concepts/yoke-conventions.md`** — one entity for the conventions
  doc as a whole, `kind: policy`. The doc is multiple rules; splitting
  per rule is deferred to a follow-up migration if individual rules
  ever need to be queryable. Not v0 work.
- **`discussions/yoke-audit-SPEC-DATE.md`** — one entity per
  `.vibeflow/audits/*.md` after-action report (e.g.,
  `discussions/yoke-audit-runtime-only-agents-2026-04-25`). Routes to
  `discussions/` (persistent learnings) rather than `fleeting/`
  (ephemeral). These become drift-sense input later.

### What goes into `.yoke/` working memory

- **`.yoke/specs/`** — every file in `.vibeflow/specs/` migrates
  here as a working-memory archive. The slug for each migrated file
  is the file's first git-commit date in `YYYY-MM-DD` form, joined by
  a hyphen to the original filename stem (e.g., a spec first committed
  on 2026-04-25 with stem `runtime-only-agents-part-1` becomes
  `.yoke/specs/2026-04-25-runtime-only-agents-part-1.md`). The slug
  must satisfy `wm_validate_slug` (≤50 chars after the date prefix;
  the tech-spec defines the truncation rule for any name that exceeds
  that limit).
- **`.yoke/prds/`** — every file in `.vibeflow/prds/` migrates the
  same way. Twelve files. Same slug derivation. The current PRD
  (`2026-04-27-yoke-doctrine-canonization.md`) already lives here
  and is unaffected.
- Audit files do NOT go to `.yoke/`. They route to canonical memory
  under `discussions/` (see above) — that is the only sensible
  destination for after-action learnings.

### What does NOT migrate as a standalone artifact

- **`.vibeflow/index.md`** — project-state snapshot. Its content
  is split: status / structure / structural units belong in CLAUDE.md
  and `projects/claude-yoke.md`; nothing migrates as a standalone
  concept. The `index.md` file itself becomes redundant after the
  project entity is populated.

### Frontmatter contract for every Yoke-doctrine entity

```yaml
---
kind: pattern | decision | policy | role | phase | sensor
tags: [yoke-framework]                # primary retrieval-scoping mechanism
ratified: 2026-MM-DD                  # original ratification date (preserved verbatim from .vibeflow/)
last_validated: 2026-04-27            # date of migration / last verification
traceability: free-text or backlinks to motivating decision/audit/spec
status: active | deprecated | superseded
project: claude-yoke                  # backlink to projects/claude-yoke.md
---
```

The exact frontmatter shape is final; the tech-spec may add fields,
not remove them.

### Tooling

- **Content ingestion:** `/yoke:teach` against the `.vibeflow/` directory
  in slices, validated by `/yoke:ask` round-trips before expanding.
  Throwaway shell glue is permitted; a reusable `.vibeflow → Bedrock`
  framework is anti-scope.
- **Spec/PRD migration:** mechanical `git mv` for each file from
  `.vibeflow/specs/` to `.yoke/specs/` (and same for prds/), renaming
  to the date-prefixed slug derived from each file's first-commit
  date. The Generator may script this in a single bash pass; no LLM
  judgment required.
- **Cutover:** every skill / agent / hook / lib / template reference
  to `.vibeflow/patterns/*`, `.vibeflow/decisions.md`,
  `.vibeflow/index.md`, `.vibeflow/specs/*`, or `.vibeflow/prds/*`
  rewrites to either a `/yoke:ask` invocation (for doctrine) or a
  path under `.yoke/specs/` or `.yoke/prds/` (for project history).
  Surface enumeration produces a concrete file list as a tech-spec
  deliverable.
- **Validation:** an automated grep — invocable from a sensor — that
  fails the Acceptance Contract if any file under `skills/`, `agents/`,
  `hooks/`, `lib/`, or `templates/` contains the literal string
  `.vibeflow/`. `tests/`, `examples/`, `docs/lineage.md`, and the
  project's `CLAUDE.md` are exempt.
- **Final deletion:** `git rm -rf .vibeflow/` runs as the LAST step
  of v0, after every other criterion is green. Once the directory is
  removed, the validation grep above is reinforced by the directory's
  absence.

## Business context

Yoke v1.1 ships with the full plugin layout, three runtime subagents, the
ralph loop, sensors, and the canonization skills — but **its own design
doctrine is not in canonical memory**. The patterns, decisions,
conventions, and audits that govern how Yoke is built live in `.vibeflow/`,
which is Vibeflow's working-memory format, not Yoke's canonical-memory
substrate. This is the artifact of a deliberate v1.0 choice (per
`.vibeflow/decisions.md`: "Yoke v1.0 is built without running Yoke on
itself — manual bootstrap"). The choice was correct then; the cost is now
visible.

Three concrete consequences of leaving doctrine in `.vibeflow/`:

1. **`/yoke:ask` returns nothing useful inside this repo.** A canonical
   query against `iurykrieger/brain` for "what's the role of the
   Validator at runtime?" hits a vault that doesn't know about the
   Yoke framework. The skill is wired but data-starved for self-queries.
2. **Doctrine drifts silently.** Decisions in `decisions.md` lack the
   ratification frontmatter, last-validation dates, and traceability
   metadata that canonical-memory entries carry. `/yoke:drift-sense`
   has no Yoke-doctrine target to scan against. Pruning candidates can't
   be identified because nothing has decay metadata.
3. **Yoke v1.1 cannot dogfood Yoke.** Building Yoke v1.2+ via Yoke
   itself requires `/yoke:ask` to return real doctrine. Without this
   migration, every new Yoke change still has to read `.vibeflow/`
   directly — the framework's own users (starting with the maintainer)
   bypass the framework. That is the canonical sign of a broken
   dogfood.

The migration is the trigger to flip this. After v0 of this PRD ships:
the maintainer building Yoke v1.2+ runs `/yoke:discover` → … → `/yoke:preserve`
end-to-end, with `/yoke:ask` queries returning live doctrine, with
canonization writes flowing into `iurykrieger/brain` under Model C, with
`/yoke:drift-sense` having a real corpus to monitor. **Yoke building Yoke
becomes the default operating mode** rather than a planned future.

The "why now" is that the immediate next round of Yoke work (Sprint 8 CI
gate, drift-sense calibration, post-v1.0 features) is meaningfully easier
to do *inside* the framework than alongside it.

## Known constraints

What the implementation must respect, grouped by source.

### Technical

- **Bedrock-vault entity model.** `iurykrieger/brain` is a Bedrock-style
  Second Brain with entity types `concept`, `actor`, `project`,
  `person`, `team`, `topic`, `discussion`, `fleeting`. The migration
  must MAP each `.vibeflow/` artifact to a fitting entity type, not dump
  files verbatim. The mapping itself is part of the tech-spec deliverable.
- **`/yoke:ask` is the only read path.** No skill or agent reads the vault
  directly via `cat`, `grep`, or git tooling. The `lib/canonical-memory/`
  helpers and the `/yoke:ask` skill mediate every read. This applies to
  the migration tooling itself: validation queries during implementation
  go through `/yoke:ask`.
- **`/yoke:preserve` and `/yoke:teach` are the only write paths.**
  `/yoke:teach` ingests external sources (including local Markdown
  directories like `.vibeflow/`); `/yoke:preserve` is the single
  governed write point under Model C. The migration uses `/yoke:teach`
  for content ingestion and `/yoke:preserve` for canonization of
  learnings produced *by* the migration (e.g., refined patterns).
- **Working-memory path discipline.** All `.yoke/` paths construct via
  `lib/working-memory/paths.sh` (`wm_*_path`). No flat or hand-built
  paths.
- **CLAUDE.md rewrite scope.** The host repo's `CLAUDE.md` currently
  points agents at `.vibeflow/` for doctrine. After v0 ships, agents
  must be redirected to query `/yoke:ask` instead. The rewrite is part
  of the deliverable, not a side-effect.
- **Skill / agent surface that reads `.vibeflow/`.** Every existing
  `skills/*/SKILL.md` and `agents/*.md` that references
  `.vibeflow/patterns/*.md`, `.vibeflow/decisions.md`, or
  `.vibeflow/index.md` must be updated to query canonical memory
  instead. The tech-spec must enumerate the surface in advance — this
  is a real fan-out.

### Regulatory

- None. Yoke is a development framework; no PCI / LGPD / HIPAA scope.

### Organizational

- **Single maintainer.** This PRD's audience is the maintainer
  (iurykrieger). No other reviewers, no veto windows from other teams.
  Model C ratification simplifies to "maintainer approves the PR" for
  every canonization class.
- **No external coordination.** The migration touches only `iurykrieger/brain`
  (already owned by the maintainer) and this repo. No shared
  infrastructure, no cross-team dependencies.

## Risks

What could go wrong. Each risk has an observable signal and a mitigation
hint. The Validator may consume these in Phase 3 for sensor calibration.

- **Entity-model mismatch.** A `.vibeflow/` artifact (e.g., `decisions.md`)
  doesn't fit cleanly into Bedrock entity types and forces lossy
  conversion. Signal: a tech-spec task cannot specify a destination
  entity type without ambiguity, OR `/yoke:ask` queries return content
  that lost the original artifact's structure (e.g., decision context
  collapsed into a single paragraph). Mitigation: lock the mapping in
  tech-spec; for one-off shapes (decision log), use `concept` entities
  with explicit `kind: decision` frontmatter rather than forcing them
  into existing types.
- **Doctrine co-mingling with personal Stone work.** `iurykrieger/brain`
  has Stone work content. Writing Yoke doctrine into the same vault
  means `/yoke:ask` queries from this repo could return Stone-context
  results. Signal: a `/yoke:ask` query about a Yoke pattern returns
  hits from another project's folder under `projects/` or an unrelated
  person's folder under `people/` or `actors/`. Mitigation: every Yoke
  entity carries `tags: [yoke-framework]` in frontmatter; every
  `/yoke:ask` invocation issued from inside this repo filters on that
  tag. The mechanism is locked in the Migration-mapping section.
- **Cutover incompleteness.** v0 migrates content but a skill or agent
  somewhere still reads `.vibeflow/` directly. Signal: an automated
  scan finds at least one live reference to `.vibeflow/patterns/`,
  `.vibeflow/decisions.md`, or `.vibeflow/index.md` in `skills/`,
  `agents/`, or `lib/`. Mitigation: tech-spec includes a binary
  acceptance criterion "zero `.vibeflow/` references in live code"
  and a sensor that enforces it.
- **`/yoke:teach` ingestion fails or produces unusable entities.**
  `/yoke:teach` is a real skill but has not been exercised against
  `.vibeflow/`-style content at scale. Signal: ingestion produces
  malformed frontmatter, missing backlinks, or empty bodies for
  some artifacts. Mitigation: ingest a small slice first (e.g., one
  pattern doc), validate via `/yoke:ask` round-trip, then expand.
  This is a tech-spec sequencing decision.
- **Recursive failure of dogfood.** A Yoke phase fails during this
  PRD's own execution (e.g., `/yoke:tech-spec` produces an unworkable
  spec; `/yoke:implement`'s ralph loop diverges with no resolution).
  Signal: at any phase, the maintainer falls back to manual editing of
  `.vibeflow/`, `.yoke/`, or vault entities to make progress.
  Mitigation: this risk is itself the v0 falsifiability signal — if
  it fires, v0 has failed, and the failure becomes input to a
  follow-up Yoke fix. Document each fallback as a structured failure
  trace for canonization in `/yoke:preserve`.
- **Co-mingled vault ratification ambiguity.** A canonization PR
  against `iurykrieger/brain` carries Yoke doctrine + arbitrary other
  Stone work content in unrelated commits. Signal: the canonization
  PR's diff touches files outside the Yoke namespace. Mitigation:
  every canonization PR for this PRD must touch only Yoke-namespaced
  paths. The Orchestrator skill (`/yoke:preserve`) enforces this in
  Model C classification.

## Anti-scope

Explicitly NOT in v0. Confirmed during the discovery dialogue (Round 3).

- **No generic `.vibeflow → Bedrock-vault` migration framework.** This
  PRD is a one-shot ingestion of THIS repo's `.vibeflow/`. Reusable
  tooling (format detection, plugin adapters, multi-vault support) is
  out of scope. A throwaway script or `/yoke:teach` invocations are
  fine; a framework is not the deliverable.
- **No new writes to `.vibeflow/`, ever.** Product invariant restated
  as anti-scope: from `/yoke:tech-spec` onward, every task scratchpad
  goes to `.yoke/` and every doctrine write goes through `/yoke:preserve`
  to canonical memory. The runtime loop and every future Yoke change
  inherit this rule. (Note: deletion of the entire `.vibeflow/`
  directory IS in v0 scope — see Migration mapping. The previous
  draft's "no deletion" anti-scope was reversed by the user during
  Q5 resolution.)
- **No partial deletion before validation.** v0 deletes `.vibeflow/`
  in a single step at the END of the implement phase, after every
  Acceptance Contract criterion is green (every entity round-trip
  validated, every framework file rewritten, every spec/PRD migrated).
  Incremental deletion as files are migrated is anti-scope — it
  removes the source-of-truth comparison artifact mid-flight.
- **No migration of `.vibeflow/specs/` and `.vibeflow/prds/` as
  canonical-memory doctrine.** Those are sprint-history artifacts —
  they are project-task working memory, not pattern/decision/policy
  content. They migrate to `.yoke/specs/` and `.yoke/prds/` (working
  memory archives), NOT to `concepts/` in the vault. Audits are the
  exception: they route to `discussions/` because after-action
  learnings ARE doctrine.
- **No new vault.** We are not creating `iurykrieger/yoke-canonical-memory`
  or any other separate substrate. Decision: one vault, namespaced.
- **No retro-canonization of past Yoke v0.x decisions beyond what
  `.vibeflow/decisions.md` already contains.** The migration ports
  what exists; it does not re-litigate or invent decision history.
- **No changes to the Bedrock skills (`bedrock:*`) themselves.** Yoke
  uses the canonical-memory layer through `/yoke:ask` / `/yoke:preserve`
  / `/yoke:teach`; the upstream Bedrock skills are out of scope.
