# PRD: Tech Spec as Design Doc — stack negotiation, architecture-first, no task generation

> Generated by `/yoke:discover` on 2026-05-03.
> Status: approved
> Approved by: iurykrieger
> Approved at: 2026-05-03T06:24:39Z

## Introduction / Overview

The current `/yoke:tech-spec` skill (Yoke v3.0.0) is technically shallow
and silently entangles two phases. It does not ask the user about stack
choice, does not negotiate architecture against either organizational
canonical memory or industry practice, and produces a spec template
that lacks the canonical sections expected of a software design
document (Context/Scope, Goals/Non-Goals, System Context, Architecture,
Stack & Dependencies, Non-Functional Requirements, Alternatives
Considered, Trade-offs, Cross-cutting Concerns). Worse, it already
generates `### Task <ID>` anchors and per-sprint runtime bundles in
Phase 2 — so the binding sprint partition and task breakdown happen
**before** the Acceptance Contract decides what "done" means in
measurable terms. That ordering is upside-down: tasks should be carved
against ratified BDD scenarios, not against an unratified spec.

The user (this repo's maintainer) is hitting four concrete pains while
dogfooding Yoke on real features: (1) stack is implicit, never
surfaced; (2) architectural decisions are not questioned against
known patterns; (3) the produced spec is light on technical content
and the user stories from the PRD are not lifted with technical depth;
(4) Phase 2 already generates tasks, atrophying the role of Phase 3.

This PRD reshapes Phase 2 into an architecture-first **design doc**
(in the Google design-doc / Stack Overflow practical-spec / MADR ADR
sense) and defers sprint partition + task breakdown into Phase 3,
where the Acceptance Contract drives them.

## Goals

- The skill negotiates a stack choice with the user via a curated menu
  of market-default options by feature category, plus auto-detection
  of the host project's existing stack as the default offer, plus an
  `Other:` free-text escape.
- The skill consults canonical memory for applicable architectural
  patterns first; when fewer than 3 applicable patterns return (or
  zero), the skill falls back to a `WebSearch` for industry patterns
  and presents the top 2-3 with explicit trade-offs.
- The produced spec follows the canonical 12-section design-doc
  shape (Context/Scope, Goals/Non-Goals, System Context, Architecture,
  Stack & Dependencies, APIs and Data Model, Non-Functional
  Requirements, Alternatives Considered, Trade-offs, Cross-cutting
  Concerns, Technical Use Cases, Open Questions).
- Each PRD `US-###` is lifted into a Technical Use Cases entry that
  explicitly names the components touched, contracts used, NFRs
  applied, and edge cases covered.
- The spec is the architectural-decision record: there is no separate
  ADR file. The spec body itself encodes the Nygard / MADR shape
  (context, decision, alternatives, consequences) across its sections.
- The skill produces exactly **one** file at `.yoke/specs/<slug>.md`
  and **zero** files under `.yoke/sprints/`. No `### Task <ID>`
  anchors appear in spec output.
- Phase 3 (`/yoke:acceptance-contract`) absorbs sprint partition and
  task breakdown after drafting the binding BDD scenarios. The
  Acceptance Contract is drafted first; sprint+task generation
  follows in the same skill.

## Product invariants

These are non-negotiable shape constraints. They survive verbatim
into the Acceptance Contract and bind every sprint of the
implementation.

- The tech-spec is a single coherent file at `.yoke/specs/<slug>.md`.
  No sibling sprint files. No inline tasks.
- The tech-spec carries quantifiable Non-Functional Requirements
  (latency in milliseconds, availability as a percentage,
  throughput as requests per second, etc.). Adjective-only NFRs
  ("performant", "secure", "reliable") are rejected.
- Every entry under "Alternatives Considered" carries (a) the
  alternative name, (b) at least one trade-off vs. the chosen
  approach, (c) the explicit reason for rejection. Vague
  "considered other options" entries fail review.
- Every entry under "Technical Use Cases" cites a `US-###` from the
  approved PRD verbatim and lists, at minimum: components involved,
  contracts used, NFRs applied, edge cases.
- Stack negotiation is mandatory. The skill never silently picks the
  stack from canonical memory or from auto-detection — auto-detection
  populates the default, but the user must confirm explicitly.
- WebSearch is fallback-only, gated by a canonical-pattern threshold
  (default 3, configurable). Never always-on.
- Phase 2 never writes to `.yoke/sprints/`. Phase 3 owns sprint and
  task generation. Violations abort the skill non-zero.

## User Stories

### US-001: stack negotiation with auto-detect + market menu

**Description.** As an engineer running `/yoke:tech-spec` on an
approved PRD, I want the skill to (a) auto-detect the host project's
stack from manifest files and (b) present a curated menu of
market-default stacks by feature category with the auto-detected
stack pre-selected as the default and an `Other:` escape, so that
my stack choice is explicit and informed instead of implicit.

**Acceptance criteria:**

- [ ] Skill reads at least these manifest files when present:
  `package.json`, `go.mod`, `Cargo.toml`, `requirements.txt`,
  `pyproject.toml`, `pom.xml`, `Gemfile`. The detected stack
  signature populates the dialogue's default offer.
- [ ] Skill prints a 4-line stack menu of the form `1A./1B./1C./1D./Other:` keyed by feature category (web-api, web-ui, cli, library, data-pipeline) with 3-5 lettered options + the `Other:` escape.
- [ ] When at least two manifest types are detected, the skill does
  not auto-pick — it lists every detected stack as a candidate and
  the user must reply.
- [ ] Typecheck / lint passes.

### US-002: canonical-memory-first architecture, WebSearch as fallback

**Description.** As an engineer running `/yoke:tech-spec`, I want the
skill to query canonical memory for applicable architectural patterns
**before** drafting the spec, and only fall back to WebSearch when
canonical memory returns fewer than the configured threshold of
applicable pattern entities, so that organizational doctrine is
preferred over generic industry text and external research is reserved
for genuine gaps.

**Acceptance criteria:**

- [ ] Skill invokes `/yoke:search-canonical-memory` with a query
  scoped to the feature's domain (lifted from the PRD's
  Introduction / Overview).
- [ ] When the canonical-memory response surfaces ≥ 3 applicable
  pattern entities, the skill uses those and skips WebSearch.
- [ ] When the canonical-memory response surfaces < 3 applicable
  pattern entities, the skill invokes `WebSearch` with a targeted
  query for the feature's domain and presents the top 2-3 industry
  patterns inline with trade-offs.
- [ ] The threshold (default 3) is overridable via
  `.yoke/config.yaml :: overrides.tech_spec.canonical_pattern_threshold`.
- [ ] The "Alternatives Considered" section of the produced spec
  cites both canonical-memory pattern entities and any WebSearch
  sources actually used.
- [ ] Typecheck / lint passes.

### US-003: design-doc shape

**Description.** As a downstream consumer (Phase 3 Validator persona,
Phase 4 council personas, human reviewer at Trigger 2), I want the
spec to follow the canonical design-doc shape so that the artifact
reads as an architectural decision record, not a sprint plan.

**Acceptance criteria:**

- [ ] Generated spec contains exactly these H2 sections, in this
  order: `## Context and Scope`, `## Goals and Non-Goals`,
  `## System Context`, `## Architecture`, `## Stack and Dependencies`,
  `## APIs and Data Model`, `## Non-Functional Requirements`,
  `## Alternatives Considered`, `## Trade-offs`,
  `## Cross-cutting Concerns`, `## Technical Use Cases`,
  `## Open Questions`.
- [ ] Each Non-Functional Requirement entry carries a quantitative
  target (e.g., "p95 latency < 200ms", "availability ≥ 99.9%").
- [ ] Each Alternatives Considered entry carries an alternative
  name, ≥ 1 trade-off vs. the chosen approach, and an explicit
  reason for rejection.
- [ ] The spec carries no `### Task <ID>` anchor.
- [ ] Typecheck / lint passes.

### US-004: technical use cases lifted from PRD

**Description.** As a Phase 3 Validator drafting BDD scenarios, I
want each PRD `US-###` to appear in the spec's "Technical Use Cases"
section with explicit technical context (components, contracts,
NFRs, edge cases) so that BDD scenarios can be drafted against
unambiguous technical anchors.

**Acceptance criteria:**

- [ ] Generated spec's "Technical Use Cases" section contains one
  subsection per PRD `US-###`, headed `### US-### — <story title>`.
- [ ] Each subsection lists, at minimum: **Components involved**,
  **Contracts used**, **NFRs applied**, **Edge cases**.
- [ ] No PRD `US-###` is silently dropped. If the spec author
  intends to defer one, that subsection states `Deferred: <reason>`
  and surfaces the deferral in `## Open Questions`.
- [ ] Typecheck / lint passes.

### US-005: no sprint or task generation in Phase 2

**Description.** As an engineer running `/yoke:tech-spec`, I want
the skill to NOT create any sprint files and NOT emit any
`### Task <ID>` anchors in the spec body, so that the binding
sprint+task partition is decided in Phase 3 against ratified BDD
scenarios, not in Phase 2 against an unratified spec.

**Acceptance criteria:**

- [ ] Skill exits 0 with exactly one file written at
  `.yoke/specs/<slug>.md`. No file is created under
  `.yoke/sprints/`.
- [ ] Spec body matches `not contains "### Task "` (regex / grep).
- [ ] On `revise` at Trigger 2, only `.yoke/specs/<slug>.md` is
  deleted (no sprint files exist at this point to delete).
- [ ] Typecheck / lint passes.

### US-006: Phase 3 absorbs sprint+task generation

**Description.** As an engineer running `/yoke:acceptance-contract`,
I want Phase 3 to draft the binding BDD scenarios first and then,
after drafting, partition the work into sprints with task anchors —
so that "what is built" and "in what increments it ships" are
decided together against measurable criteria.

**Acceptance criteria:**

- [ ] `/yoke:acceptance-contract` reads the approved single-file
  spec and the approved PRD; no sprint files are required as input.
- [ ] Skill drafts BDD scenarios first (one per PRD `US-###` and per
  `FR-N`, mapped through the spec's Technical Use Cases).
- [ ] After BDD drafting, the skill partitions the work into ≥ 1
  sprint and writes `.yoke/sprints/<slug>-s<NN>.md` files with
  `### Task <ID>` anchors carrying the four labels (`Story`,
  `Technical implementation`, `Validation`, `Acceptance criterion`)
  per the existing `templates/sprint.md` shape.
- [ ] Trigger 3 covers the contract **and** every sprint file
  together. Partial state (contract drafted, sprint files missing)
  aborts the skill non-zero before the menu renders.
- [ ] On `revise`, the skill deletes the contract and every sprint
  file for the slug before re-running.
- [ ] Typecheck / lint passes.

## Functional Requirements

- **FR-1:** `/yoke:tech-spec` must auto-detect the host project's
  stack by reading at least these manifest files when present:
  `package.json`, `go.mod`, `Cargo.toml`, `requirements.txt`,
  `pyproject.toml`, `pom.xml`, `Gemfile`. The detection result
  populates the default offer in the stack-negotiation dialogue.
- **FR-2:** `/yoke:tech-spec` must present a curated stack menu by
  feature category (web-api, web-ui, cli, library, data-pipeline)
  with 3-5 lettered options per category and an `Other: <free-text>`
  escape. The user must select before drafting begins.
- **FR-3:** `/yoke:tech-spec` must invoke `/yoke:search-canonical-memory`
  with a query scoped to the feature's domain before drafting. If
  the response surfaces fewer than `overrides.tech_spec.canonical_pattern_threshold`
  applicable pattern entities (default 3), the skill must invoke
  `WebSearch` with a targeted query for industry architecture
  patterns and present the top 2-3 in the dialogue with explicit
  trade-offs.
- **FR-4:** `/yoke:tech-spec` must output exactly one file at
  `wm_spec_path "$slug"` (`.yoke/specs/<slug>.md`) carrying these
  H2 sections in this order: Context and Scope; Goals and Non-Goals;
  System Context; Architecture; Stack and Dependencies; APIs and
  Data Model; Non-Functional Requirements; Alternatives Considered;
  Trade-offs; Cross-cutting Concerns; Technical Use Cases; Open
  Questions.
- **FR-5:** `/yoke:tech-spec` must not create any file under
  `.yoke/sprints/` and must not emit any `### Task <ID>` anchor in
  the spec body. The skill aborts non-zero if a self-check finds
  either violation post-draft.
- **FR-6:** Each entry in the spec's "Technical Use Cases" section
  must cite a PRD `US-###` verbatim and must list, at minimum:
  Components involved, Contracts used, NFRs applied, Edge cases.
- **FR-7:** Each entry under "Non-Functional Requirements" must
  carry a quantitative target. Adjective-only entries
  ("performant", "secure", "reliable") fail self-check.
- **FR-8:** Each entry under "Alternatives Considered" must name
  the alternative, list ≥ 1 trade-off vs. the chosen approach, and
  give an explicit reason for rejection.
- **FR-9:** `/yoke:acceptance-contract` must absorb sprint partition
  and task breakdown after drafting BDD scenarios, writing
  `.yoke/sprints/<slug>-s<NN>.md` files with the existing
  `templates/sprint.md` shape (carrying `### Task <ID>` anchors with
  the four inline labels).
- **FR-10:** Trigger 3 must cover the contract and every sprint
  file together — partial state (contract drafted, sprint files
  missing or unapproved) aborts before the menu renders. On
  `approve` / `approve_and_continue`, all artifacts flip
  `Status: approved` atomically at the bash level.
- **FR-11:** `lib/working-memory/scaffold-sprints.sh` must be
  invokable from Phase 3 (the helper itself stays bash-deterministic;
  only the calling skill changes). Phase 2 must never invoke it.
- **FR-12:** When the user picks `revise` at Trigger 2,
  `/yoke:tech-spec` must delete only `.yoke/specs/<slug>.md` (no
  sprint files exist at Phase 2) and re-run dialogue + drafting
  with the captured feedback as additional context.
- **FR-13:** When the user picks `revise` at Trigger 3,
  `/yoke:acceptance-contract` must delete the contract file plus
  every `wm_list_sprint_paths "$slug"` entry before re-running.
- **FR-14:** The Phase 2 skill must surface the `WebSearch` URLs it
  consulted in the spec's "Alternatives Considered" section using
  the shape `[<title>](<url>)`. Sources must not be invented; only
  URLs returned by `WebSearch` may be cited.

## Non-Goals (Out of Scope)

- Modifying the PRD shape. The v2.1.0 PRD shape (US-### / FR-N
  indexing, lettered question options, ralph-aligned sections)
  stays as-is.
- Modifying Phase 4 (`/yoke:implement`) runtime. It still consumes
  sprint files; only the producer of sprint files changes from
  Phase 2 to Phase 3.
- Modifying the canonical-memory provider facade. `/yoke:search-canonical-memory`
  and `/yoke:canonize` keep their current contracts.
- Introducing a new Phase 2.5. Phase 3 absorbs the deferred work
  directly. The 5-phase + 1 continuous shape from
  `concepts/yoke-pattern-phase-flow` is preserved.
- Per-section approval at Trigger 2. Approval is still spec-level
  (one decision marks the whole spec approved or rejected).
- Per-task approval at Trigger 3. Approval is still
  contract-level + atomic with sprint files.
- Retroactive rewrite of any spec already on disk under
  `.yoke/specs/*.md`. Migration of existing slugs is out of scope
  for v0.
- Always-on WebSearch. WebSearch is fallback-only, gated by the
  canonical-pattern threshold.
- Project-stack lock-in. Yoke is a generic framework; the skill
  must support any stack the user picks, with no canonical-memory
  guard that blocks "novel" stack choices.
- New ADR file format. The spec **is** the ADR — there is no
  `.yoke/decisions/<slug>-adr-NN.md` artifact.

## Design Considerations

The skill renders four dialogue rounds (after pre-flight + PRD read):

1. **Stack round.** Auto-detected default + market menu by feature
   category + `Other:` escape. Single response captures the choice.
2. **Architecture round.** Canonical-memory query → present
   applicable patterns. If < threshold, WebSearch fallback →
   present industry patterns with trade-offs. Single response
   captures the chosen pattern.
3. **NFR round.** Skill prompts for quantitative NFRs (latency,
   availability, throughput, consistency, ...). Adjective-only
   answers are challenged inline.
4. **Use-cases round.** Skill walks each PRD `US-###` and prompts
   for Components / Contracts / NFRs / Edge cases. Skipped only if
   the user explicitly defers (recorded in Open Questions).

After the rounds, the skill drafts the spec end-to-end in a single
`Write` call (no per-section LLM-per-call ladder; the shape is
short and the round captures already provide the section content).

The dialogue surface keeps the lettered question + `Other:` escape
convention from `/yoke:discover` to stay consistent with the PRD
phase.

## Technical Considerations

### Technical

- The current skill at `skills/tech-spec/SKILL.md` runs a 3-stage
  blueprint (LLM index → bash scaffold-sprints → LLM-per-sprint
  fill). Stages 2 and 3 collapse to nothing in the new shape; the
  scaffolder script `lib/working-memory/scaffold-sprints.sh` moves
  to be invoked by `/yoke:acceptance-contract` instead.
- `templates/spec.md` is rewritten end-to-end. The current sprint-
  pointer shape (`### Sprint <NN> — <name>` + `**Tasks:** see
  .yoke/sprints/...`) disappears.
- `templates/sprint.md` is unchanged structurally; only the
  producer changes from Phase 2 to Phase 3.
- Path helpers in `lib/working-memory/paths.sh` are unchanged for
  v0 (`wm_spec_path`, `wm_sprint_path`, `wm_list_sprint_paths`
  remain). The semantic shift is in **who** writes them, not in
  the layout.
- `WebSearch` is a deferred tool in this runtime; the skill must
  load it via `ToolSearch` at runtime, not assume it is preloaded.
- The skill prompt that drives stack auto-detection must read
  manifest files via the `Read` tool, not `cat` via `Bash`, per
  repo coding conventions.

### Regulatory

- None — this is a developer-tooling change inside the framework.

### Organizational

- This rewrite is dogfooded by Yoke on Yoke at v3.x. The PRD,
  spec, contract, and implementation flow through the framework's
  own phase machine. Council personas (Sr Eng / Sr QA / Sr Staff)
  ratify the implementation under the existing acceptance-contract
  envelope.
- Breaking change: existing `.yoke/specs/*.md` files written by
  the old 3-stage blueprint remain readable but no longer match
  the new shape. The migration policy is "no retroactive rewrite";
  a new spec for an existing slug must be re-run from PRD.

## Risks

- **Canonical-pattern threshold mis-tuned.** Default of 3 may be
  too aggressive (WebSearch fires when it shouldn't) or too
  conservative (canonical memory drift goes unaugmented). Signal:
  WebSearch fires on > 60% of invocations or < 5% of invocations
  over a 10-spec window. Mitigation: expose
  `overrides.tech_spec.canonical_pattern_threshold` in
  `.yoke/config.yaml`; calibrate during dogfood.
- **Phase 3 wall-clock budget blown.** Phase 3 already runs sensor
  discovery + BDD drafting; adding sprint+task generation may push
  it past the budget Trigger 3 ratifiers tolerate. Signal: median
  Trigger 3 wall-clock > 10 minutes. Mitigation: blueprint stages
  inside Phase 3 (LLM contract draft → bash scaffold-sprints → LLM
  per-sprint task fill), mirroring the structure the old Phase 2
  used.
- **Auto-detection wrong on polyglot repos.** A repo with
  `package.json` + `go.mod` should ask, not pick. Signal: skill
  silently picks a single stack on a multi-manifest repo.
  Mitigation: when ≥ 2 manifest types are present, the skill lists
  every detected stack as a candidate and forces the user to pick
  (FR-1 + US-001 acceptance criterion).
- **Spec-as-ADR loses revision history.** Per Nygard, ADRs are
  append-only and revisions create new ADRs that supersede old.
  A `revise` at Trigger 2 deletes the previous draft. Signal:
  reviewers ask "what alternatives did we already reject?".
  Mitigation: `revise` writes a new file with frontmatter
  `Supersedes: <previous spec sha>` and the previous version stays
  in git history; the body keeps prior alternatives in the
  "Alternatives Considered" section.
- **Council personas miscalibrate against spec-without-tasks.**
  Sr Eng / Sr QA prompts in v3.0.0 reference `### Task <ID>`
  anchors as their unit of work. If those anchors now appear only
  in sprint files (Phase 3 output), persona prompts must consume
  the sprint file, not the spec, when iterating tasks. Signal:
  council personas write code that doesn't map to any task ID.
  Mitigation: persona prompts updated as part of the rollout
  (within FR-9 / FR-11 scope) to consume sprint files.
- **WebSearch returns irrelevant content.** WebSearch is sensitive
  to query quality; a poorly-scoped query returns generic noise.
  Signal: spec's "Alternatives Considered" cites blog spam.
  Mitigation: query template scoped to the feature's domain
  lifted from the PRD's Introduction; user reviews the surfaced
  alternatives in the architecture round before they land in the
  spec.

- 0% of generated specs contain `### Task <ID>` anchors. 0% of

  `.yoke/sprints/`.
- ≥ 80% of generated specs contain quantifiable NFRs (numeric
  targets present), measured by self-check at draft time.
- ≥ 80% of generated specs contain ≥ 1 entry in "Alternatives

- 100% of generated specs cite `US-###` IDs from the PRD verbatim

- Median wall-clock for Phase 3 (`/yoke:acceptance-contract`)

- WebSearch fires on between 5% and 60% of `/yoke:tech-spec`
  invocations across a 10-spec dogfood window (calibration band
  for the canonical-pattern threshold).
