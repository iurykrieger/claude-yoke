## Product invariants

What must hold regardless of implementation:

- **Sensors são harness capability do projeto, não artefatos de uma task.** Um sensor é declarado uma vez e referenciado por qualquer número de Acceptance Contracts e critérios ao longo da vida do projeto. Reuso entre sessões é o default; criação per-task é a exceção (apenas quando o sensor é genuinamente específico daquele trabalho).
- **`type` é hard, declared, escolhido pelo author — `computational | inferential`.** `computational` ⇒ feedback determinístico (mesmo input → mesmo output: linters, formatters, unit/integration tests, schema validators, futuros CI checks). `inferential` ⇒ feedback não-determinístico (LLM-as-judge, agent-driven review, semantic analysis, suítes e2e cujo resultado depende de rendering / estado externo). O `type` é o **único discriminador** — dispatch e calibração derivam dele.
- **`token_cost` e `time_cost` são campos primários do frontmatter.** Cada sensor declara dois custos numéricos: `token_cost: <int>` (estimativa de tokens consumidos por execução; tipicamente 0 para computational, > 0 para inferential) e `time_cost: <int>` (estimativa de wall-clock em segundos). Substituem o `tier: cheap | expensive` binário com expressividade dual: o plano de scheduling pode raciocinar separadamente sobre custo computacional e custo de tokens, e o filtro de execução em `verify-acceptance.sh` pode operar em qualquer das duas dimensões.
- **Scheduling de sensores é plan-driven, não policy-driven.** Quais sensores rodam em quais momentos do `/yoke:implement` é decisão expressa no Acceptance Contract (per critério), propagada para o Validator runtime. Lag-by-one continua existindo como mecânica de inferential dispatch; a heurística "expensive autorizado quando cheap green" deixa de ser default implícito do Validator e vira decisão explícita do plano. Filtros de execução em `verify-acceptance.sh` operam sobre `token_cost` e `time_cost`.
- **Acceptance Contract carrega validação per-critério.** Cada regra de negócio / critério no Acceptance Contract carrega uma sub-seção declarando: (a) quais sensors são usados para garantir aceitação do critério, e (b) **como interpretar o feedback de cada sensor** para determinar sucesso/falha do critério. Como o sensor é executado **não** é repetido — vive no arquivo do sensor (`## How to run`). A sub-seção é interpretation-only.
- **Vínculo sensor ↔ critério vive no Acceptance Contract.** Sensors não conhecem tasks. O contrato nomeia quais sensors gateiam quais critérios e como interpretá-los. O arquivo do sensor não carrega `applies_to`.
- **O arquivo do sensor é knowledge base consolidado, não log de execução.** Não há array `runs:`, não há `recent_runs:`, não há histórico de timestamps no arquivo. O arquivo captura: como rodar, problemas conhecidos, erros frequentes que o sensor detecta no código sob análise, e (para inferential) calibração / prompt / rubric / verdict schema.
- **Body shape é fixo e linta-do.** Toda sensor file contém:
  - `## How to run` (obrigatória, qualquer type).
  - `## Known issues` (obrigatória, qualquer type — flakes, dependências ambientais, gotchas do próprio sensor).
  - `## Frequent errors` (obrigatória, qualquer type — catálogo de pitfalls recorrentes que o sensor já capturou no código analisado, formato `- <pattern>: <fix>`).
  - `## Calibration` (obrigatória para `type: inferential`, ausente para `type: computational`) — sub-seções `### Prompt`, `### Rubric`, `### Verdict schema`.
- **Aprendizado é destilado ao fim de cada `/yoke:implement` pela skill `/yoke:consolidate-sensors`.** A skill é invocada sem argumentos, lê o histórico do implement atual (`.yoke/runtime/`) + arquivos de memória local da task corrente, e atualiza os sensors envolvidos:
  - **Body**: append-only nas seções `## Known issues` / `## Frequent errors` / (inferential) `## Calibration`. Jamais reescreve linhas pré-existentes.
  - **Frontmatter**: atualiza `token_cost` e `time_cost` com base nas observações reais de runtime acumuladas no `progress.md` da task. Demais campos preservados.
  Diff-review opt-out: humano vê o diff e escolhe aceitar tudo / parcial / pular, configurável em `.yoke/config.yaml` (`sensor_consolidation: review | auto | skip`, default `review`).
- **Inferential = agent dispatch.** Sensores `inferential` declaram `agent: <subagent-id>` no frontmatter. O runtime materializa o spawn via Task tool, lendo prompt + rubric + verdict schema das sub-seções de `## Calibration`. O atual `agents/semantic-judge.md` torna-se uma instância desse shape, não um caso especial.
- **Verdict schema inferential é estável.** Envelope JSON: `{ criterion, status, location, fix_instruction, sensor, evidence, confidence, supporting_quotes }`. `confidence` é float em `[0, 1]`, validado pelo parser (verdict inválido = sensor fail). `supporting_quotes` é lista de strings; mínimo ≥1 quando `status: fail`; vazia permitida em `status: pass`. Os demais campos preservam o envelope atual de `agents/semantic-judge.md`.
- **Shape extensível por type, sem refactor para novos sources.** `type: computational` hoje pode rodar via `command:` (shell local). Amanhã, sem mudar o discriminador nem a referência no contract, um sensor `computational` pode ter origem em GitHub Actions check / webhook / coverage gate — adicionando campos opcionais ao frontmatter sem redefinir a forma. Não há comprometimento com implementação desses sources em v0.
- **Composability.** Remover um sensor de um contrato não afeta sua existência no catálogo. Adicionar um sensor a um contrato é uma mudança apenas de contrato — nenhum arquivo de sensor é reescrito por essa operação.
- **Dispatch consciente de `type` em todos os pontos do fluxo.** Onde quer que o framework dispare um sensor — `hooks/verify-acceptance.sh`, `agents/validator.md`, `skills/implement/SKILL.md`, `lib/sensors/ack-sensors.sh`, `/yoke:consolidate-sensors` — a lógica honra a dicotomia: shell para computational, subagent para inferential. Nenhum caminho ignora o `type`.
- **Manifesto invariants preservados.** Shift-feedback-left, structured sensor output, hard bounds, binding spec, adversarial loop, sprint-contract subordination, working-memory placement — nenhum enfraquecido.

## Business context

A implementação atual de sensores (pós sensor-cost-tiering, abr/2026) carrega o vocabulário certo — `class: computational | inferential`, `tier: cheap | expensive`, slot `runs:` — mas a modelagem desviou do frame de harness engineering que o framework deveria encarnar. Cinco sintomas de drift tornaram esta PRD necessária:

1. **Sensors são task-bound.** Todo `.yoke/sensors/<id>.md` carrega `applies_to: [<task-slug>-s<NN>-t<MM>]`. Nos 45 arquivos hoje em disco, o campo é sempre exatamente uma task. Tasks novas regeneram sensores conceitualmente idênticos sob ids novos. Checks de nível harness não têm casa reusável. O framework não acumula conhecimento sobre seus próprios sensors entre sessões porque o sensor é destruído (ou duplicado) na fronteira da task.

2. **Inferential está submodelado.** ~95% dos sensors existentes são `computational`; os únicos casos `inferential` (e.g. `round-trip-suite-passes`) são scripts shell que por acaso invocam um LLM. O framework não oferece shape para o tipo de sensor inferential que o diagrama de Fowler explicitamente nomeia: code-review agents, QA agents, semantic-analysis judges. O atual `semantic-judge` existe como subagent interno do Validator — não é endereçável a partir de um contrato, não tem arquivo de conhecimento por sensor, e não pode ser reusado como capability genérica.

3. **`runs:` é mismodelado.** O slot existe mas seu propósito virou audit-log-de-execuções. O valor de harness engineering é oposto: o arquivo do sensor deveria ser o lugar onde o time grava o que já aprendeu sobre esse check — known flakes, gotchas ambientais, calibration history, prompt drifts já corrigidos, padrões de erro frequente. Persistência de audit-log é outra preocupação (runtime state, progress.md), e conflar as duas produziu um slot que cresce sem informar ninguém.

4. **Não há fase de consolidação de aprendizado.** Cada `/yoke:implement` produz dezenas de fix-instructions, calibration adjustments e known-failure observations — e tudo evapora no fim do loop. A próxima task começa do zero. O sensor file é o lugar natural para essa knowledge persistir, mas hoje não há mecanismo que escreva nele. Da mesma forma, o `cost` real observado em runtime nunca alimenta de volta a estimativa declarada — o `tier` continua estático ad infinitum.

5. **Scheduling é policy-driven implícito, não plan-driven explícito.** Hoje o Validator runtime decide "expensive autorizado quando cheap green" como heurística embutida no agent, lendo `runs:` no arquivo do sensor. Isso entrelaça dois concerns: o que rodar (planning) e quando rodar (enforcement). Para features com perfil de sensor não-trivial, a heurística genérica é insuficiente. Plan-driven scheduling resolve: Acceptance Contract carrega o plano explícito por critério; Validator aplica.

O trigger agora: com v1.1 dogfoodada e sensor-cost-tiering shipada, a próxima feature não-trivial tocando contracts compõe os cinco problemas a menos que o modelo seja corrigido antes. Estamos no momento mais barato para refatorar — 45 arquivos, em sua maioria órfãos de tasks fechadas, antes do número crescer.

Uma preocupação estratégica secundária: o diagrama de Fowler mostra explicitamente sensors operando em múltiplos estágios do ciclo — o self-correction loop *e* o pipeline pós-merge. Yoke hoje só consome sensors durante `/yoke:implement`. v0 desta PRD não implementa sensors pós-merge (GitHub Actions, webhooks), mas a modelagem precisa permitir esse shape no futuro sem outro refactor.

## Known constraints

### Technical

- **Backward-compat parcial com sensor-cost-tiering.** A mecânica de scheduling lag-by-one preserva-se; a heurística embutida (policy) deixa de ser default e passa a vir do Acceptance Contract. O conceito `cheap | expensive` é absorvido por (`token_cost`, `time_cost`); o flag `verify-acceptance.sh --tier cheap|expensive|all` é substituído por filtros sobre os dois custos — forma exata em tech-spec (provavelmente `--max-time-cost <N>` e `--max-token-cost <N>`, combinados via AND).
- **Field rename `class → type` é big-bang.** Single PR atômico: parser atualizado para aceitar apenas `type:`, todos os arquivos sobreviventes reescritos no mesmo commit. Sem janela de coexistência. Cobertura de teste compensatória obrigatória.
- **`tier` é descontinuado, `token_cost` + `time_cost` são introduzidos.** Mesma migração big-bang: parser deixa de aceitar `tier:`, todos os arquivos sobreviventes ganham `token_cost` (int) e `time_cost` (int, segundos) no mesmo commit. Defaults razoáveis na migração: computational → `token_cost: 0`, `time_cost` estimado pelo author (ou conservador 30s); inferential → `token_cost: 1000` (estimativa conservadora), `time_cost: 60`.
- **`applies_to` é removido do sensor file.** Toda referência sensor↔critério migra para o Acceptance Contract. Parser de `hooks/verify-acceptance.sh` resolve metadata (command/type/costs/agent) só do arquivo do sensor.
- **`runs:` e `recent_runs:` são banidos do arquivo do sensor.** Não há array de execuções no frontmatter nem em sidecar gitignored. Aprendizado vive no body, escrito pela fase de consolidação. Custos atualizam-se no frontmatter, escritos pela mesma fase.
- **Inferential sensors invocam subagent.** Frontmatter: `agent: <subagent-id>`. Body em `## Calibration` carrega `### Prompt`, `### Rubric`, `### Verdict schema`. Runtime materializa spawn via Task tool. Verdict schema mantém o envelope atual de `agents/semantic-judge.md` mais `confidence` e `supporting_quotes`.
- **Acceptance Contract template ganha sub-seção per critério.** Cada critério no template carrega:
  ```
  ### Validation
  
  - **<sensor-id>** — <how to interpret this sensor's feedback to validate this criterion>
  - **<sensor-id>** — <interpretation>
  ```
  Naming exato da sub-seção (`### Validation`, `### Sensors`, `### Acceptance check`) e shape final (markdown bullets vs YAML block) decidido em tech-spec. O parser de `verify-acceptance.sh` lê essa sub-seção para resolver vínculo sensor↔critério e a interpretation guidance é input para o Validator.
- **`/yoke:consolidate-sensors` é skill nova, sem argumentos.** Lê `.yoke/runtime/.current` para descobrir o slug ativo, lê o histórico do implement em `.yoke/runtime/` (judge verdicts, progress, snapshots) + arquivos de memória local da task corrente, e atualiza:
  - **Body** dos sensors envolvidos: append-only nas seções fixas, com citação de evidência por bullet (`cycle N, fix-instruction X`).
  - **Frontmatter** dos sensors envolvidos: `token_cost` e `time_cost` recalculados a partir das observações reais. Forma de recálculo (média móvel? média simples? média ponderada por recência?) decidida em tech-spec — default proposto: média simples sobre todas as runs do implement atual.
  Reentrância idempotente: pré-check antes do append → se a citação já existe no body, pula; cost só atualiza se delta > 5% (evita oscilação trivial). Diff-review opt-out por `.yoke/config.yaml` (`sensor_consolidation: review | auto | skip`, default `review`).
- **Body shape obrigatório, lintado estritamente.** `lib/sensors/ack-sensors.sh` (modos catalog / readiness / upsert) lint-a:
  - Presença das 4 (ou 3 para computational) headers.
  - Conteúdo não-vazio sob cada header.
  - Formato de bullets em `## Frequent errors`: `- <pattern>: <fix>` single-line.
  - Sub-seções `### Prompt`, `### Rubric`, `### Verdict schema` em `## Calibration` (inferential).
  Falta de qualquer um → readiness fail.
- **Triagem dos 45 arquivos existentes.** Genéricos harness-level (e.g. `bash-syntax-clean`, `frontmatter-yaml-valid`, `shellcheck-new-scripts`, `skills-frontmatter-valid`) viram catálogo durável, perdem `applies_to`, ganham `token_cost` + `time_cost`. Específicos de doctrine-canonization (e.g. `pattern-entities-count-9`, `vibeflow-prds-empty`, `audit-count-matches`, `decision-count-matches`) são deletados. Sanity check: nenhum sensor referenciado por contract sob `.yoke/acceptance-contracts/` é deletado. Estimativa visual: ~10-15 sobrevivem, ~30-35 deletados.
- **Working-memory placement preservado.** `.yoke/sensors/<id>.md` continua em working memory (per host project), commitado no repo do projeto. Promoção de conhecimento estável de sensor para canonical memory permanece fora de escopo.
- **Dispatch refatorado em todos os pontos do fluxo.** `hooks/verify-acceptance.sh`, `agents/validator.md`, `skills/implement/SKILL.md`, `lib/sensors/ack-sensors.sh`, `agents/semantic-judge.md` (que vira instância do shape novo), templates `acceptance-contract.md` e `sensor.md`, e a skill nova `/yoke:consolidate-sensors` — todos atualizados no mesmo PR. Nenhum caminho permanece com o shape antigo.
- **Future-proofing minimal.** v0 commits a apenas: `type` é o discriminador estável, `token_cost` + `time_cost` são os canais primários de expressão de custo, e o body `## How to run` é o descriptor humano permanente. Novos sources de feedback (CI, webhook, coverage gate) adicionam campos opcionais de frontmatter sem redefinir a forma.

### Regulatory

- Nenhuma. PRD toca tooling interno; sem superfícies de PII / PCI-DSS / LGPD / HIPAA.

### Organizational

- **Um desenvolvedor (Iury), dogfooding.** Sem coordenação multi-time; refactor cabe num único sprint sem bloqueadores externos.
- **Templates e `lib/sensors/` são plugin-versionados.** Mudanças shipam na mesma plugin version que as introduz; consumidores atualizam `.yoke/sensors/` via `/yoke:ack-sensors --mode upsert` (estendido para o novo shape, com migração big-bang automática).
- **Sem cross-project sensor sharing ainda.** Catálogo no plugin (Q1 alternativa b) explicitamente diferido — promoção para plugin acontece só após o sensor provar-se em ≥3 projetos.

## Risks

- **Migration deixa um sensor órfão.** Se um sensor é referenciado por contrato ainda aberto e a triagem o classifica errado como one-shot e deleta, o próximo `/yoke:implement` naquele contrato falha opacamente. *Sinal:* `verify-acceptance.sh` emite "sensor file missing" para id presente em contrato sob `.yoke/acceptance-contracts/`. *Mitigação:* pre-migration audit listando todo sensor ainda referenciado por algum contract; allowlist explícito de deleção, gerado e revisado antes do PR.

- **Big-bang rename / cost-introduction quebra teste/exemplo legado.** Sem janela de coexistência, qualquer fixture em `tests/sensors/` ou `examples/` ainda lendo `class:` ou `tier:` regride silenciosamente. *Sinal:* test suite vermelha pós-PR. *Mitigação:* PR atômico inclui `tests/sensors/migration.test.sh` (one-shot) e `tests/sensors/dispatch-by-type.test.sh` (permanente); sem cobertura, PR não merge.

- **Inferential dispatch protocol diverge do `semantic-judge` atual.** Se o novo shape inventar um contrato I/O paralelo, runtime ganha dois caminhos. *Sinal:* `hooks/verify-acceptance.sh` cresce um `case "$type" in inferential)` que faz qualquer coisa diferente do batch path lag-by-one que os judges já usam. *Mitigação:* tech-spec demonstra que `agents/semantic-judge.md` torna-se instância do shape novo, não sibling.

- **Body knowledge cresce em bikeshed.** Sem schema estrito, autores escrevem prosa livre e o body vira ungrep-able. *Sinal:* arquivos pós-migração variam wildly em shape; lint passa porque seções existem, mas conteúdo é inútil. *Mitigação:* lint estrito (presença + non-empty + formato de bullets em `## Frequent errors`); body vazio ou má-formatado falha readiness.

- **Consolidation step escreve lixo no sensor file.** A destilação automática pode hallucinar erros frequentes que não aconteceram, ou enterrar conhecimento real sob ruído. Atualização de cost pode introduzir oscilação não-monotônica (cycle alto puxa média pra cima, próxima task com cycle baixo puxa pra baixo). *Sinal:* commits da fase de consolidação adicionam linhas que não correspondem a nenhuma fix-instruction emitida no loop; ou `token_cost`/`time_cost` oscila > 30% entre invocações. *Mitigação:* (a) escrita append-only no body — jamais reescreve linhas pré-existentes; (b) diff-review opt-out (default `review`) — humano vê o diff antes do commit; (c) prompt de destilação cita evidência (cycle N, fix-instruction X) por bullet adicionado, lint exige presença da citação; (d) cost só atualiza se delta > 5% (evita oscilação trivial); (e) tech-spec define forma de recálculo (média ponderada favorecendo runs recentes provavelmente, com cap de N runs históricas).

- **`token_cost` e `time_cost` mal calibrados → scheduling sub-ótimo na primeira task.** Antes do primeiro `/yoke:consolidate-sensors`, os números são estimativas do author no momento da migração. Se errados, plan-driven scheduling produz decisões ruins. *Sinal:* primeira task pós-realignment roda mais lento que antes. *Mitigação:* defaults conservadores na migração (computational baixo, inferential alto); a primeira execução do consolidation step recalibra; humano valida no diff-review.

- **Acceptance Contract per-criterion validation section infla template.** Adicionar uma sub-seção por critério aumenta o boilerplate do contract; specs com 20+ critérios ficam difíceis de ler. *Sinal:* tech-specs reportam que escrever o contract leva 2x mais tempo. *Mitigação:* sub-seção é interpretation-only (não duplica command, não duplica config); template fornece exemplo conciso (1-2 bullets por critério); critérios triviais (one-sensor, "pass = sensor passes, fail = sensor fails") usam shorthand.

- **Plan-driven scheduling aumenta planning overhead.** Tech-spec author agora precisa pensar em scheduling per-critério, não só em escopo. *Sinal:* tech-specs ficam mais lentas de produzir. *Mitigação:* defaults sensatos no template (rodar todos os sensors low-cost cada cycle; high-cost só no merge-ready) cobrem o caso comum; explicitação só é exigida quando o caso requer.

- **Extensibility surface vira spec morta.** Se o shape carrega `type` + opcional `command` + `agent` + `token_cost` + `time_cost`, e nenhum source novo (CI/webhook) é adicionado em 6 meses, a frase "extensível por type" fica como decoração. *Sinal:* PRD futura para CI sensors propõe nova refatoração ao invés de estender o shape. *Mitigação:* tech-spec esboça (sem implementar) o exemplo de um GitHub-Actions sensor sob o shape v0 — se o esboço requer refactor, o shape v0 está errado e ajusta-se agora.

- **Inferential dispatch consome budget de runtime.** Cada inferential sensor é um Task spawn potencial; muitos por ciclo estouram budget. *Sinal:* cycle wall-clock regride em features com ≥3 sensors inferential. *Mitigação:* o cap `runtime.inferential_sensor_concurrency` continua ativo; tech-spec verifica que o caminho novo de dispatch honra. Plan-driven scheduling agora dá ao author controle preciso de "rodar este inferential só nestes cycles".

## Open questions

Decisões fechadas durante discovery (não são open questions; listadas para rastreabilidade):

- `type:` substitui `class:`. Migração big-bang.
- `token_cost: <int>` + `time_cost: <int seconds>` substituem `tier:`. Migração big-bang.
- Body shape: `## How to run`, `## Known issues`, `## Frequent errors`, `## Calibration` (inferential only); lint estrito (presença + non-empty + bullet format + sub-seções obrigatórias).
- Drop completo de `runs:` / `recent_runs:` — não há histórico de execução no arquivo.
- Inferential dispatch via `agent: <subagent-id>` + sub-seções de `## Calibration` (`### Prompt`, `### Rubric`, `### Verdict schema`).
- Verdict schema inferential: envelope atual + `confidence` (float [0,1], validado pelo parser) + `supporting_quotes` (lista de strings, ≥1 quando `status: fail`).
- Pós-implement consolidation via sub-skill nova `/yoke:consolidate-sensors`, sem argumentos, lê `.current` + `.yoke/runtime/`. Atualiza body (append-only) e frontmatter (`token_cost`, `time_cost`).
- Diff-review opt-out na consolidation, configurável em `.yoke/config.yaml` (`sensor_consolidation: review | auto | skip`, default `review`).
- Reentrância idempotente da consolidation: citação de evidência por bullet + cost só atualiza se delta > 5%.
- Scheduling plan-driven: Acceptance Contract carrega validação per-critério (sensors + interpretation guidance); Validator runtime aplica.
- Filtros de execução em `verify-acceptance.sh` operam sobre `token_cost` e `time_cost` (provavelmente `--max-time-cost`, `--max-token-cost`).
- Triagem dos 45 arquivos: genéricos viram catálogo, doctrine-canonization é deletado.
- Catalog é commitado, sem sidecar runtime para histórico de runs.
- Future-proof CI/webhook sensors via campos opcionais de frontmatter; v0 não implementa.
- Test scope: `migration.test.sh` (one-shot) + `dispatch-by-type.test.sh` (permanente, gate de CI) + `body-lint.test.sh` (permanente, gate de CI) + `consolidation-stage.test.sh` (permanente, gate de CI).

Restam para tech-spec resolver (questões abertas genuínas, sem resolução de discovery):

- **Sintaxe exata da sub-seção de validação per-critério no Acceptance Contract.** Naming (`### Validation`, `### Sensors`, `### Acceptance check`), shape (markdown bullets, YAML block, ou tabela), e shorthand para critérios triviais (one-sensor, pass=sensor-pass).
- **Sintaxe exata dos filtros de custo em `verify-acceptance.sh`.** `--max-time-cost <N>` + `--max-token-cost <N>` (AND), ou um shorthand combinado, ou substituição direta por `--plan-stage <name>` que delega ao plan?
- **Forma de recálculo de `token_cost` e `time_cost` na consolidation.** Média simples? Média ponderada favorecendo runs recentes? EMA? Cap de N runs históricas considerados? Default proposto: média simples sobre todas as runs do implement atual, com piso de mínimo 1 run.
- **Defaults conservadores de cost na migração inicial.** Valores específicos para sensors computational (`token_cost: 0`, `time_cost: ?`) e inferential (`token_cost: ?`, `time_cost: ?`). Tech-spec propõe valores baseados em observação dos sensors existentes.
- **Triagem definitiva dos 45 arquivos.** Lista exata delete-vs-preservar gerada por audit pré-migração contra `.yoke/acceptance-contracts/`.
