# PRD: Pluggable canonical-memory provider

> Generated by `/yoke:discover` on 2026-04-30.
> Status: approved
> Approved by: iury.krieger@stone.com.br
> Approved at: 2026-04-30

## Product invariants

What must hold regardless of implementation. The "shape" of the product
that constrains every solution. Non-negotiable.

- **Yoke owns exactly two canonical-memory verbs.** `/yoke:search-canonical-memory`
  (read) and `/yoke:canonize` (write). No other Yoke skill touches canonical
  memory. Provider-specific operations (compression, dedup, drift sensing,
  health checks, registry management, external-source ingestion, schema
  validation) are *not* Yoke's concern and stay inside the provider plugin.
- **The provider is the source of truth for memory semantics.** Yoke imposes
  no schema, no entity model, no frontmatter conventions, no governance rules
  on the canonical memory's *contents*. Each provider is free to use markdown
  graphs, vector recall, key-value stores, or anything else. Yoke only knows
  "send the working memory to canonize" and "receive a markdown answer from
  search."
- **One canonical memory per Yoke project.** A project's `.yoke/config.yaml`
  declares exactly one `canonical_memory.provider` and one path/identifier.
  Multiple projects MAY point to the same memory (the sharing direction);
  one project pointing to multiple memories is out of scope.
- **Provider identity is configured at project bootstrap, not runtime.**
  `.yoke/config.yaml` carries the `canonical_memory.provider` field and is
  written during `/yoke:bootstrap`. The runtime never asks "which provider";
  it dispatches deterministically.
- **Yoke's two verbs are opaque pipes.** `/yoke:search-canonical-memory`
  forwards a natural-language query and returns the provider's textual
  answer verbatim to the caller. `/yoke:canonize` hands the provider a path
  to `.yoke/` and returns the provider's exit status. Yoke does not parse,
  validate, or post-process either side.
- **Bedrock remains the reference provider, but ships as a peer plugin.**
  Bedrock skills no longer live inside Yoke. Yoke + Bedrock installed
  together must cover every use case Yoke covers today.
- **Backward compatibility for in-flight tasks is not promised.** Existing
  projects that ran prior Yoke versions must explicitly migrate via
  `/yoke:bootstrap` re-run before any other Yoke skill works again. Hard
  break is preferable to silent default.

## Business context

Yoke v0.1.0 absorbed Bedrock skills (`/bedrock:ask`, `/bedrock:teach`, etc.)
as a single fork — see `concepts/yoke-decision-2026-04-24-embed-upstream-skills-as-a-single-fork-at-creation`.
That decision said *"there is no continuous port from upstream"* and was right
at the time: a single fork removes upstream-coupling overhead and pins the
framework against a versioned, internally-consistent skill set.

Two things changed since then.

**Bedrock evolution is now constrained by Yoke's release cadence.** Improvements
to the canonical-memory substrate (new entity types, schema migrations, query
semantics) require a Yoke PR, even when the change has nothing to do with the
runtime ralph loop. The fork is paying interest.

**Users arriving at Yoke already have memory setups.** Whoever installs Yoke
in their Claude Code may already run `claude-mem`, a private vault, a custom
markdown brain, or a different fork of Bedrock. The current Yoke design forces
them to either abandon their memory or fork Yoke to swap the embedded
operations. Neither is acceptable.

The decision to make Bedrock the *reference* implementation
(`yoke-decision-2026-04-24-external-canonical-memory-substrate-not-embedded`,
*"replaceable by any versioned store reachable over MCP or equivalent"*) was
already pluggable in principle — but in practice the abstraction stopped at
the substrate layer and the *skills* are still Bedrock-specific. This PRD
finishes the job: pluggability moves up to the skill surface.

## Known constraints

### Technical

- **Two skills only.** Yoke ships `/yoke:search-canonical-memory` and
  `/yoke:canonize`. Every other current canonical-memory skill (`/yoke:ask`,
  `/yoke:preserve`, `/yoke:teach`, `/yoke:compress`, `/yoke:status` (canonical
  parts), `/yoke:memory`, `/yoke:drift-sense --target canonical-memory`)
  either gets renamed into the two verbs above or **removed from the Yoke
  plugin entirely**. The provider plugin (Bedrock) keeps the equivalents
  under its own namespace.
- **`/yoke:canonize` payload contract = filesystem path.** Yoke invokes
  `${provider}:<canonize-skill> --working-memory .yoke/`. The provider reads
  `.yoke/` directly. This means each provider's canonize skill must understand
  Yoke's working-memory layout (`prds/`, `specs/`, `sprints/`, `acceptance-contracts/`,
  `contracts/`, `runtime/progress.md`). Yoke does not normalize, summarize,
  or bundle.
- **`/yoke:canonize` trigger = end of every `/yoke:implement` invocation,
  unconditional.** It fires when the runtime loop terminates regardless of
  termination reason (convergence, divergence, hard-bound). The provider is
  responsible for filtering out non-consolidated learnings. Yoke does not
  classify maturity, does not gate by termination reason, does not promote
  fleeting notes. The provider receives the full working memory and decides.
- **Provider registry is a curated YAML in the Yoke plugin.** A
  `providers.yaml` file at the plugin root enumerates known providers, each
  with the de/para mapping `search → <skill>` / `canonize → <skill>` plus
  invocation parameters. Adding a provider = PR to Yoke (trivial: 4–6 lines
  of YAML). No dynamic plugin discovery, no convention-based scanning.
- **Project config carries `canonical_memory.provider`.** `.yoke/config.yaml`
  gets a new top-level key (`canonical_memory: { provider: <name>, ... }`).
  Provider-specific options live nested under that key and are passed to the
  provider opaquely. Yoke does not interpret them.
- **No dual-provider, no fallbacks.** A project has one provider. If it is
  unavailable (plugin not installed, search returns error), Yoke fails the
  invocation and surfaces the error. Yoke does not retry with another
  provider, does not cache, does not silently degrade.
- **Skill renaming is not a backward-compat exercise.** `/yoke:ask` and
  `/yoke:preserve` cease to exist as Yoke skills. References across the
  codebase (CLAUDE.md, docs, lib, hooks, runtime subagents, sensor scripts)
  are rewritten to the new names. No aliases.
- **Migration path = `/yoke:bootstrap` re-run, hard break.** Projects whose
  `.yoke/config.yaml` lacks `canonical_memory.provider` are rejected by
  every Yoke skill until they re-run `/yoke:bootstrap`, which detects the
  legacy `memories.json`, prompts for provider choice, writes the new key,
  and removes `memories.json` after confirmation. No silent default to
  `bedrock`. No grace period.

### Regulatory

- None applicable. This is a pure refactor of the framework's internal
  layering; it does not change which data is stored, where, or under what
  governance. Model C governance over canonical-memory writes is enforced
  by the provider, not by Yoke.

### Organizational

- **Bedrock as a peer plugin needs an owner.** The
  `iurykrieger/claude-bedrock` repo (or equivalent) becomes the canonical
  Bedrock distribution; its release cadence is independent of Yoke. The
  same maintainer (Iury) owns both during v0, but the contract between
  them is no longer "single fork" — it's "two plugins that interoperate via
  the providers.yaml manifest."
- **Yoke's own canonical memory (the `iury-brain` Bedrock vault holding
  `concepts/yoke-pattern-*`, `concepts/yoke-decision-*`, etc.) keeps
  working** because Bedrock remains a valid provider. The dogfood loop is
  preserved. No content migration is required for the Yoke project itself
  beyond updating its `.yoke/config.yaml`.

## Risks

- **Cold-start canonization regression.** The current doctrine
  (`yoke-decision-2026-04-25-consult-live-canonize-on-termination-new-invariant`)
  fires canonization per-task to capture freshest signal. By delegating the
  filter ("is this consolidated enough?") entirely to the provider, Yoke
  becomes blind to *whether* the provider chose to canonize anything. If
  the provider's filter is too aggressive, learnings rot in working memory.
  Signal: working memory accumulates archived tasks but canonical memory
  shows zero growth across multiple `/yoke:implement` runs.
  Mitigation: the provider's canonize skill SHOULD return a structured
  exit summary (entities created/updated/skipped); Yoke logs it. Final
  shape of that summary is provider-dependent (TODO in Open Questions).

- **Working-memory schema becomes a public contract.** Today, the layout
  of `.yoke/` (`prds/`, `specs/`, `sprints/<slug>-s<NN>.md`, `runtime/progress.md`)
  is internal to Yoke; only `/yoke:preserve` reads it. After this change,
  every provider's canonize skill must read the same layout. Any future
  rearrangement of `.yoke/` becomes a breaking change for every provider.
  Signal: a `lib/working-memory/paths.sh` change reaches review without
  the provider plugins being notified.
  Mitigation: document the working-memory layout as a versioned contract
  under `docs/canonical-memory-provider-contract.md`; bump a contract
  version when it changes.

- **Provider absent or broken silently degrades the runtime loop.** Today
  `/yoke:ask` failure means the agent loses context but the loop continues.
  After this change, `/yoke:search-canonical-memory` failures still degrade
  gracefully (no context), but `/yoke:canonize` failures at end-of-loop
  may go unnoticed (the loop already converged; nobody is watching the
  exit code).
  Signal: `/yoke:implement` returns success but no canonical-memory PR
  appears.
  Mitigation: `/yoke:implement` records canonize invocation outcome in
  `progress.md` final cycle entry; failure is surfaced to the user.

- **Migration hostility breaks dogfood loops.** Hard-break migration (γ)
  means anyone running an older Yoke version against a working project will
  hit "rerun bootstrap" errors mid-task. For Yoke developers (Iury) running
  the framework on itself during this very refactor, this is annoying but
  acceptable. For external users, it's a one-time friction.
  Signal: GitHub issues from users reporting their `/yoke:implement` runs
  abort after upgrade.
  Mitigation: release notes; the bootstrap re-run is fast and idempotent;
  this PRD is the v1 → v2 break, future provider additions are additive.

- **`providers.yaml` curation pressure.** Curated registry means the Yoke
  team becomes a gatekeeper for provider listings. If demand grows, PRs
  may pile up. Signal: open PRs adding provider entries with no maintainer
  movement.
  Mitigation: keep the entry shape so trivial that auto-merge under simple
  CI lint is reasonable. If demand actually grows, revisit and consider a
  hybrid (curated + local override) — but **not in v0**.

- **Yoke's own doctrine in canonical memory references retired skill names.**
  Many `concepts/yoke-pattern-*` and `concepts/yoke-decision-*` entities
  cite `/yoke:ask` and `/yoke:preserve` directly. After rename, those
  references become stale until a doctrine-canonization pass updates them.
  Signal: searching the canonical memory for "ask" or "preserve" returns
  outdated entities. Mitigation: dogfood `/yoke:canonize` to file an
  update PR against the canonical memory in the same release.

## Open questions

TODOs the Generator could not resolve in dialogue. Block downstream phases
when load-bearing; the Tech Spec must close them.

- **Q1 — `providers.yaml` schema.** The exact shape of each provider
  entry: how to encode skill invocation (positional args? flag templates?
  named parameters?), how to declare provider-specific config keys that
  should be passed through from `.yoke/config.yaml`, how to express
  prerequisites (e.g., "Bedrock provider requires `claude-bedrock` plugin
  installed"). Decide before implementation.
- **Q2 — Canonize exit-summary contract (optional or mandatory).** The
  risk-mitigation note above suggests providers SHOULD return a structured
  summary. Is this a soft convention (Yoke logs whatever it gets) or a
  hard contract (Yoke fails if the format is wrong)? Probably soft for v0,
  but record the decision.
- **Q3 — Fate of `lib/canonical-memory/`.** Concretely: which scripts go
  to the Bedrock plugin (`canonization-criteria.sh`, `graph.sh`,
  `registry.sh`, `scaffold-memory.sh`, `semantic-overlap-rewrite.sh`,
  `trace-analyzer.sh`, `write-promoted-concept.sh`), which stay in Yoke
  (a slim `resolve-provider.sh` that reads `config.yaml` and returns
  provider name + opts), and which are deleted outright.
- **Q4 — Bedrock peer plugin distribution mechanism.** Standalone plugin
  in `iurykrieger/claude-bedrock`? Marketplace listing? Submodule? Same
  repo, separate `.claude-plugin/`? The choice affects `/yoke:bootstrap`'s
  ability to verify the provider is installed.
- **Q5 — `/yoke:bootstrap` flow for provider selection.** Interactive
  prompt with provider options from `providers.yaml`? Default to
  `bedrock` with confirmation? `--provider <name>` flag for non-interactive
  bootstrap? Specify the UX.
- **Q6 — Migration detection for legacy projects.** The bootstrap re-run
  must detect a project that pre-dates this refactor. Signals available:
  presence of `memories.json` in plugin dir; absence of
  `canonical_memory` key in `.yoke/config.yaml`; presence of skill names
  like `/yoke:ask` references in older `progress.md` files. Pick the
  detection heuristic.
- **Q7 — Sensor implications.** `lib/sensors/*.sh` may reference the old
  skill names (`/yoke:ask`, `/yoke:preserve`). Audit needed during Phase 2
  or Phase 4.
- **Q8 — Test coverage strategy.** Smoke tests under `tests/smoke/`
  currently exercise the embedded canonical-memory operations. Decide
  whether to (a) replace with a stub provider for hermetic tests, or
  (b) require Bedrock installed in CI and exercise the real path.
