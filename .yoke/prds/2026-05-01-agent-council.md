## Product invariants

What must hold regardless of implementation. The "shape" of the council
that constrains every solution. Non-negotiable.

- **Distinct objectives per persona.** Each persona has its own success
  criterion (Sr Eng: ship working code; Sr QA: prove the code is wrong
  via tests + sensors; Sr Staff: prove the architecture is wrong via
  long-term sustainability lens). Objectives are *complementary but
  different* — collaboration within a persona; signal across personas.
- **Sync barrier per cycle.** The runtime coordinator MUST wait for all
  council personas to finish their Phase A (parallel execution) work
  before opening Phase B (council ponderation). The current bug —
  Validator/Orchestrator finishing before Generator's code generation
  completes — is the prime artifact this invariant exists to kill.
- **`progress.md` as the single source of cycle state.** It is the
  ponderation file: a multi-author surface where every persona records
  its own progress in Phase B.1, its readings of others in Phase B.2,
  and its réplicas in Phase B.3. No other channel exists between
  personas during a cycle.
- **Round-bounded council.** Phase B runs for at most a configured
  number of réplica rounds. If divergence persists beyond the cap,
  Trigger 4 fires and the human arbitrates. Council never loops
  forever.
- **Trigger 4 generalizes to N personas.** Today the trigger fires on
  Implementation↔Validation divergence (2-party). With N=3 personas,
  any unresolved pairwise disagreement at the end of the council
  rounds escalates. Council never silently agrees by majority — every
  unresolved pair is a Trigger 4.
- **Pluggable persona definitions.** Yoke ships defaults; every adopting
  org overrides the persona spec (objective + sensor toolkit + prompt
  shape) via host-project files. Audience is OSS, not a single org.
- **Sensors and canonical memory readable by every persona.** No
  persona has privileged access to a sensor or to the canonical
  substrate. Each persona invokes the sensors and `/yoke:search-canonical-memory`
  it needs to substantiate its verdict.
- **No backward compatibility commitment.** Yoke is still in
  development; v3.0 may break any boundary it needs to (Phase 4
  runtime, Phase 1–3 artifact shapes, sensor harness, persona spec).
  Breaking changes are acceptable wherever they make the council
  cleaner. Migration is "drain in-flight v2.x cycles before
  upgrading" — not a deliverable runbook.

## Business context

The Yoke v2.x runtime ships two coupled defects that the council
architecture is designed to retire together:

1. **Sync defect — adversarial-in-name only.** Today's Generator,
   Validator, and Orchestrator-monitor are spawned in parallel by
   `/yoke:implement`. In practice, Validator and Orchestrator-monitor
   complete *before* Generator finishes the code-generation work they
   are supposed to judge. The verdicts pre-date the artifact —
   structural impossibility for adversarial pressure. The framework
   advertises "objetivos opostos" but at runtime the objectives never
   actually meet.
2. **Coverage defect — two viewpoints, four classes of regression.**
   Generator and Validator together cover correctness ("does it pass
   the contract?") but leave four blind spots that surface repeatedly
   in the audits archived under `discussions/yoke-audit-*`: code
   craftsmanship (smells, conventions, idioms), long-term architecture
   (sustainability, coupling, future extensibility), code review
   (the review-skill-using-agent), and downstream concerns
   (DevOps/pipeline — explicitly out of v0; see Anti-scope).

The aposta is **deliberate**: a council of three personas (Sr Eng,
Sr QA, Sr Staff) costs roughly 3× per cycle but is bet to raise
first-try quality enough to reduce drift findings density. v3.0.0 is
where the framework stops pretending the binary loop works and pays
for the structure that does.

Why now: the v2.x dogfood (2026-04-27 doctrine canonization, 9
framework signals surfaced) crossed the threshold where the binary
loop's structural insufficiency is no longer hypothesis. The pluggable
canonical-memory work (v2.0.0) freed the architecture to evolve Phase
4 without entangling Phase 5.

## Known constraints

What the implementation must respect, grouped by source.

### Technical
- **File-based async communication only.** Claude Code Task subagents
  do not exchange messages in realtime. Inter-persona communication is
  via shared files in `.yoke/runtime/` (chiefly per-persona slices
  merged into a council-readable view). Realtime chat is out.
- **Multi-author writes.** Three personas write concurrently each
  cycle. The protocol must be race-free; per-persona files merged
  at council open is the chosen mechanism (see Resolved decision 2).
- **Hard-bound council rounds.** Phase B.2/B.3 (read others, write
  réplica, re-read) must terminate. Default is 3 réplica rounds per
  cycle, configurable in `.yoke/config.yaml :: overrides`.
- **Sensors and canonical memory available to every persona.** Each
  persona has the same tool surface; their differentiation is in
  objective + sensor selection + prompt, not in tool gating.
- **Pluggable persona definitions.** Persona spec files reuse Claude
  Code's agent-format convention: shipped defaults at plugin-root
  `agents/sr-eng.md`, `agents/sr-qa.md`, `agents/sr-staff.md`; host
  overrides under the host project's `.claude/agents/` directory
  (Claude Code's standard agent resolution order resolves the
  override automatically). Frontmatter is Claude Code's agent shape
  extended with Yoke-specific keys (`objective`, `sensor-toolkit`,
  `review-skill`); Claude Code's loader ignores unknown keys, so the
  same file works for both consumers.

### Regulatory
- None identified. Council is an internal runtime concern.

### Organizational
- **Audience is OSS.** Personas ship as defaults; users override.
  Stone-specific persona shapes are NOT acceptable.
- **Sprint cadence.** Implementation lands across multiple sprints under
  `.yoke/specs/2026-05-01-agent-council.md`; the PRD does not pre-
  budget sprint count.

## Risks

What could go wrong. Each risk has an observable signal and a
mitigation hint. The Validator may consume these in Phase 3 for sensor
calibration.

- **Council convergence ill-defined in implementation.** The decision
  ratifies a hybrid quiescence + contradiction-detection rule (see
  Resolved 3); a sloppy implementation could still loop or escalate
  trivially. Signal: Trigger 4 rate at v3.0.0 launch >50% of cycles.
  Mitigation: Acceptance-Contract scenario covers the consensus rule;
  sensor asserts the rule fired correctly on a fixture cycle.
- **N-fold cost without quality gain.** Council costs 3× per cycle but
  drift findings density doesn't budge. Signal: post-launch drift
  findings density (per `/yoke:drift-sense --target codebase` over
  the last N tasks) is flat vs the v2.x baseline (see Resolved 9).
  Mitigation: anchor the success criterion to drift density and run
  the baseline measurement BEFORE v3.0.0 ships, so the comparison is
  honest.
- **Sync barrier still leaks.** The "wait for all personas" depends
  on `/yoke:implement`'s ability to block on Task subagent completion.
  If Task semantics are weaker than expected (eg fire-and-forget),
  the original sync bug returns dressed up. Signal: a persona's
  verdict references a state from BEFORE code generation completed
  (detectable by file mtime). Mitigation: file-marker guard + sensor
  per Resolved 1.
- **Persona overlap with existing roles.** If Sr Eng = Generator
  renamed, Sr QA = Validator renamed, Sr Staff = Orchestrator-consult
  renamed, the council is a renaming exercise costing 3× for nothing.
  Signal: every persona's behavior reproducible by the v2.x agent
  with a prompt tweak alone. Mitigation: define each persona by its
  sensor toolkit + objective diff, not by its prompt; verify
  irreducibility in tech-spec. Resolved 6 partially mitigates by
  designating Sr Staff as a genuinely new role (not just a rename).
- **Persona spec extension drift.** Yoke extends Claude Code's agent
  frontmatter with extra keys (`objective`, `sensor-toolkit`,
  `review-skill`). If Claude Code tightens its loader to reject
  unknown keys, every shipped persona file becomes invalid. Signal:
  Claude Code release notes flag a frontmatter-validation change.
  Mitigation: tech-spec ratifies the field set; the runtime asserts
  the extension keys at startup and surfaces a clear error when the
  loader rejects them.
- **Concurrent-write race despite per-persona files.** Each persona
  owns its own slice file (Resolved 2), but a buggy merge or a
  persona writing outside its slice could still race. Signal: a
  cycle's merged view contains content not present in any persona's
  slice, OR a persona modifies another persona's slice. Mitigation:
  merge helper is a pure deterministic function; sensor asserts the
  merged view is byte-equivalent to the deterministic merge of the
  per-persona slices.
- **Réplica-round explosion.** Default cap of 3; if too low, real
  disagreements escalate to Trigger 4 prematurely; if too high,
  cycles inflate cost. Signal: ratio of Trigger-4 escalations vs
  council-resolved-by-round-3. Mitigation: replay v2.x audit
  history pre-launch; tune the default during the v3.0 dogfood.

### Resolved

The decisions below are binding inputs for the tech-spec; they are
not re-litigated in Phase 2.

1. **Sync barrier mechanics.** Hybrid: rely on the Task tool's
   blocking semantics for the wait, plus a defensive file-marker
   that each persona writes immediately before its Task exits, plus
   a sensor that asserts every Phase-B read of a per-persona slice
   happens with mtime greater than or equal to the latest Phase-A
   marker. Sync-bug regressions become test failures rather than
   silent runtime drift.

2. **Concurrent-write protocol.** Separate per-persona files merged
   at council open. Each cycle owns a directory under
   `.yoke/runtime/cycles/`; each persona writes only its own slice.
   The council reader merges the slices into a read-only view at
   the start of Phase B. The "single progress.md" invariant is
   replaced by "the cycle's progress is the merge of the cycle's
   per-persona slices." Merge logic lives in
   `lib/runtime/council-merge.sh` as a pure, deterministic helper.

3. **Consensus rule in Phase B.4.** Hybrid quiescence + LLM
   contradiction detection. Quiescence — a réplica round that
   produces zero new réplicas — is the primary signal. When a
   round DID produce réplicas, an LLM arbiter reads the merged
   per-persona slices and emits a structured contradiction-detection
   verdict. Zero contradictions on the last round implies consensus.
   Otherwise the council enters another réplica round (capped — see
   #4) or Trigger 4 if the cap is reached.

4. **Council round cap.** Default of 3 réplica rounds per cycle.
   Configurable via `.yoke/config.yaml :: overrides.runtime.council_rounds_max`.
   The default is validated post-launch by replaying v2.x audit
   history and tuned during the v3.0 dogfood if needed.

5. **Persona definition file format and override path.** Reuse
   Claude Code's agent format. Shipped defaults at plugin-root
   `agents/sr-eng.md`, `agents/sr-qa.md`, `agents/sr-staff.md`.
   Host overrides under the host project's `.claude/agents/`
   directory — resolved automatically by Claude Code's standard
   agent resolution order. Yoke-specific keys (`objective`,
   `sensor-toolkit`, `review-skill`) are added to the frontmatter;
   Claude Code's loader ignores unknown keys, so the same file
   serves both consumers without forking. The runtime validates
   the extended fields at `/yoke:implement` startup and fails
   fast with a clear diagnostic when a persona file is missing
   required keys.

6. **Generator / Validator / Orchestrator → 3-persona mapping.**
   Hybrid: Sr Eng renames Generator (objective + sensor-toolkit
   retooled but agent class preserved); Sr QA renames Validator
   (same shape); Sr Staff is genuinely new — it absorbs the
   former Orchestrator-consult mode AND adds responsibilities
   (canonical-memory-driven architectural review, `/review`
   invocation, long-term sustainability lens). Orchestrator-canonize
   (Phase 5 write authority) survives unchanged and is NOT a
   council persona.

7. **Trigger 4 generalization wording.** Adopted as proposed:
   "Trigger 4 — council arbitration. Fires when, at the end of
   the configured council rounds, at least one pair of personas
   remains in unresolved disagreement (a persona's last verdict
   directly contradicts another persona's last verdict, or a
   persona's last réplica introduces a new objection that no other
   persona's verdict has resolved)." The contradiction-detection
   arbiter from Resolved 3 is the same gatekeeper. Tone or phrasing
   differences with no semantic gap do NOT count as disagreement;
   importance disagreements (one persona says "good enough", another
   says "rework") DO count.

8. **`/codereview` skill provenance.** Sr Staff defaults to Claude
   Code's built-in `/review`. Adopters who want richer review
   override the persona's `review-skill` frontmatter field. The
   `/ultrareview` command is documented as a human-only escalation
   that the user can invoke manually — Sr Staff cannot fire it
   autonomously.

9. **Drift findings density baseline.** Measured before Sprint 1
   begins by running `/yoke:drift-sense --target codebase` against
   each post-merge SHA over the past N tasks, then averaging.
   Output is committed to `.yoke/specs/2026-05-01-agent-council.md`
   under a `## Baseline metrics` heading before tech-spec is
   approved. Capture: total findings count, breakdown by category,
   kLoC denominator (scoped to "code modified or added under the
   v2.x runtime", not total repo size), top three findings
   categories.

10. **Backward compatibility.** None required. The framework is
    still in development; v3.0 may break Phase 4 runtime, Phase 1–3
    artifact shapes, sensor harness, or persona spec wherever it
    makes the council architecture cleaner. Migration is "drain
    in-flight v2.x cycles before upgrading" — not a deliverable
    runbook. This deletes the previously-listed
    backward-compat-verification work item.

11. **Sr QA writes tests.** v0 of Sr QA produces tests, not just
    verdicts. Sr Eng writes happy-path unit tests for new code
    paths; Sr QA writes acceptance-contract-anchored tests plus
    property-based and fuzz tests where applicable, in a new
    directory `tests/acceptance/` namespaced per contract slug.
    When Sr Eng's code does not pass Sr QA's tests AND Sr QA's
    tests are themselves under dispute (Sr Eng believes the test
    is wrong), the council protocol escalates the canonical
    Trigger-4 case; the user is the tiebreaker on "is this test
    fair?".

### Carry-forward (tech-spec resolves)

These are smaller sub-questions inherited from the resolved
decisions; they do not block tech-spec approval but must be closed
before Sprint 1.

- **Cycle directory layout.** Flat per-cycle (one file per persona
  per cycle) versus nested per-cycle-per-round (one file per
  persona per réplica round). Trade-off: flat is simpler; nested
  preserves réplica history for debugging.
- **Contradiction-detection arbiter identity.** A new dedicated
  LLM-judge subagent invoked by `/yoke:implement` between réplica
  rounds, OR a duty rotated among the existing personas. Former is
  cleaner; latter is cheaper.
- **Schema validation surface.** Validate persona files at
  `/yoke:implement` startup (cleanest) or lazily at first
  invocation (cheaper). Default to startup unless a measurable
  cost surfaces.
- **Trigger 4 dispute rubric.** What concrete rubric does the
  contradiction-detection arbiter apply to decide "tone vs.
  semantic disagreement"? Tech-spec authors a small structured
  rubric with worked examples drawn from the v2.x audit history.
- **`review-skill` field arity.** Single value v0; an array
  fallback chain is a v3.x tightening, not a v0 concern.

## Anti-scope

What is explicitly out of v0. Aggressive on purpose.

- **Sr DevOps persona.** Pipeline, metrics, and observability sensors
  do not exist in Yoke today. Building that sensor category is a
  prerequisite spike (likely a separate PRD). DevOps persona deferred
  to v3.x at the earliest.
- **Realtime / chat-shaped inter-persona communication.** Council
  communication is file-based async via per-persona slices merged at
  council open. No realtime protocol, no streaming, no socket layer.
- **Persona override at the sensor level.** v0 personas all have the
  same sensor surface. Per-persona sensor gating is a future tightening,
  not a v0 concern.
- **Renaming of existing canonical-memory entities.** `concepts/yoke-pattern-roles`
  and the 30 decisions referencing Generator/Validator stay where they
  are; the rewrite to reflect the council architecture is part of the
  Phase 5 canonization work AFTER v3.0.0 ships, not the PRD's deliverable.
- **Multi-tenant / multi-org persona registries.** v0 ships defaults
  + single-host override. A registry of swappable persona packs is
  v3.x.
- **Cycle-level token budget enforcement per persona.** Today's
  `cycles_max` covers full implementation cycles; per-persona token
  budgets are a future tightening.

## Success criteria

The bet is anchored to **drift findings density**: violations of
project patterns per kLoC, measured by `/yoke:drift-sense --target
codebase` over the last N tasks shipped post-launch.

- **Baseline:** measured against v2.x main, captured BEFORE v3.0.0
  ships (see Resolved 9).
- **Bet:** v3.0.0 reduces drift findings density by ≥ 30% over the
  first ten tasks shipped on the council architecture.
- **Falsification:** flat or worse density after ten tasks → council
  is overhead without payoff → revisit, do not double-down.

A secondary signal — **first-try Acceptance-Contract pass rate**
(percentage of cycles whose audit goes PASS without Trigger 4 first)
— is captured but is not the primary metric. The primary metric must
be the one the user nominated: drift findings density.
