# PRD: Sprint synthesis via `/yoke:generate-sprints`

> Generated by `/yoke:discover` on 2026-05-03.
> Status: approved
> Approved by: iurykrieger
> Approved at: 2026-05-03T06:39:27Z

## Introduction / Overview

Today, the sprint runtime bundles under `.yoke/sprints/<slug>-s<NN>.md`
are produced by `/yoke:tech-spec` itself: stage 3 of that skill drafts
the sprint objective, DoD, task bodies, functional acceptance-criteria
references, and sensor references — all from the same input (the PRD
plus whatever architecture decisions the persona has made along the
way). `/yoke:acceptance-contract` runs *after* sprints already exist
and retro-fits BDD scenarios onto task IDs the tech-spec already
created. The acceptance artifact is therefore a downstream witness of
the tech-spec's task partition, not a co-equal source of the sprint
shape.

This is the wrong directionality. A sprint is supposed to be a unit
of *delivery*, not a unit of *technical decomposition*. A delivery
unit is defined by the use cases it realizes (acceptance-criteria
domain), bounded by the architecture available to realize them
(tech-spec domain), and only then expressed as a task list and a
sprint partition. With the current flow the team cannot evolve the
acceptance-criteria document independently, cannot see the synthesis
trade-off explicitly, and cannot inspect the produced sprint plan as
its own ratifiable artifact.

This PRD introduces a new skill `/yoke:generate-sprints` that runs
**after** `/yoke:tech-spec` and `/yoke:acceptance-criteria` (the
post-rename name of `/yoke:acceptance-contract`, which is being
addressed in a separate session and is presumed resolved here). The
new skill takes the approved spec and the approved acceptance-criteria
as inputs, synthesizes the full task list, partitions it into sprints
with explicit delivery objectives, and writes the sprint runtime
bundles. `/yoke:tech-spec` becomes architecture-only; the
acceptance-criteria document becomes a use-case catalog (UC-IDs)
without task references; `/yoke:generate-sprints` is the place where
both meet and produce something a council agent can execute.

The new flow is:
`/yoke:discover` → `/yoke:tech-spec` → `/yoke:acceptance-criteria` →
`/yoke:generate-sprints` → `/yoke:implement`.

## Goals

- Decouple sprint generation from `/yoke:tech-spec`: tech-spec stops
  emitting any file under `.yoke/sprints/`.
- Reshape acceptance-criteria around use cases (`UC-1`, `UC-2`, …)
  instead of task-anchored BDD scenarios, so the artifact is
  authorable before tasks exist.
- Introduce `/yoke:generate-sprints` as a self-contained skill that
  takes the spec and acceptance-criteria as parameters, synthesizes
  tasks, partitions sprints, and writes runtime bundles using
  `templates/sprint.md`.
- Make every task self-contained enough that any of Sr Eng, Sr QA, or
  Sr Staff can execute its lens with no follow-up reads beyond the
  cited UC and the cited sensors.
- Preserve coexistence with already-approved tasks under the legacy
  flow — no automatic migration, no breakage of in-flight work.
- Keep `/yoke:implement` agnostic of which flow produced the sprint
  bundles, given that the bundle shape (`templates/sprint.md`) does
  not change.

## Product invariants

These shape constraints survive verbatim into the Acceptance Contract
and bind every sprint of this work.

- **Single source per concern.** Architecture lives only in
  `.yoke/specs/<slug>.md`; use cases / DoD / criteria / FR / sensor
  bindings live only in `.yoke/acceptance-criteria/<slug>.md`; sprint
  runtime bundles live only in `.yoke/sprints/<slug>-s<NN>.md`. A
  field appears in exactly one of these three files.
- **Sprint bundles are derived.** A sprint runtime bundle is a pure
  function of (approved spec, approved acceptance-criteria). Re-running
  `/yoke:generate-sprints` against an unchanged pair must converge to
  the same sprint partition modulo deterministic ordering.
- **Reference-by-ID, never inline.** The `## Functional acceptance
  criteria` and `## Sensors` sections inside sprint files continue to
  carry only IDs that resolve against acceptance-criteria and
  `.yoke/sensors/<id>.md` respectively. No inlined criterion bodies,
  no inlined sensor logic. (Inherits from
  `concepts/yoke-pattern-sprint-runtime-bundle`.)
- **No per-persona forks inside a task.** Each task in the bundle has
  a single, unified instruction block readable by all three council
  personas. Per-persona sub-sections (`**For Sr Eng:**`, etc.) are
  forbidden — guidance density goes into the shared block.
- **Legacy tasks remain valid.** Any task whose sprint bundles were
  emitted by the legacy `/yoke:tech-spec` stage 3 continues to be
  consumable by `/yoke:implement` without re-running
  `/yoke:generate-sprints`.
- **Trigger 2.5 is non-binding for criteria.** The new gate ratifies
  *the sprint partition*, not the acceptance criteria — those are
  already bound under Trigger 3. Approving `/yoke:generate-sprints`'s
  output does not re-open the acceptance-criteria envelope.

## User Stories

### US-001: Refocus `/yoke:tech-spec` to architecture-only

**Description.** As a Yoke user authoring a Tech Spec, I want
`/yoke:tech-spec` to produce only `.yoke/specs/<slug>.md` (objective,
architecture, stack, tradeoffs, dependencies, out-of-scope), so that
sprint generation is no longer entangled with technical decision
authoring.

**Acceptance criteria:**
- [ ] `/yoke:tech-spec` writes exactly one file at
  `.yoke/specs/<slug>.md` and no file under `.yoke/sprints/`.
- [ ] The retired stage 2 (`scaffold-sprints.sh` invocation) and stage
  3 (per-sprint LLM fill) are removed from the skill body.
- [ ] `templates/spec.md` is updated to drop sprint-index sections that
  reference task bodies; cross-sprint architecture remains.
- [ ] `tests/smoke/tech-spec-architecture-only.test.sh` exits 0 against
  a fixture run that asserts no `.yoke/sprints/<slug>-s*.md` files are
  created by `/yoke:tech-spec`.
- [ ] Existing smoke tests that asserted sprint creation under
  tech-spec are either deleted or moved to the
  `/yoke:generate-sprints` test surface.

### US-002: Reshape acceptance-criteria around use cases

**Description.** As a Yoke user authoring acceptance-criteria, I want
the artifact to enumerate use cases (`UC-1`, `UC-2`, …) carrying name,
DoD, acceptance criteria, FR mapping, and sensor list — independently
of any task IDs — so that the document can be ratified before
`/yoke:generate-sprints` produces tasks.

**Acceptance criteria:**
- [ ] `templates/acceptance-criteria.md` exists and lists use cases
  with the documented shape (`### UC-<n>`, body fields: name, DoD,
  criteria, FRs, sensors).
- [ ] `/yoke:acceptance-criteria` (post-rename name) emits a file that
  contains zero strings matching `<slug>-s[0-9]+-t[0-9]+` (no task
  references).
- [ ] Each `### UC-<n>` carries at least one bound sensor ID resolvable
  against `.yoke/sensors/`.
- [ ] `tests/smoke/acceptance-criteria-shape.test.sh` exits 0 against
  a fixture acceptance-criteria authored to the new template.

### US-003: New `/yoke:generate-sprints` skill scaffolding

**Description.** As a Yoke user, I want a new callable skill at
`skills/generate-sprints/SKILL.md` that takes the spec and the
acceptance-criteria file paths as parameters, runs the standard
pre-flight (config + provider hard break + active-task check), and
fails fast if either input is missing or unapproved, so that the
skill can be invoked deterministically by the user or by chained
flows.

**Acceptance criteria:**
- [ ] `skills/generate-sprints/SKILL.md` exists with frontmatter
  declaring `name: generate-sprints`, an `argument-hint`, and an
  `allowed-tools` list that includes `Read, Write, Edit, Bash, Skill`.
- [ ] Pre-flight refuses to run when `.yoke/config.yaml` is missing or
  lacks `canonical_memory.provider`, surfacing the standard
  `yoke_require_provider` stderr verbatim.
- [ ] Pre-flight refuses to run when `.yoke/specs/<slug>.md` is absent
  or its frontmatter `status` is not `approved`.
- [ ] Pre-flight refuses to run when
  `.yoke/acceptance-criteria/<slug>.md` is absent or its frontmatter
  `status` is not `approved`.
- [ ] `tests/smoke/generate-sprints-preflight.test.sh` exits 0 across
  fixtures covering: missing spec, missing AC, unapproved spec,
  unapproved AC, all-good.

### US-004: Synthesis stage — tasks from spec ⊕ acceptance-criteria

**Description.** As a Yoke user, I want `/yoke:generate-sprints` to
read both inputs, consult canonical memory via
`/yoke:search-canonical-memory` when a UC needs context, and produce
an in-memory task list where each task realizes one or more UCs and
respects one or more architecture decisions, so that downstream
partitioning has a complete and ordered task graph to work with.

**Acceptance criteria:**
- [ ] The skill emits a structured intermediate (committed to runtime
  state under `.yoke/runtime/.generate-sprints-plan.yaml`, gitignored)
  that lists tasks with fields: `task_id`, `realizes_ucs`,
  `applies_decisions`, `instructions`, `sensors`, `acceptance_criterion`.
- [ ] Every task lists at least one UC it realizes.
- [ ] Every UC in the input acceptance-criteria is realized by at
  least one task (no orphan use cases). The skill exits non-zero if
  any UC is left unrealized.
- [ ] The skill MAY invoke `/yoke:search-canonical-memory` and the
  invocation is logged once per call to `progress.md` runtime stream.
- [ ] `tests/smoke/generate-sprints-synthesis.test.sh` exits 0 against
  a fixture pair (spec + AC) and asserts the plan file's UC coverage.

### US-005: Sprint partitioning + bundle materialization

**Description.** As a Yoke user, I want the skill to partition the
synthesized task list into sprints with explicit delivery objectives
and binary DoD, then write each sprint as a runtime bundle at
`.yoke/sprints/<slug>-s<NN>.md` using `templates/sprint.md`, so that
the output is consumable by `/yoke:implement` without modification.

**Acceptance criteria:**
- [ ] Each rendered sprint file conforms to `templates/sprint.md`:
  YAML frontmatter (`task_id`, `sprint`, `slug`, `status`,
  `created_at`, `model`, `traceability`) plus the 5 H2 sections in
  fixed order.
- [ ] Frontmatter `traceability` cites both
  `.yoke/specs/<slug>.md` and `.yoke/acceptance-criteria/<slug>.md`.
- [ ] Each `### Task <ID>` carries the four inline labels
  (`**Story:**`, `**Technical implementation:**`, `**Validation:**`,
  `**Acceptance criterion:**`) and includes a parenthesized
  `(Realizes: UC-N[, UC-M])` clause adjacent to the Story line.
- [ ] `## Functional acceptance criteria` lists UC-IDs only — no
  inlined bodies — and the union across the sprint covers every UC
  realized by tasks in that sprint.
- [ ] `## Sensors` lists sensor IDs only, computed from the union of
  sensors bound to the realized UCs.
- [ ] `tests/smoke/generate-sprints-bundle-shape.test.sh` exits 0
  against a multi-sprint fixture and asserts no orphan UCs and no
  inlined sensor logic.

## Functional Requirements

- **FR-1:** `/yoke:tech-spec` MUST NOT write any file under
  `.yoke/sprints/`. Verifiable by running `/yoke:tech-spec` against a
  fixture and asserting `find .yoke/sprints -newer <pre> -type f` is
  empty.
- **FR-2:** `/yoke:tech-spec`'s output `.yoke/specs/<slug>.md` MUST NOT
  contain any per-task body (no `### Task <slug>-s<NN>-t<MM>` headings,
  no `**Story:**` / `**Technical implementation:**` /
  `**Validation:**` / `**Acceptance criterion:**` labels).
- **FR-3:** `/yoke:acceptance-criteria` MUST emit a file at
  `.yoke/acceptance-criteria/<slug>.md` whose body lists at least one
  `### UC-<n>` heading, where each UC carries name, DoD, criteria,
  FR mapping, and a sensor list.
- **FR-4:** `/yoke:acceptance-criteria` MUST NOT emit any string
  matching the regex `<slug>-s[0-9]+-t[0-9]+` (i.e., no task IDs are
  referenced because tasks do not yet exist).
- **FR-5:** `skills/generate-sprints/SKILL.md` MUST exist with
  frontmatter (`name`, `description`, `argument-hint`,
  `allowed-tools`).
- **FR-6:** `/yoke:generate-sprints` MUST refuse to run when
  `.yoke/config.yaml` is missing or `canonical_memory.provider` is
  empty (standard provider hard break).
- **FR-7:** `/yoke:generate-sprints` MUST refuse to run when either
  `.yoke/specs/<slug>.md` or `.yoke/acceptance-criteria/<slug>.md` is
  missing, or when either has frontmatter `status` not equal to
  `approved`.
- **FR-8:** `/yoke:generate-sprints` MUST emit one or more files at
  `.yoke/sprints/<slug>-s<NN>.md` conforming to `templates/sprint.md`.
  Verifiable by parsing the frontmatter and matching the 5 H2 section
  ordering.
- **FR-9:** Every UC listed in the input acceptance-criteria MUST be
  realized by at least one task across the produced sprints. The skill
  MUST exit non-zero with `wm: unrealized UCs: UC-N[, UC-M]` on
  stderr if any UC is left without a realizing task.
- **FR-10:** Every produced task MUST cite at least one UC via a
  `(Realizes: UC-N[, UC-M])` clause adjacent to its `**Story:**` line.
- **FR-11:** Every produced task MUST contain a single unified
  instruction block (no per-persona sub-sections such as
  `**For Sr Eng:**`).
- **FR-12:** `/yoke:generate-sprints` MAY invoke
  `/yoke:search-canonical-memory` for cross-task context, and each
  invocation MUST be logged once to `.yoke/runtime/progress.md` as a
  `search:` event, per existing logging conventions.
- **FR-13:** `/yoke:generate-sprints` MUST render the shared approval
  menu (Trigger 2.5) and only flip every produced sprint file's
  frontmatter to `status: approved` after the user replies `approve`
  or `approve_and_continue`.
- **FR-14:** `/yoke:implement` MUST refuse to run when the active task
  is in state `awaiting:generate-sprints` (i.e., a spec and an
  acceptance-criteria file exist but no sprint files do). Surface the
  literal stderr `wm: run /yoke:generate-sprints to advance to Phase 4`
  and exit non-zero.
- **FR-15:** `/yoke:implement` MUST consume legacy-flow sprint bundles
  (those emitted by the legacy `/yoke:tech-spec` stage 3, identifiable
  by absence of `.yoke/acceptance-criteria/<slug>.md`) without
  modification.
- **FR-16:** Re-running `/yoke:generate-sprints` against a legacy task
  MUST exit non-zero with the literal stderr `wm: legacy task —
  generate-sprints does not migrate` and MUST NOT touch any file under
  `.yoke/sprints/`.
- **FR-17:** `/yoke:status` MUST surface the new gate
  `awaiting:generate-sprints` when the active task has approved spec +
  approved acceptance-criteria but zero sprint files.

## Non-Goals (Out of Scope)

- **Renaming `/yoke:acceptance-contract` → `/yoke:acceptance-criteria`
  and the directory `.yoke/acceptance-contracts/` →
  `.yoke/acceptance-criteria/`.** This is being addressed in a
  separate session and is presumed done; this PRD writes against the
  post-rename names.
- **Migrating already-approved legacy tasks** (those currently in
  `.yoke/sprints/` or `.yoke/specs/` whose runtime ran under
  `/yoke:tech-spec` stage 3). Decision 6A: legacy tasks remain
  unchanged.
- **Changing the council protocol** (Phase A / B / C, sync barrier,
  arbiter). The council consumes the same `templates/sprint.md`
  bundle shape as today; this work modifies *who produces* that
  bundle, not *what it looks like at the consumer side*.
- **Per-persona forks inside a task body.** Decision 5A: instructions
  are unified, shared by Sr Eng, Sr QA, Sr Staff.
- **Adding LLM-driven sprint count estimation** (e.g., "this task
  needs 3 sprints"). Sprint partitioning is the skill's deterministic
  output of the synthesis stage; if the synthesis stage produces a
  too-large or too-small partition, the user iterates via the
  `revise` verb of the approval menu.
- **A new sensor for detecting sprint-bundle drift.** Existing
  invariants (sprint-runtime-bundle pattern, reference-by-ID) cover
  the contract surface.

## Design Considerations

- The new skill produces the same `templates/sprint.md` shape as
  today's stage 3. From the consumer's standpoint
  (`/yoke:implement`, the council personas, `/yoke:status`) nothing
  changes; this is a producer-side refactor.
- The new approval menu (Trigger 2.5) reuses
  `templates/approval-menu.md` with a different `artifact_label`. No
  new template is required.
- The skill sits at `skills/generate-sprints/SKILL.md` and adopts the
  same lib helpers as siblings: `lib/yoke-prelude.sh`,
  `lib/working-memory/paths.sh`, and the canonical-memory facade
  `/yoke:search-canonical-memory`.

## Technical Considerations

### Technical
- **Single deterministic spine.** The synthesis stage is LLM-driven
  but bracketed by deterministic bash: pre-flight (`yoke_require_provider`
  + status checks), input file reads via `wm_*_path`, intermediate
  plan write under `.yoke/runtime/`, sprint-file scaffold reuse via
  the existing `templates/sprint.md`, and approval-menu render via
  the shared template.
- **Reuse `templates/sprint.md` unchanged.** Adding fields would force
  template churn; the `(Realizes: UC-N)` clause inside each
  `**Story:**` line satisfies the UC-trace requirement without a
  template change.
- **Plan file is gitignored.** `.yoke/runtime/.generate-sprints-plan.yaml`
  is intermediate state; only the final sprint files are versioned.

### Regulatory
- None.

### Organizational
- **Hard dependency on the rename PR.** The renaming of
  `acceptance-contract` → `acceptance-criteria` is being addressed in
  a separate session and MUST land before the implementation PR for
  this work. The Tech Spec presumes the rename is complete and writes
  against the post-rename paths (`/yoke:acceptance-criteria`,
  `.yoke/acceptance-criteria/<slug>.md`). No transitional dual-name
  path is supported. (Resolved at Trigger 1 ratification on
  2026-05-03.)

## Risks

- **Tech-spec consumers break.** Removing sprint generation from
  `/yoke:tech-spec` may break smoke tests or upstream tooling that
  asserts the post-tech-spec state includes sprint files. **Signal:**
  smoke-test failures in `tests/smoke/tech-spec*`. **Mitigation:**
  inventory all `.yoke/sprints/` references in test files during
  US-001 and migrate them.
- **Synthesis quality regression.** The new LLM stage may produce
  task partitions visibly worse than today's tech-spec stage 3 (too
  fine-grained, too coarse, drifting from the established 4–8 task
  per sprint baseline). **Signal:** task count per sprint exits the
  baseline window of 3–10 (current corpus mean 5.4) on a calibration
  fixture. **Mitigation:** include a calibration fixture under
  `tests/fixtures/generate-sprints-calibration/` derived from
  `2026-05-01-agent-council` and assert the partition stays in-window.
- **AC shape change disrupts in-flight tasks.** If the
  acceptance-criteria template changes shape mid-sprint of an
  in-flight task, that task's existing AC file becomes invalid.
  **Signal:** `/yoke:status` errors on tasks whose AC predates the
  shape change. **Mitigation:** detect the new shape by presence of
  any `### UC-<n>` heading; legacy ACs (no UC headings) keep their
  legacy interpretation.
- **Approval fatigue from a 4th gate.** Adding Trigger 2.5 (sprint
  plan) increases the number of human-in-the-loop pauses from 4 to
  5 per task. **Signal:** approvals come back within < 30 seconds
  with no edits across more than 3 consecutive tasks (rubber-stamp
  pattern). **Mitigation:** the rendered sprint plan must fit in
  one screen per sprint; the approval menu suppresses verbose
  guidance.
- **Doctrine drift.** Two flows (legacy / new) coexisting indefinitely
  invites doctrine confusion in canonical-memory entries. **Signal:**
  contradictory `concepts/yoke-pattern-*` entries land within the
  next two canonization rounds. **Mitigation:** the
  canonize handoff for this PRD includes a single doctrine entry that
  declares the cut-over date and explicitly retires the legacy
  description from `yoke-pattern-sprint-runtime-bundle`.

## Success Metrics

- **Producer split realized.** `grep -RIn 'sprints/' skills/tech-spec/`
  returns zero results post-cutover.
- **UC coverage.** On every new-flow task created in the first
  calibration window, every UC in
  `.yoke/acceptance-criteria/<slug>.md` appears in at least one
  `(Realizes: UC-N)` clause across `.yoke/sprints/<slug>-s*.md`.
- **Partition stability.** Tasks-per-sprint distribution across the
  first 3 new-flow tasks stays within ±30 % of the legacy baseline
  mean (5.4 tasks / sprint).
- **Trigger 4 frequency unchanged.** Council Trigger 4 fires at-or-
  below the 30-day rolling baseline post-cutover (no quality
  regression introduced by the refactor).
- **Legacy walks succeed.** All currently approved legacy tasks
  (`2026-04-27-*`, `2026-04-30-*`, `2026-05-01-*`) keep walking
  cleanly under `/yoke:implement` post-cutover.
