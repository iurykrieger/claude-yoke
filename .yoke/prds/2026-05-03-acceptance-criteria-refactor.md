## Introduction / Overview

Yoke's Phase 3 today produces an artifact called the **Acceptance
Contract**, materialized at `.yoke/acceptance-contracts/<slug>.md`. The
shape — BDD scenarios anchored to task IDs, a flat sensor list per
scenario, a parallel `## Functional requirements` block, and the same
word "contract" reused for sprint contracts (`.yoke/contracts/<slug>.md`),
sprint-contract amendments, contract-time sensor smokes, and more —
makes the artifact ambiguous to both human readers and council personas
in Phase 4. The dogfood signal `2026-04-27-yoke-contract-time-sensor-smoke`
already records one class of failure that traces back to this overload:
the artifact's binding semantics are clear, but its *shape* doesn't
help readers separate **what's complete (Done)** from **what's
acceptable (Quality)**.

The pain is concrete: when a task ships, neither the human ratifier
nor the Sr QA / Sr Staff personas have a clean place to ask "is this
done?" separately from "is the quality acceptable?". Today both
questions collapse into one BDD scenario block with one list of
sensors, and the council's Phase B spends rounds re-litigating the
distinction instead of making it operational.

This refactor is a **forward-only** restructuring of the Phase 3
artifact. We rename `acceptance-contracts/` to `acceptance-criteria/`,
restructure the file around **User Stories → Definition of Done →
Acceptance Criteria → Sensor pool**, and let the runtime council
decide *which* sensors apply to which criterion at validation time.
The 17 historical files under `.yoke/acceptance-contracts/` are not
migrated — Yoke is in active development, the cutover is clean.

## Goals

- Eliminate naming collision between the Phase 3 artifact and Phase 4
  sprint contracts by renaming the artifact and its directory to
  `acceptance-criteria/` and the skill verb to
  `/yoke:acceptance-criteria`. This is a **breaking change**: Yoke
  ships as **v4.0.0**, the legacy `acceptance-contract(s)` paths and
  helpers are removed (not delegated), and host projects pinning
  `claude-yoke@3.x` must explicitly upgrade.
- Make **Done** (binary, completion-anchored) and **Acceptable**
  (multi-criterion, quality-anchored) structurally distinct in the
  artifact, mirroring standard QA discipline.
- Move user-story authorship (`US-###`) out of the PRD entirely. The
  Tech Spec is **unchanged** — it stays as the engineering breakdown
  and does not gain a US-### responsibility.
  `/yoke:acceptance-criteria` becomes the **sole owner** of user-story
  generation, performed via interactive dialogue with the human.
- Replace the inline `Sensors: [a, b, c]` flat list per BDD scenario
  with a per-document **Sensor pool** that the council reads at
  runtime; the Sr QA + Sr Staff personas decide which pool members
  apply to each criterion at validation time.
- Make the skill itself an **interactive grill** in the same shape as
  `/yoke:discover` and `/yoke:tech-spec`: read PRD + Tech Spec, present
  a structured *resume* of both back to the user, then drive a
  lettered-option dialogue scoped to base quality gates (US
  enumeration, DoD per story, AC per story, sensor pool). The skill
  never auto-generates the artifact silently from PRD + Spec alone.
- Preserve binding semantics — Trigger 3 still ratifies; sprint
  contracts still operate inside the envelope; runtime modifications
  still require a fresh ratification round.

## Product invariants

- **Binding gate intact.** Approving the acceptance-criteria document
  remains Trigger 3. Approval freezes the document operationally;
  Phase 4 cannot relax it.
- **Single source of truth for QA scope.** User stories, DoD, and
  acceptance criteria live in exactly one place — the
  acceptance-criteria document. PRDs do not contain US-### at all
  after v4.0.0; Tech Specs do not contain US-### either.
  Cross-references go by ID only.
- **Sensors-as-pool.** The acceptance-criteria document declares a
  pool of relevant sensors; it does not assign sensors to criteria at
  authoring time. Pool members must each resolve to a
  `.yoke/sensors/<id>.md` file (existing invariant).
- **Cutover, not migration.** Files under `.yoke/acceptance-contracts/`
  remain frozen on disk for historical reference; new tasks write to
  `.yoke/acceptance-criteria/<slug>.md` only.
- **DoD ⇒ AC, never the reverse.** A user story cannot be Acceptable
  if it isn't Done. The runtime council enforces ordering: DoD checks
  must pass before any AC is evaluated for that story.
- **No silent generation.** `/yoke:acceptance-criteria` MUST run an
  interactive grill before materializing the artifact; auto-derivation
  from PRD + Tech Spec without human dialogue is a banned mode. The
  human's lettered-option answers are the artifact's source of truth,
  not the LLM's inference from upstream documents.

### US-002: Restructure the artifact around User Story → DoD → Acceptance Criteria

**Description.** As a council persona consuming the binding artifact
in Phase 4, I want the document to be organized by user story, with
each story carrying a single Definition of Done and one or more

## Design Considerations

- The DoD vs AC split is borrowed from standard QA discipline: DoD
  defines completion (binary, single per work item); AC defines
  acceptability (multiple per work item, observable, often
  Given/When/Then). The artifact's hierarchy mirrors this directly so
  agents and humans see the same structure QA practitioners already
  reach for.
- Each AC entry should still be expressible as Given/When/Then or as
  a clean observable condition; the template will offer both shapes
  and let the author pick per criterion.
- The Sensor pool section is plain text on purpose — keeping it
  parseable by a single regex (`^- <sensor-id>$` or similar) lets
  the runtime council read the pool without YAML overhead.

## Risks

- **Orphan references after rename.** *Description:* a `grep` for
  `acceptance-contract` in active code paths returns matches after
  the cutover. *Signal:* CI fails the orphan-ref sensor; or a
  Phase 4 cycle reads a stale path and produces an empty document.
  *Mitigation:* ship a single binding sensor that asserts zero
  matches outside `.yoke/acceptance-contracts/historical/` and
  intentional historical references in `docs/migration-*.md`.
- **Council can't pick sensors at runtime.** *Description:* without
  a classification at authoring time, Sr QA / Sr Staff over- or
  under-run sensors and the cycle either thrashes (running every
  pool member every cycle) or under-validates (skipping pool
  members it should have run). *Signal:* council cycles take longer
  than the v3.0 baseline OR Trigger 4 fires on validation
  divergence more often than baseline. *Mitigation:* persona
  prompts include explicit selection heuristics and the slice file
  records the rationale; Phase B arbiter treats sensor-selection
  disagreements as direct contradictions, surfacing the problem
  fast.
- **DoD vs AC distinction misapplied by authors.** *Description:*
  authors collapse both into one list ("done = passes all AC") and
  the structural split adds ceremony without clarity. *Signal:* in
  the first 3 tasks authored under the new shape, DoD blocks contain
  items indistinguishable from AC items. *Mitigation:* template
  carries inline guidance + at least one shipped example
  (acceptance-criteria for *this very PRD*) demonstrates the split.
- **Doctrine drift.** *Description:* `concepts/yoke-pattern-acceptance-contract`
  in canonical memory keeps the old name and shape; the framework's
  own doctrine becomes a stale source of truth. *Signal:*
  `/yoke:search-canonical-memory` returns the old pattern when
  asked about Phase 3. *Mitigation:* the canonization PR for this
  task supersedes the existing pattern entity (using the
  `supersedes:` graph field) and writes a new
  `concepts/yoke-pattern-acceptance-criteria` entry.
- **Grill fatigue.** *Description:* the new dialogue adds a fifth
  interactive surface (after `/yoke:discover` and `/yoke:tech-spec`),
  each with its own grill rounds; the cumulative ratifier load
  becomes a bottleneck on small features and the user starts
  rubber-stamping. *Signal:* in the first 5 tasks under v4.0.0,
  the average turn-count of the `/yoke:acceptance-criteria`
  dialogue is < 2 (i.e., the user accepts the first proposal
  without challenge), or the user records "no changes" to ≥ 80% of
  candidate user stories the skill proposes. *Mitigation:* the
  Quick-Round fast-track from `/yoke:discover` (skip multi-round
  dialogue when the input is already crisp) is mirrored here —
  when PRD goals + Tech Spec sprints already imply unambiguous US
  + DoD + AC, the skill proposes the full draft and converges in
  one confirmation round.
