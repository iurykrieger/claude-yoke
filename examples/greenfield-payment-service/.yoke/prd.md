## Product invariants

What must hold regardless of implementation. Non-negotiable.

- Reversal is **idempotent on `tx_id`** — multiple reversal attempts on the same transaction must produce at most one refund.
- Refund amount equals the original `tx.amount` minus already-refunded amount; never exceeds the original.
- Reversal succeeds only when the original transaction is in a `settled` state.
- Every reversal emits an audit event (`reversal.requested`, `reversal.completed`, `reversal.failed`) with the original `tx_id`, the requestor identity, and a UTC timestamp.

## Business context

Customer support handles ~50 reversal requests per week, currently as
manual SQL UPDATE statements + emails to the payments provider. This is
slow (avg 2-day cycle time), error-prone (one out of forty results in a
double-refund or a missed refund), and not auditable in any structured
way. The new service is the first step in automating the support
team's most frequent escalation.

Strategic context: payments compliance audit lands in 90 days; auditors
need an automated trail for all reversals. Manual SQL is a finding
risk.

## Known constraints

### Technical
- Must integrate with the existing Stripe-like gateway via its existing
  `/refunds` API (no new external integrations).
- Must run on the existing Node.js 20 / TypeScript 5 stack; no new
  language platforms.
- Must publish events to the existing internal `payments-events` Kafka
  topic; no new event buses.

### Regulatory
- **PCI-DSS 3.2.1** — never log full card numbers, CVV, or PINs in
  audit events. (Already enforced in the gateway client; the new
  service inherits.)
- **LGPD art. 46** — refund-correlated PII (customer email, phone) must
  be redacted from logs by default; full PII is available only via the
  audited admin trace endpoint.

### Organizational
- Owned by the **payments squad** (3 engineers); coordination with
  customer-support team for the support tooling rollout.
- Must ship before the 2026-07-25 compliance audit.

## Risks

- **Race condition on concurrent reversal requests** for the same `tx_id`. Signal: duplicate `reversal.completed` events. Mitigation: row-level lock on the `transactions` table during the reversal flow.
- **Gateway API rate limit** under bulk-reversal scenarios (e.g., a fraud event triggering 200 simultaneous reversals). Signal: HTTP 429 from the gateway. Mitigation: token-bucket retry with exponential backoff.
- **PII leak via audit-event payloads.** Signal: any audit event with raw email or phone number. Mitigation: PII redaction enforced at event-emission time, not at the consumer side.

## Open questions

- None. (All resolved during discovery: customer-facing UX is out of scope; only the support-tool API; no partial refunds in v0; no multi-currency handling — single-currency only.)
